# AutoResearch 实施任务总览

**状态：** T01–T03 已完成，T04–T18 未开始。  
**更新日期：** 2026-10-17。  
**本次交付：** 阶段 01 本地工作台，独立模块、SQLite、项目与会话 API 和 React 页面已实现，见[验收记录](phases/01-workspace/ACCEPTANCE.md)。

**当前设计：** 阶段 02 独立[设计](phases/02-agent-runtime/DESIGN.md)与[实施计划](phases/02-agent-runtime/IMPLEMENTATION.md)已编写，等待评审，源码未实施。

**Goal:** 交付一个面向计算机专业学生的研究 Agent：在项目会话中整理论文、探索方向、开展调研，并通过 SSH 在实验室服务器运行论文复现或用户实验。

**Architecture:** 整个产品是一个 AutoResearch Agent，内部按交互、应用、领域、基础设施四层实现。应用直接用 goHarness Graph 编排理解/澄清、业务分流、产物检查、执行与核对，复用现有模型/工具节点与恢复机制；三个任务类型共用会话入口和项目上下文。

**Tech Stack:** Go 1.24、React 19、TypeScript 5、Vite 7、SQLite、goHarness 现有 Graph / LLM / Tool / MCP / Stream / State / Observe；本机 Connector 使用 OpenSSH。

> 执行者按 writing-plans / executing-plans 的检查点逐项执行。本计划不要求委派子代理。用户已授权开始阶段 01，该阶段已完成；后续阶段仍按各自设计、实施与验收推进。

## 二、实施前确定的选择

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 项目位置 | 全部留在本目录，内部可分子目录 | 满足“一个项目文件夹”，不再把业务放入框架核心 |
| Go 依赖 | 创建独立 go.mod，使用两个本地 replace 引用 goHarness 及 extensions | 应用的 SQLite 等依赖不修改框架模块 |
| 数据持久化 | SQLite 保存业务、事件和检查点；大文件进入 data/artifacts | 支持项目长期保存、浏览器刷新和服务重启 |
| 运行环境 | 单用户、本机 Go 服务 + Web；CLI 只做调试和离线验收 | 第一版先打通真实工作台 |
| Agent | 一个统一定义，按会话隔离历史；研究 / 复现 / 用户实验是任务类型 | 保留自主选择工具、观察与继续执行的循环 |
| 主流程编排 | 应用直接定义 Graph 主图、ResearchState 和 State Codec | 可以增加节点/分支；不套内置 agent.New，不重新实现调度与恢复 |
| 学术接入 | arXiv MCP 优先，Zotero 为后续适配任务 | 复用现有 extensions/mcp，结果仍归档到项目 |
| 外部执行 | 本机 Connector + SSH；优先受控 Linux 环境 | 不要求实验室部署 AutoResearch 常驻进程 |
| 长任务 | 应用任务台账 + 服务器已有任务管理器 | Agent 或浏览器断开不等于实验停止 |
| 框架 API | 使用现有公共 API | 不增加 ObservedModel、公共 Agent 层或替代事件协议 |

独立模块建成后，项目命令必须在本目录运行。父模块的 go test ./... 不会包含嵌套模块；本项目必须有独立测试入口。

## 三、全局约束

- 所有新项目文件均位于 extensions/examples/auto-research/。
- 中文注释和文档；Go 源码使用 gofmt。
- 领域代码不导入模型 SDK、HTTP、数据库或 SSH。
- 使用现有 callback 和 observe；保留 StreamReader[T] 的类型边界。
- MCP 作为工具来源；注册原始 MCP 工具不代表项目数据已保存。
- 业务对象、框架检查点和远程任务台账分别存储。
- 工具从可信 Context 获取用户、项目和当前任务身份，不能相信模型提供的 user_id/project_id。
- 同一会话同一时刻一个活动 Agent turn；等待确认时普通新消息返回冲突，使用确认入口继续。
- 执行审批绑定计划版本和哈希；计划变化必须重新确认。
- 框架恢复允许重放；外部任务幂等和提交结果核对由应用负责。
- 秘钥留在环境变量引用、OS 凭据存储或 SSH Agent 中，不能进入模型上下文、日志、检查点和业务表。
- 离线 fixture 只证明流程、失败处理和数据一致性，不证明真实研究或复现质量。
- 用户未要求部署、发布、推送；任务验收不自动触发这些动作。
- 当前工作区存在无关改动，实施时只提交本项目文件；核心修改另立任务。
- 集中执行阶段验证，不运行竞态测试；必要的失败回归先确认能复现再实现。

## 六、执行纪律

每项任务按“行为用例 → 失败复现 → 最小实现 → 阶段验证 → 评审记录”推进。阶段 01 对应类型和 API 已实现；其他候选类型和函数签名仍待实现，不能当作现有框架 API。

- [ ] 阶段开始前核对前置任务、文件和契约版本。
- [ ] 每个缺陷 / 新行为选择能捕捉真实错误的用例；不为简单 getter 或文案镜像写测试。
- [ ] 只在依赖相同、已授权的范围内实现，不自动切换到后续里程碑。
- [ ] 阶段结束集中验证并记录命令、结果和未覆盖的外部依赖。
- [ ] 如提交 Git，按任务只暂存指定项目文件，每项形成一个可审查提交；不顺带提交工作区其他改动。

## 七、最终验收路径

创建研究项目 → 新建会话 → Agent 搜索学术 MCP → 将论文归档到项目 → 分析证据并提出方向 → 用户确认 → 自动调研和报告 → 选择论文复现或用户实验 → 本机 Connector 检查服务器 → 用户确认具体计划 → 远程运行 → 重连并查看日志 → 收集指标 → 生成有来源的比较结果。

阶段 01 已完成独立模块、真实 API、React 页面与重启持久化验收。上述完整研究与实验流程仍是阶段 02–06 的目标，不能将工作台验收等同于 Agent、MCP 或 SSH 已接通。
