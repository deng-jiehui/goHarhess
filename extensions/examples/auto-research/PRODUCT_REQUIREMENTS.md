# AutoResearch 产品需求文档

**文档状态：** V1.1 需求基线（Agent 产品修订稿）  
**项目类型：** 面向计算机专业学生的论文研究工作台  
**实现基础：** goHarness Graph / LLM / Tool / RAG / Checkpoint / Stream  
**第一版目标：** 可运行、可解释、可恢复的论文整理、自动研究和受控实验复现系统

## 1. 产品定位

AutoResearch 是一个面向计算机专业学生的研究工作台。用户以“项目”为单位组织一个研究主题，以“会话”与 Agent 讨论问题、整理论文和推进研究任务。系统能够搜索和收录论文，帮助用户梳理研究方向，生成检索计划，提取论文证据，比较不同方法，访问用户授权的实验室服务器，执行受控的论文复现实验，最后形成带引用和实验记录的研究报告。

产品本身是一个研究 Agent。第一版提供统一的会话入口，由 Agent 根据用户目标、项目上下文和工具结果推进任务。论文研究、论文复现和用户实验是同一个 Agent 的三种任务模式，共用项目、会话和工具。应用直接使用 goHarness Graph 定义模型决策、工具执行、校验与结束流程，框架负责节点执行、事件和检查点恢复；后续按需要增加节点或分支，明确的批处理也可封装为工具内部流程。

它的交互形态参考代码 Agent：

```text
项目
  ├─ 研究方向
  ├─ 论文库
  ├─ 会话
  ├─ 研究任务
  ├─ 服务器连接
  ├─ 实验复现任务
  └─ 报告与其他产物
```

用户可以先聊天，再把聊天中的研究问题转成研究任务；也可以直接从项目启动一次 AutoResearch。每次任务都要展示计划、进度、工具调用、候选论文和可恢复状态。

## 2. 面向用户与核心问题

### 2.1 目标用户

第一目标用户是计算机专业本科生、研究生和课程项目成员。他们通常有一个模糊方向，能够阅读论文，但缺少系统整理资料、比较方法和形成研究问题的工具。

### 2.2 要解决的问题

- 论文分散在多个来源，用户难以形成自己的论文库；
- 只知道一个大方向，不知道可以拆成哪些研究子方向；
- 读过论文后，难以统一记录问题、方法、数据集、指标和局限；
- 普通聊天容易丢失项目上下文，研究过程无法继续；
- AI 生成的结论缺少原文证据，难以判断是否可靠；
- 自动研究过程不可见，用户不知道系统查了什么、为什么纳入或排除论文；
- 论文中的代码、环境和数据通常分散在实验室服务器上，用户需要手动配置环境、提交任务、查看日志和比较结果。

### 2.3 产品承诺

系统帮助用户**发现、整理、理解、比较和复现论文**，并把研究过程保存为可以继续推进的项目。系统输出研究辅助结果和实验记录，用户对最终研究结论负责；系统不能把一次运行成功等同于科学结论成立。

## 3. 参考产品模式

参考产品只用于提取交互模式，不复制其品牌或完整功能。

| 产品 | 可借鉴模式 | 本项目的取舍 |
| --- | --- | --- |
| [Elicit](https://elicit.com/) | 研究问题驱动的报告、语义论文搜索、论文库、研究报告、交互式表格、逐句引用、可持续研究流程 | 借鉴“证据表 + 引用 + 研究流程”，第一版只接公开来源和有限论文数量 |
| [Consensus](https://consensus.app/) | 面向研究问题的论文检索和回答 | 借鉴“先问问题再检索”，保留完整候选集和筛选过程 |

Elicit 官方页面强调研究报告、论文搜索、论文库、系统综述辅助、交互式研究流程和句子级引用；这些模式说明 AutoResearch 的核心界面应是“项目工作区 + 证据表 + 会话”，而不是一个孤立的聊天框。参考页面于 2026-10-16 访问。

## 4. 核心概念

### 4.1 Project 项目

项目是用户研究一个主题的长期工作区。

项目字段：

- 名称、简介、研究领域；
- 当前研究问题和目标；
- 研究范围：年份、语言、来源、论文数量上限；
- 项目状态：草稿、进行中、已归档；
- 项目内的论文、方向、会话、研究任务和报告；
- 项目级系统提示和输出偏好。

项目必须能够长期保存。删除项目属于显式用户操作，默认只归档。

### 4.2 Session 会话

会话是项目内的一次连续对话。会话保存用户消息、助手消息、工具调用、工具结果、阶段进度和关联产物。

会话可以：

- 讨论一个研究方向；
- 让 Agent 解释某篇论文；
- 从论文库中比较方法；
- 启动或查看研究任务；
- 继续上一次中断的研究流程。

会话不能脱离项目使用。会话默认读取项目摘要、用户选定的论文和方向，避免每次把整个项目内容塞进模型上下文。

### 4.3 Paper 论文

论文是项目内可管理的研究资料。论文来自公开来源或用户手动导入。

论文状态：

```text
discovered → saved → reading → analyzed → cited
                         └──────→ rejected
```

论文至少保存来源 ID、标题、作者、年份、摘要、URL、来源、开放内容状态、用户标签、笔记和更新时间。论文在不同项目之间可以通过来源 ID 去重，但项目内的标签、笔记和分析结果独立保存。

### 4.4 Research Direction 研究方向

研究方向是用户或 Agent 从项目主题中整理出的子方向，例如：

```text
LLM Agent for Software Engineering
  ├─ 自动代码修复
  ├─ 测试生成与修复验证
  ├─ 软件仓库级 Agent
  ├─ 工具调用与环境交互
  └─ 评测基准与可靠性
```

方向必须包含名称、描述、关键问题、代表论文、待研究问题和来源会话。Agent 可以提出方向，但用户确认后才进入项目的正式方向树。

### 4.5 Research Run 研究任务

研究任务是一次可观察、可恢复的长流程。它可以由会话创建，也可以从项目页面直接创建。

研究任务保存：

- 输入问题和范围快照；
- 检索计划和使用的来源；
- 候选论文及纳入 / 排除原因；
- 用户确认记录；
- 每篇论文的证据提取状态；
- 综合结论、引用覆盖和警告；
- 当前阶段、进度、错误和检查点；
- 最终报告及其他产物。

### 4.6 Server Profile 服务器连接

服务器连接描述用户授权给某个项目使用的实验室服务器或集群入口。

服务器连接字段：

- 显示名称、主机别名、连接方式；
- 工作目录根路径；
- Python / Conda / 容器环境信息；
- GPU、CPU、内存、磁盘和调度器能力；
- 允许使用的项目目录和资源上限；
- 最近一次环境检查结果。

私钥、密码和 Token 不写入项目数据库。第一版通过用户本机 SSH Agent 或本地连接器使用已有凭据；后续通过实验室服务器上的 Runner Agent 主动连接控制服务。

### 4.7 Experiment Plan / Experiment Run 复现实验

`ExperimentPlan` 是 Agent 根据论文和代码仓库生成的结构化执行计划，必须在执行前通过规则校验和用户确认。

计划至少包含：任务类型、研究目标、代码仓库、commit、数据集版本、环境要求、命令、资源需求和预计输出。论文复现任务额外关联论文 ID、论文报告指标和比较规则；用户实验保存自己的假设、变量和目标指标。

`ExperimentRun` 是计划的一次执行实例，状态如下：

```text
planned → awaiting_approval → submitting → queued → running
  → collecting → completed / failed / cancelled / unknown
```

执行状态和比较结论分开保存。比较结论为 matched / partial / not_comparable / not_requested，界面综合展示环境匹配、实验完成、指标部分匹配、无法比较和执行失败。系统不能只根据进程退出码标记“复现成功”。

### 4.8 同一个研究 Agent 的实验任务模式

AutoResearch 可以处理用户自己的研究想法，不要求存在对应论文。用户可以在会话中提出：

```text
我想比较两个检索模型在自己的数据集上的 Recall@10 和延迟，数据在 lab-gpu-01 的项目目录中。
```

AutoResearch 在用户实验模式下把想法整理成实验规格，检查服务器和数据，生成执行计划，等待用户确认，提交实验并分析结果。它与论文复现模式共用 Runner、工作区、日志、指标和产物模型。

两者的区别：

| 任务模式 | 输入 | 主要输出 | 是否要求论文 |
| --- | --- | --- | --- |
| 论文复现 | 论文、代码仓库、论文指标 | 与论文结果的可比性报告 | 是 |
| 用户实验 | 用户想法、代码、数据集和参数 | 实验结果、对比表、图表和下一步建议 | 否 |

用户实验可以从论文复现任务派生，也可以独立创建 `ExperimentRun`。Agent 根据会话目标切换任务模式；计划校验和用户确认由应用规则执行。

## 5. 典型用户流程

### 流程 A：创建项目并整理研究方向

1. 用户创建项目“LLM Agent 在软件工程中的应用”。
2. 用户在会话中输入：“我想做代码缺陷修复方向的课程综述，不知道如何细分。”
3. Agent 读取项目描述，提出 4 至 6 个研究方向，每个方向附初步关键词和代表论文。
4. 用户勾选“自动代码修复”“测试生成”“工具调用”三个方向。
5. 系统把方向写入项目，生成对应的会话书签和待研究问题。

### 流程 B：整理一篇论文

1. 用户通过 DOI、arXiv ID 或论文 URL 导入论文。
2. 系统获取公开元数据和摘要，显示论文卡片。
3. 用户在论文详情页点击“分析论文”。
4. Agent 提取研究问题、方法、工具、数据集、指标、结果和局限。
5. 用户可以修改字段、添加笔记、打标签，并把论文加入某个研究方向。

### 流程 C：启动 AutoResearch

1. 用户在项目中点击“新建研究任务”。
2. 输入研究问题：“LLM Agent 在自动化代码缺陷修复中采用了哪些工具调用方式，常用数据集和评测指标是什么？”
3. 系统显示研究范围、来源、论文数量上限和预计阶段，用户确认后开始。
4. Agent 生成检索式，系统并行查询公开来源并去重。
5. 系统展示候选论文表，包含相关性理由和排除风险。
6. 用户选择纳入论文后，任务继续抓取摘要或开放全文并提取证据。
7. 系统生成证据矩阵、比较表和带引用的研究报告。
8. 用户回到会话追问：“哪些论文真正使用了测试执行工具？”系统只基于项目证据回答。

### 流程 D：恢复中断任务

1. 研究任务在人工确认或网络失败处暂停。
2. 项目页面显示任务状态、待处理问题和 `interrupt_id`。
3. 用户在任务页面确认或修改选择。
4. 系统从最近检查点恢复，不重复已完成的检索、论文导入和证据抽取。

### 流程 E：复现论文实验

1. 用户在论文详情页点击“尝试复现”。
2. Agent 读取论文中的代码仓库、commit、数据集、环境和运行命令；缺失信息进入待确认项。
3. 系统生成 `ExperimentPlan`，列出服务器、工作目录、资源需求、命令、预计时间和输出文件。
4. 系统先执行只读环境检查，确认 Python、GPU、磁盘、依赖和调度器状态。
5. 用户确认执行计划后，系统在项目隔离目录创建工作区并提交任务。
6. 前端实时显示排队、运行、日志、GPU / CPU 使用情况和错误。
7. 任务完成后收集指标、图表、日志、代码 commit、环境指纹和运行参数。
8. 系统将实验结果与论文报告值进行比较，生成“成功、部分匹配、无法比较或失败”的解释。
9. 复现结果回写论文卡片、研究方向和会话，并可纳入最终报告。

### 流程 F：运行用户自己的实验

1. 用户在项目会话中描述实验想法，指定代码仓库、数据位置、变量和目标指标。
2. AutoResearch 读取项目代码上下文和已登记的服务器能力，提出实验规格。
3. 用户确认数据目录、参数范围、资源预算和输出指标。
4. 系统生成执行计划，先做只读环境检查，再等待提交确认。
5. 用户确认后，系统在项目工作区提交一次或多次实验任务。
6. 前端实时展示任务状态、日志、指标和产物。
7. Agent 汇总结果，指出异常、失败实验和下一步建议，并把结果保存到项目。

## 8. 数据对象与关系

```text
User
 └─ Project
     ├─ Session ── Message ── ToolCall / Citation
     ├─ Paper ── PaperNote
     ├─ ResearchDirection ── DirectionPaper
     ├─ ResearchRun ── RunStage / Candidate / Evidence / Claim
     ├─ ServerProfile ── EnvironmentSnapshot
     ├─ ExperimentRun ── ExperimentPlan / Job / Metric / Artifact
     └─ Artifact ── Report / Table / Export
```

`ResearchRun` 是长流程对象，`Session` 是交互对象。两者可以互相链接，但不能混成一个表：会话可以持续多年，研究任务有明确的输入快照、状态和输出。

`ExperimentRun` 与论文和研究任务关联，但有独立的远程任务状态。服务器断开、任务取消和结果比较失败不能改变论文元数据；只能在实验记录中保存状态和原因。

## 9. Agent 工具边界

Agent 只能调用受控工具：

- `search_papers`：按照项目来源配置搜索，不接受任意 URL；
- `save_paper`：把论文加入当前项目，去重后返回项目论文 ID；
- `analyze_paper`：对项目内论文提取结构化证据；
- `propose_directions`：基于项目问题和论文库提出方向候选；
- `create_research_run`：创建研究任务并保存输入快照；
- `search_project_evidence`：只检索当前项目的论文和证据；
- `save_note`：保存用户明确要求的项目笔记；
- `inspect_server`：读取已登记服务器的环境和资源信息；
- `prepare_workspace`：在允许的项目根目录创建隔离工作区；
- `submit_experiment`：提交已经确认的 ExperimentPlan；
- `get_experiment_status` / `tail_experiment_logs`：查看任务状态和日志；
- `collect_experiment_artifacts`：收集允许的指标、图表、日志和环境指纹；
- `cancel_experiment`：取消当前项目拥有的实验任务；
- `generate_report`：只能在研究任务通过证据检查后生成报告。

网络来源白名单、项目 ID、论文归属、数量上限、引用校验、服务器目录、命令策略和报告写入由 Go 服务负责。模型不能自行访问任意网站、改变项目边界、执行无限制 Shell 或伪造论文来源。

远程执行必须经过 Runner 抽象层，但 Runner 不一定是服务器上的常驻程序。MVP 使用用户本机连接器通过 SSH Agent 连接实验室服务器，体验类似 VSCode Remote；产品化版本再使用服务器侧 Runner Agent。两种模式都不能把私钥交给模型。

浏览器本身不能安全、稳定地直接连接 SSH。VSCode 类体验需要一个本机连接器：它调用用户已有的 SSH Agent，通过经过认证的通道领取绑定计划哈希的授权任务，连接服务器并回传状态。服务器侧 Runner 适合控制服务需要在用户电脑离线时继续运行、实验室服务器位于内网、需要 Slurm 长任务或需要多用户统一审计的场景。

## 10. AutoResearch 的实验任务规则

### 10.1 任务类型

任务类型有两个：

- `paper_reproduction`：以论文中的代码、环境、数据和指标为基准，目标是判断结果是否可比；
- `user_experiment`：以用户提出的假设、代码和数据为输入，目标是运行实验并产生可分析结果。

以上是两类实验任务；文献调研使用 `literature_research` 类型的 ResearchRun。三类任务均由统一的 AutoResearch 会话入口管理。

两者都使用 `ExperimentPlan` 和 `ExperimentRun`，但报告模板不同。论文复现报告包含论文值与本次值的比较；用户实验报告包含变量、实验矩阵、结果和下一步建议。

### 10.2 复现计划

Agent 生成的 `ExperimentPlan` 至少包含：

```text
paper_id
repository_url
commit
dataset_version
environment_requirements
commands
resource_request
expected_metrics
output_paths
comparison_tolerance
```

计划必须标记缺失信息。论文没有明确给出代码 commit、数据版本或指标定义时，系统显示“无法完全复现”的风险，不能由模型自行补齐为确定事实。

### 10.3 服务器访问流程

```text
用户授权的 ServerProfile
  → 只读 preflight
  → 生成并展示 ExperimentPlan
  → 用户确认
  → 选择 Runner 模式
  → 隔离工作区
  → 拉取指定代码与数据
  → 提交本地进程 / Slurm 任务
  → 轮询状态和日志
  → 收集产物
  → 指标比较与报告
```

允许自动执行的操作只包括已注册服务器上的只读检查和已确认计划中的命令。以下操作默认拒绝：`sudo`、任意系统目录写入、读取凭据、删除项目根目录、访问其他项目目录、终止其他用户任务和绕过调度器。

### 10.4 Runner 连接模式

| 模式 | 连接路径 | 是否需要服务器安装 Runner | 适用场景 |
| --- | --- | --- | --- |
| 本机连接器 | Web 服务 → 本机 Connector → SSH / Slurm | 否 | 学生单机使用、VSCode Remote 风格体验 |
| 控制服务直连 SSH | Go 服务 → SSH → 服务器 | 否 | 内网打通、单用户或可信部署 |
| 服务器 Runner Agent | Web 服务 → Runner Agent → 本地进程 / SSH / Slurm | 是 | 多用户、长任务、服务器内网、统一审计 |

三种模式都实现同一个 `Runner` 接口。第一版优先实现本机连接器；接口和 `ExperimentRun` 状态不绑定具体连接模式，后续可以无缝增加服务器 Runner。

本机连接器需要处理：连接注册、任务授权、心跳、断线重连、日志回传和本机 SSH Agent 调用。它不应把私钥或完整 Shell 暴露给网页。

### 10.5 结果判定

系统依据代码、数据、环境和指标定义进行规则比较：

| 结果 | 判定 |
| --- | --- |
| `matched` | 环境和数据条件满足，实验完成，关键指标在设定容差内 |
| `partial` | 实验完成，但环境、数据或部分指标与论文不一致 |
| `not_comparable` | 缺少指标定义、数据版本或关键实验条件 |
| `not_requested` | 用户实验未指定论文或参考基准，不进行论文复现判定 |

执行失败或取消分别记录为 failed / cancelled。模型可以解释差异，比较结论依据已确认计划的指标、数据和容差计算；不能由模型事后放宽标准。

### 10.6 远程任务的可靠性

- 远程任务提交成功后保存远程 `job_id`，控制服务重启后可以重新查询；
- 日志读取是增量的，不能把整个日志反复写入会话历史；
- 任务取消和服务器断开都保存原因；
- 实验产物使用大小上限和允许路径白名单；
- 同一项目、同一论文、同一 commit 和同一参数可以生成幂等运行键，避免重复提交；
- 实验状态事件和论文证据事件分开保存，实验失败不能覆盖原论文信息。

## 12. 非目标

MVP 不包含：

- 自动修改代码、替代代码 Agent 或让模型直接获得无限制 Shell；
- 付费论文下载、绕过登录或抓取任意网站；
- 多人实时协作和复杂权限体系；
- 论文质量的绝对判断和系统综述完整性保证；
- 一次任务分析数百或数千篇论文；
- 复杂 PDF 版面恢复、公式识别和图片表格理解；
- 训练自有大模型或 GPU 推理调度。实验室服务器上的受控实验提交属于产品能力，但不负责调度器本身的资源管理。

## 14. 验收标准

完成 MVP 后，用户应能完成下面的完整演示：

1. 创建项目“LLM Agent 在软件工程中的应用”；
2. 新建会话，让 Agent 提出研究方向；
3. 确认一个方向并导入至少 5 篇论文；
4. 在论文库中查看摘要、标签、笔记和结构化证据；
5. 创建 AutoResearch 任务，查看检索计划和候选论文；
6. 人工排除一篇论文并确认其余论文；
7. 观察任务阶段和模型工具调用；
8. 生成带引用的证据矩阵和 Markdown 报告；
9. 中断任务后刷新页面，提交恢复答案并继续；
10. 从报告引用跳回论文和证据片段。

11. 在项目中登记一台实验室服务器并完成只读环境检查；
12. 从论文详情页生成复现计划，看到仓库、commit、命令和资源需求；
13. 未确认计划时不能提交远程任务，确认后可以看到排队、运行和日志事件；
14. 实验结束后查看指标、图表、环境指纹和论文结果比较；
15. 服务器断开或服务重启后，可以凭远程 job ID 恢复任务状态；
16. 危险命令、越权目录和未登记服务器访问被拒绝。

技术验收还包括：项目数据隔离、引用不可伪造、网络失败可恢复、模型调用有上限、前端能区分运行中 / 暂停 / 失败 / 完成状态、远程实验状态不会因前端刷新而丢失。

## 15. 目标边界

AutoResearch 的第一版目标是成为一个**有项目工作区的计算机专业研究 Agent 产品**。用户通过统一的会话入口提出目标，Agent 结合项目上下文，在论文发现、方向整理、证据分析、服务器实验和报告更新之间选择下一步行动。goHarness 提供执行、工具调用、流式交互和恢复能力，领域规则保证研究证据与实验记录可核验。
