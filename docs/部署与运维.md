# 部署与运维

面向把 goHarness 嵌进后端服务的运维侧：Redis 配置、多副本、旋钮关系、
停机排空、容量估算。指标清单与告警建议见[运维指标与告警](运维指标与告警.md)。

## Redis 配置

`state.Store` 的 Redis 实现是 `extensions/state/redis`，接收
`redis.UniversalClient`——单机、哨兵、集群同一入口：

```go
// 单机
client := redis.NewClient(&redis.Options{Addr: "127.0.0.1:6379"})

// 哨兵
client := redis.NewFailoverClient(&redis.FailoverOptions{
    MasterName: "mymaster", SentinelAddrs: []string{"127.0.0.1:26379"},
})

// 集群
client := redis.NewClusterClient(&redis.ClusterOptions{
    Addrs: []string{"c1:6379", "c2:6379", "c3:6379"},
})

store, err := redisstore.New(redisstore.RedisStoreConfig{
    Client: client, Prefix: "myapp",
    TTL: 24 * time.Hour, MaxHistory: 200, LogCacheSize: 4096,
})
```

- **集群**：`state/redis` 的 key 带 `{id}` 哈希标签，同一会话的所有 key
  落同槽，Lua 脚本可安全执行。检索文档（`retrieval/redisstore`）
  **不使用**哈希标签，避免大租户集中在一个槽。
- **Redis Search**：向量检索需要带 Search 模块的发行版（Redis Stack /
  Redis 8）。首版验证范围是**单机与主从**；集群模式下索引与分片行为
  随发行版不同，按所用发行版核对。客户端必须用 RESP2
  （`Options{Protocol: 2}`），go-redis 的 `FT.*` 在 RESP3 下有解析缺陷。
- **持久化模式**：默认异步持久化（保存开销摊到后台）；审批类场景
  （挂起等人工输入）用 `agent.WithSyncPersist` 同步持久化，保证挂起
  点先落盘再返回。

## 多副本

服务实例无状态：会话归属不绑定实例，任何副本都能跑或恢复任何会话。

- **同会话串行化**不在框架内，由应用层保证（粘性路由、分布式锁或
  队列分区键，见[对接说明](integration.md#会话串行化)）。串行化失效
  时的兜底是检查点 CAS：两个实例同时保存同一会话，后到的提交被
  `state.ErrConflict` 拒绝，不会出现两份结果。
- **跨实例恢复**：实例 A 中途崩溃或排空，实例 B 用同一存储
  `agent.Resume` 继续，已完成的工具调用不重复执行。
- **恢复前校验定义版本**：`agent.WithDefinitionVersion` 把版本写进
  执行记录，副本间镜像不一致时挂起运行拒绝在不匹配的版本上恢复。

## 旋钮关系表

| 旋钮 | 位置 | 默认 | 与谁相关 |
| --- | --- | --- | --- |
| `Bulkhead.MaxConcurrent` | `limits.NewBulkhead` | 不限 | 单进程在途运行上限；打满 LLM 网关或下游前的主闸 |
| `Bulkhead.MaxQueue`/`QueueTimeout` | 同上 | 不排队/随 ctx | 过载时的短期削峰；排队本身是资源占用，别给太大 |
| `Bulkhead.PerTenant` | 同上 | 不限 | 防单租户挤占；TenantKey 默认读租户作用域 |
| `tool.RuntimeConfig.MaxWorkers` | `agent.WithToolWorkers` | 128（硬顶 4096） | 工具并发执行上限；等不到名额会随 ctx 取消 |
| `httpclient.Pool` | `httpclient.NewPool` | 每主机空闲 20、总连接不限 | LLM/嵌入/重排/MCP 共用；调大时先确认对端承受力 |
| Redis `PoolSize`/`PoolTimeout` | `redis.Options` | go-redis 默认 | 检查点读写并发；保存延迟高时先查事件循环占用 |
| `stream.Config.Buffer`/`SendTimeout` | `stream.Config` | 64 / 无限 | SSE 类慢消费者背压；SendTimeout 到时终止运行并回落协程 |
| `RedisStore.TTL`/`MaxHistory` | `RedisStoreConfig` | 不过期/不裁剪 | 会话体积上限：约 56B/条消息 + 2KB 固定/会话 |
| `RedisStore.LogCacheSize` | 同上 | 默认限 | 日志视图 LRU 上限，防爆内存 |

## 停机排空

参考实现见 `extensions/examples/server`：收到 SIGTERM 后

1. `bulk.Drain()` 拒绝新运行（`ErrDraining`→503）；
2. 在途运行收到取消信号，**中断进度已检查点落盘**，打印
   `draining: interrupting in-flight runs (progress is checkpointed)`；
3. 进程干净退出；另一实例对同一会话 `resume` 即继续。

就绪探针在排空期间应失败：`GET /readyz` 返回非 200，让负载均衡摘流。

## 容量估算（实测口径）

真实 Redis 7.2（单线程）、同步持久化、并发 8 / 64 会话（G4 门槛数据）：

| 历史长度 | 每次保存服务端耗时 | 粗估单实例吞吐（按每次运行约 5 次保存） |
| ---: | ---: | ---: |
| 200 条 | 0.71ms | ~280 运行/秒 |
| 500 条 | 1.58ms | ~126 运行/秒 |
| 1000 条 | 3.02ms | ~66 运行/秒 |

保存成本随消息历史**线性增长**（约 3µs/条），长会话的主要容量杠杆是
`MaxHistory` 裁剪。假模型压测基线：32 会话/并发 8/内存/异步约
211 req/s、p50 37ms。压测工具 `extensions/examples/loadtest` 可调
会话数、并发数、工具数与历史长度，用自己的环境重测后再估容量。
