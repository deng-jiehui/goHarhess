# 结构化输出实施方案（4.4）

- 日期：2026-10-10
- 状态：主体已落地，2026-10-11 审核未通过；四项功能问题和性能验收待修正，见[独立审核记录](../../.bench/results/review-4-4/verification.md)
- 目标：让模型输出能够经过 Schema 校验，转换成明确的 Go 结构体，并作为普通节点接入现有 Graph
- 基础：Go 1.24、现有 Runnable/Option/Graph、`google/jsonschema-go v0.4.3`；本次不增加外部依赖

## 一、问题与本次范围

当前 `llm.WithGenerateConfig` 已能把 `response_format` 透传到 OpenAI-compatible 请求体，但框架没有统一的类型化配置，也没有对返回 JSON 做 Schema 校验和类型化解码。仅用 `json.Unmarshal` 不足以确认结果正确：例如遗漏必填的布尔字段时，解码仍然成功，只会留下 `false` 零值。

本次实现三项能力：类型化的模型输出格式、按目标 Go 类型生成并编译 Schema、可作为 Runnable 使用的校验解码组件。第一版只支持原生 JSON Schema 输出；工具调用形式的结构化输出、提示词降级和自动纠错重生成不在本次范围内。校验失败直接返回明确错误。

输出格式属于 `llm.Options`，通过现有 `runnable.Option` 下发。结构化结果属于业务输出，由调用方返回或写入自己的 State 字段。Agent 继续作为消息配方，解码组件可以挂在模型或 Agent 后面；不新增内部 `State.StructuredResponse`，不改图调度器。

## 三、公开接口

### 3.1 模型输出格式

```go
type ResponseFormat struct {
    Name        string
    Description string
    Schema      json.RawMessage
    Strict      bool
}

func (f ResponseFormat) Clone() ResponseFormat
func WithResponseFormat(format *ResponseFormat) runnable.Option
```

第一版的 `ResponseFormat` 专指 JSON Schema 输出格式，Provider 负责映射成自己的线路字段。`Schema` 保存 JSON 字节，不保存 `Resolved` 校验器、函数或 Go 类型对象。

在 `llm.Options` 增加 `ResponseFormat *ResponseFormat`。未设置时保留普通消息输出；`WithResponseFormat(nil)` 清除类型化格式。Option 创建时和应用时都复制 Schema 字节，`Options.Clone`、冻结、重试转发和 Provider 使用都不得暴露可变共享数据。

类型化格式和构造配置或单次 `GenerateConfig` 中的 `response_format` 同时存在时，返回配置冲突错误，不依靠传入顺序决定。未设置类型化格式时，原有扩展参数通道继续可用；清除类型化格式不代表清除用户另外配置的原始扩展参数。

### 3.2 结构化输出组件

```go
type StructuredOutput[T any] struct {
    // 实现字段为私有：冻结后的格式、编译好的校验器和 Runnable 适配器。
}

func NewStructuredOutput[T any](options ...StructuredOutputOption) (*StructuredOutput[T], error)
func WithOutputName(name string) StructuredOutputOption
func WithOutputDescription(description string) StructuredOutputOption

func (o *StructuredOutput[T]) Format() *ResponseFormat
func (o *StructuredOutput[T]) Decode(messages []schema.Message) (T, error)
```

`StructuredOutputOption` 是构造该组件的选项，不是模型单次运行的 Option。默认名称由命名类型推导并规范化，匿名类型用 `structured_output`；显式名称必须符合目标线路要求，错误在构造期返回。

其类型固定为包内构造函数选项 `type StructuredOutputOption func(*structuredOutputConfig)`，`structuredOutputConfig` 是私有配置，只保存名称和描述。名称限定为字母、数字、下划线或连字符，长度 1 至 64；规范化后的空名称用默认值，自动名称超过长度时截断，显式不合法名称返回错误。

`Format()` 每次返回独立副本，默认 `Strict=true`。`Decode` 仅解码完整消息，不调用模型。构造完成后组件只读，可以被多个请求并发复用。

组件实现 `Runnable[[]schema.Message, T]`：

```go
func (o *StructuredOutput[T]) Invoke(ctx context.Context, messages []schema.Message, options ...runnable.Option) (T, error)
func (o *StructuredOutput[T]) Stream(ctx context.Context, messages []schema.Message, options ...runnable.Option) (*runnable.StreamReader[T], error)
func (o *StructuredOutput[T]) Collect(ctx context.Context, messages *runnable.StreamReader[[]schema.Message], options ...runnable.Option) (T, error)
func (o *StructuredOutput[T]) Transform(ctx context.Context, messages *runnable.StreamReader[[]schema.Message], options ...runnable.Option) (*runnable.StreamReader[T], error)
```

`Invoke` 调用同一条校验解码路径；`Stream` 成功时交付一次 T，失败时交付错误。输入 Reader 的一次数据是完整消息列表，不是 JSON 字符串分片；Collect/Transform 要先等待输入正常结束，再选择最终消息并解码，不能在输入后续报错前交付成功。关闭输出 Reader 时取消内部工作并关闭上游 Reader。适配可复用 `runnable.Adapt`，但必须核对上述终止语义。

组件实现 `OptionTypes() []reflect.Type` 并返回空集合，声明不接收模型配置类型；图的广播按声明类型匹配，模型 Option 不会进入 decode。Invoke 等方法通过现有 `runnable.FlattenOptions` 校验输入，非空配置或定向选项返回明确错误。不要另外引入解析器运行时配置通道。

## 四、Schema 规则

1. 第一版 T 必须是结构体，顶层指针、标量、切片和 map 在构造时拒绝；这样与原生严格模式要求的顶层对象一致。字段按照 `json` 标签命名，描述沿用现有 `jsonschema` 标签用法。
2. 推导之后生成一份用于发送和本地校验的同一 Schema。对象禁止额外字段，属性均进入 required。需要表达可空字段时用指针字段，并在对应 Schema 中明确允许 null；不要把“字段可以为 null”和“字段可以缺失”混为一谈。
3. 带 `omitempty` 或 `omitzero` 的字段要求是指针字段：规范化后仍要求键存在，空值用 null。非指针字段带这些标签时，构造失败并提示改为指针或移除省略标签，避免悄悄改变其可选语义。数组和其他可空值的 null 规则也要与 Go 类型对应。
4. 可以保留本地 `$defs`/`$ref`，但不解析外部引用。对原生严格模式不支持的关键字或推导不准确的自定义编解码类型，构造时明确报错，不静默删掉约束或降级。嵌套对象同样执行严格模式规则。
5. 用 `jsonschema.Resolve` 在构造期编译，运行期复用校验器。Provider 格式配置和解码组件的 Schema 都从已冻结的规范化结果复制，不能出现模型约束和本地校验规则不一致。

生成过程涉及指针、嵌套类型和本地引用时，必须用对应的 Go 类型信息完成规范化，不能只看到 `omitempty` 就给所有字段加 null。第一版支持范围以覆盖测试为准，无法准确表达的类型在构造时拒绝并给出字段位置。

## 五、结果选择与错误行为

解码流程固定为：选择最后一条 assistant 消息 → 检查是否为完整最终回答 → 提取 Text Block → 解析唯一 JSON 值 → Schema 校验 → 解码进 T。

- 最后一条 assistant 仍带 FunctionToolCall、只有 reasoning、没有文本，或不存在 assistant 消息时，返回结构化输出错误；不能退回解析更早的回答。
- 拒绝回答、`finish_reason=length` 或 `content_filter` 等明确不完整状态返回错误；没有提供 ResponseMeta 的自定义模型仍可按完整文本校验。
- 不自动去掉 Markdown 代码围栏，不从自然语言中猜测 JSON 片段。只接受一个 JSON 对象及其前后的空白，尾部第二个 JSON 值或额外文本均拒绝。
- 第一次解析使用 `UseNumber` 保留数值精度，校验原始 JSON 值，再从同一原始字节严格解码进 T；需要拒绝缺少必填字段、未知字段、类型错误和数值溢出。`0`、`false`、空字符串等合法值不因等于 Go 零值被拒绝。
- 失败返回 T 的零值和错误，禁止交付已经部分填充的结构体。提供 `ErrInvalidStructuredOutput` 与包装错误，能够用 errors.Is/As 分类并保留底层错误链；错误字符串默认不拼接完整模型输出。

OpenAI-compatible 的拒绝信息目前没有被完整接入。增加对 `refusal` 的读取，并规范化保存到 `Message.Extra["llm.refusal"]`，让解码组件能识别；Invoke 和 Stream 使用相同规则。结束原因继续使用已有 `ResponseMeta.FinishReason`。不要为了这项功能增加一种公开 ContentBlock 类型。

## 六、Provider、Option 与缓存

OpenAI-compatible 请求在设置类型化格式时发送：

```json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "decision",
      "description": "审批结论",
      "strict": true,
      "schema": {}
    }
  }
}
```

这里的空对象只是线路形状示意，实际必须是第三、四节生成并校验过的 Schema。配置错误在 HTTP 请求之前拒绝。

能力声明需要明确：在 `llm.Config` 增加可选的 `Capabilities *Capabilities`，工厂将显式值传给 Provider；`OpenAICompatibleConfig.Capabilities` 继续使用原有入口，非零配置按现有规则覆盖默认。OpenAI-compatible 未显式声明能力时保留 Streaming/ToolCalls 等既有默认，但 JSONSchema 默认改为 false。顶层 `llm.Config.Capabilities` 的 nil 表示采用默认，非 nil 表示使用其完整内容（包括显式全 false），不能再用结构体零值判缺省。类型化格式且 `Capabilities().JSONSchema=false` 时返回明确的不支持错误。这个声明由使用者按实际端点填写，不根据模型名称猜测，也不保证服务一定接受：HTTP 拒绝仍按模型调用错误返回，不静默改成 JSON mode 或提示词模式。

工厂实现应使用一个能区分“未声明”与“显式声明”的私有构造路径，避免显式全 false 被下层重新解释为默认。直接调用现有 `NewOpenAICompatibleModel` 且传入零值 Capabilities 的缺省语义保留，默认值只按本节关闭 JSONSchema。

这一默认值变化必须写入模型文档和测试。普通调用没有设置格式时不增加 Schema 编译、解析或分配成本；原始 `GenerateConfig` 的兼容传递也不附加新的能力检查。

`PrepareOptions`、Agent 模型选项分发、限流与重试包装器沿用现有路径。新格式要进入冻结后的有效模型配置，不能在重试时重复运行设置函数。Schema 编译器属于解码组件，不能放进 Option 或检查点。缓存已有配置指纹机制，本次要证明名称、Schema 和 Strict 的变化都会改变缓存身份；命中缓存后的响应仍由解码组件正常校验。

## 七、使用方式

### 单次回答或 Basic Agent

```go
type Decision struct {
    Approved bool   `json:"approved"`
    Reason   string `json:"reason"`
}

output, err := llm.NewStructuredOutput[Decision](llm.WithOutputName("decision"))
if err != nil {
    return err
}
messages, err := assistant.Invoke(ctx, input,
    llm.WithResponseFormat(output.Format()),
)
if err != nil {
    return err
}
decision, err := output.Decode(messages)
```

这里 assistant 使用明确声明支持 JSONSchema 的模型。直接调用模型时同样使用 `WithResponseFormat`，然后把 `response.Messages` 交给解码组件。

### 挂成普通图节点

```go
g := graph.NewGraph[[]schema.Message, Decision]("decision")
if err := g.AddNode("answer", assistant); err != nil {
    return err
}
if err := g.AddNode("decode", output); err != nil {
    return err
}
for _, edge := range [][2]string{
    {graph.Start, "answer"}, {"answer", "decode"}, {"decode", graph.End},
} {
    if err := g.AddEdge(edge[0], edge[1]); err != nil {
        return err
    }
}
compiled, err := g.Compile()
if err != nil {
    return err
}
decision, err := compiled.Invoke(ctx, input,
    runnable.ForNode("answer", llm.WithResponseFormat(output.Format())),
)
```

这里使用现有 `runnable.ForNode(nodeID string, options ...Option)`，只把格式传给 answer 内的模型，不给 decode 节点增加模型配置。

上面的简化图没有 State，不启用检查点。需要持久化时，由调用方配置自己的 State factory，定义保存模型消息和 Decision 的字段，并给 decode 安装从 State 读取消息的 PreHandler、仅在成功时写回 Decision 的 PostHandler；`WithCheckpoint` 或编译期 `Checkpointer` 沿用现有接口。进度和最终结果由现有 Graph 保存，解码节点恢复不调用模型。

### 带业务工具的 Agent

推荐显式组成 `业务 Agent → 最终整理模型 → decode`。格式 Option 只定向给最终整理模型：该节点读取原任务和已完成的结论，只生成结构化答案，`Request.Functions` 为空。业务工具和审批已经由前面的 Agent 完成；格式化失败不会重新调用这些工具。

这条路径多一次模型调用，要在示例和文档中说明，并通过现有 observe 记录其用量。首版不在 Agent 配方内部偷偷追加调用、不新增自动重试。业务需要纠错时，可以自行声明有次数限制的整理节点循环，循环只重新生成格式化答案。

首版文档必须有以下接线的完整例子，而不是只写一句“再加一个节点”：业务 State 保存原任务、Agent 全部输出、整理模型消息和最终 Decision；Agent.Post 保存消息；整理模型.Pre 从 State 组装 Request，明确不给它 Functions；整理模型.Post 保存完整消息；decode.Pre 提取这些消息，decode.Post 成功后写入 State.Decision；finish 从 State 输出 Decision。整理节点本身用 `llm.NewChatModelNode`，格式 Option 定向到该节点。上述节点各自有明确的 State 输入来源，恢复落在 decode 时可以沿用已保存的模型输出。

### 第二步：Schema 推导、校验与类型化解码

## 九、验收要点

实现完成后，使用者只需要定义目标结构体、构造输出组件并接入调用或图节点，不需要自行实现 Schema 推导、必填校验、JSON 截取或泛型解析器。最终返回的 T 必须通过同一份 Schema 的本地校验；不能以 JSON 解码成功代替完整性检查。

旧的 `agent.WithResponseFormat[T]()` 与内部 `State.StructuredResponse` 方向由本方案取代。工具输出模式、自动纠错和其他模型参数仍是后续工作，不能混入本次验收的“已完成”。

参考：[Eino MessageParser](https://www.cloudwego.io/docs/eino/core_modules/components/lambda_guide)、[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。两者用于核对接口分工和线路约束，框架内的职责以本方案为准。
