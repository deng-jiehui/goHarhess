# 通用数据模型实施方案

- 日期：2026-10-11
- 状态：已实现 · 复核待修；2026-10-11 独立复核发现字节切片规则和文档示例两项问题，见[本轮复核](../../.bench/results/review-datamodel/verification.md)；改造前后基准与成对复测证据见 `.bench/results/datamodel/`
- 目标：把外部 JSON 校验后转换成明确的 Go 类型，让结构化输出与工具参数复用已有能力
- 架构：新增 `pkg/datamodel.Model[T]` 作为用户入口；公共 Schema 编译与 JSON 解码放在 `internal/jsonvalidation`，供数据模型、LLM 和工具使用
- 技术基础：Go 1.24、现有 `github.com/google/jsonschema-go v0.4.3`；保持当前依赖版本

> 按下面四个阶段分别实现、验证和提交。每个阶段通过后再进入下一阶段。若由编码助手执行，使用 `executing-plans` 按阶段推进；本计划由开发者直接实施，不要求委派子任务。

## 一、为什么做这次改造

现在已经有两条类似的路径：`llm.StructuredOutput[T]` 从类型生成 Schema，校验模型返回的 JSON，再解码成 T；工具在注册时编译参数 Schema，在执行前校验参数，类型化工具另外把 JSON 解码成参数结构体。

这些能力已经能工作，但普通业务输入不能直接复用结构化输出中的通用校验。此次改造把“数据是什么样、如何校验和解码”独立出来，模型消息处理和工具执行继续由各自组件负责。

数据模型不是 ChatModel。它不调用大模型，也不管理任务、会话或检查点。用户定义一个 Go 类型，构造一个可重复使用的数据模型，随后把 JSON 交给它，得到 T 或明确的错误。

它主要减少外部数据入口中的类型错误、必填字段遗漏和约束错误。`[T any]` 在构造时已有具体的 T，能够据此建立规则；字段 `Data any` 仍然缺少具体约束，需要另行配置 Schema。Metadata 的复制、并发修改以及图内部的类型断言，继续属于各自模块的职责。

## 二、全局约束与职责

1. 复用 `jsonschema-go v0.4.3`，不新增第二套校验库，不另造一套字段约束语言。
2. 普通数据模型遵循 Go 类型和 `json` 标签的语义。模型服务要求的严格输出格式由 `llm` 处理。
3. 构造时生成并编译规则，运行时复用。模型格式和本地解码必须来自同一份最终 Schema。
4. Go 类型、校验器和函数不进入 `llm.Options`、缓存配置或检查点；这些位置仍然只保存现有的可复制数据。
5. 工具仍在注册时冻结参数表，执行时先于中间件校验。保持已有错误分类、中间件顺序和重试行为。
6. 测试优先覆盖常见业务输入和已有行为。低频的特殊类型和复杂手写 Schema 按支持范围处理，不借本轮扩展成完整的 Pydantic。
7. 不修改 Graph、Agent State、调度器和 Metadata 的实现。

| 位置 | 职责 | 依赖边界 |
| --- | --- | --- |
| `internal/jsonvalidation` | Schema 推导、冻结与编译；原始 JSON 解析和严格类型化解码 | 标准库和 `jsonschema-go` |
| `pkg/datamodel` | 绑定 T、配置约束和业务检查，对外提供校验解码入口 | `internal/jsonvalidation`；Schema 配置使用 `jsonschema-go` 类型 |
| `pkg/llm` | 选择最终消息、处理拒绝或截断、生成模型服务需要的严格格式、适配 Runnable | `pkg/datamodel` 和既有基础组件 |
| `pkg/tool` | 注册快照、参数校验时机、错误转换、工具执行 | 复用 `internal/jsonvalidation`，保留当前公开构造入口 |

内部公共包是实现细节。普通用户只需要理解 `datamodel.Model[T]`。工具既支持类型化参数，也支持手写参数表，因此工具 Runtime 使用内部的非泛型编译结果，不强制转换成 `Model[T]`。

## 三、公开接口

### 3.1 数据模型

在 `pkg/datamodel/model.go`、`options.go` 和 `errors.go` 中定义：

```go
type Model[T any] struct {
    schema     *jsonvalidation.Compiled
    validators []func(T) error
}

type config[T any] struct {
    schemaEdits []func(*jsonschema.Schema) error
    validators  []func(T) error
}

type Option[T any] func(*config[T])

func New[T any](options ...Option[T]) (*Model[T], error)
func WithSchema[T any](edit func(*jsonschema.Schema) error) Option[T]
func WithValidator[T any](check func(T) error) Option[T]

func (m *Model[T]) DecodeJSON(data []byte) (T, error)
func (m *Model[T]) JSONSchema() json.RawMessage
func (m *Model[T]) WithSchema(edit func(*jsonschema.Schema) error) (*Model[T], error)

var ErrInvalidData = errors.New("invalid data")
```

这里的 `Option[T]` 是构造数据模型的选项，与 `runnable.Option` 无关。相较于讨论时的接口草图，选项增加 T，是为了让业务校验函数一直保持 `func(T) error`，避免把函数存进 `any` 后再做类型断言。

包级 `WithSchema[T]` 在构造时调整推导结果；模型方法 `WithSchema` 生成一份调整规则后的新模型。后者主要供 LLM 适配使用，原模型不会被修改，已有业务检查保留。

`JSONSchema()` 返回独立字节副本。零值或 nil 模型不具备解码能力，`DecodeJSON` 返回错误；`JSONSchema` 返回 nil；模型方法 `WithSchema` 返回错误。调用方通过 `New` 获取可用实例。

业务校验在类型化解码成功后执行。注册多个检查时按顺序执行，遇到第一个错误就停止。检查函数只负责判断，不用它修改或补全数据。检查函数的闭包由调用者负责并发安全；框架只保证自身保存的 Schema 和检查函数列表不会被运行过程修改。

### 3.2 结构化输出接线

现有 `NewStructuredOutput[T]`、`Format`、`Decode` 和四种 Runnable 方法继续使用。新增一个入口，让已经配置好的数据模型可以用于模型输出：

```go
func NewStructuredOutputFromModel[T any](
    model *datamodel.Model[T],
    options ...StructuredOutputOption,
) (*StructuredOutput[T], error)
```

该入口从原数据模型生成严格格式的副本，把副本用于 Format 和 Decode，保留其中的业务检查。原数据模型仍可用于普通业务 JSON。

## 四、数据规则与执行流程

### 4.1 普通模型的规则

采用依赖已有的类型推导：标量、结构体、指针、数组、切片和字符串键 map 按库的规则处理。不打开 `IgnoreInvalidTypes`，库不支持的类型在构造时返回错误。

结构体字段按 `json` 标签命名；带 `omitempty` 或 `omitzero` 的字段可以缺失，其余字段进入 required。可空与可缺失分别由字段类型和标签表达。结构体默认禁止额外字段，字符串键 map 按值类型约束动态键的内容。

`jsonschema` 标签在当前依赖中只提供描述，不把 `jsonschema:"minimum=0"` 或 `validate:"required"` 当成约束。数值范围、字符串长度和枚举等要求通过 `WithSchema` 配置现有的 `jsonschema.Schema`。

Schema 编辑回调用于补充或调整约束，字段名和 JSON 类型应与 T 对应。第一版不实现任意手写 Schema 与 Go 类型之间的完整兼容性证明；最后的类型化解码仍负责拒绝无法放进 T 的值。

现有结构化输出对自定义 JSON/Text 编解码、`json.Number`、`,string` 和带显式 JSON 名的匿名内嵌字段的检查，整理到 `pkg/datamodel/typecheck.go`。继续保留当前标准库类型的已知支持范围；普通数据模型不带入严格格式对 map 和非指针 `omitempty` 的限制。

字段中的 `any` 按依赖的开放 Schema 处理。它没有自动获得字段约束；业务需要限制其内容时用 Schema 明确表达，或者改成具体类型。

### 4.2 构造与冻结

`New[T]` 依次执行：检查类型的可表达性 → 推导 Schema → 执行 Schema 编辑回调 → 序列化并重新解析为独立 Schema → 检查版本和编译 → 保存冻结结果及业务检查列表。

重新解析的作用是隔离回调拿到的可变 Schema。回调即使保留了某个属性指针，之后修改它也不能改变已构造模型。不要每次 Decode 再复制 Schema 或调用 Resolve。

模型方法 `WithSchema` 从已冻结的 Schema 字节解析一个独立对象，执行新回调并编译新模型，同时复制业务检查列表。它不重新执行原构造回调。

### 4.3 JSON 校验解码

`DecodeJSON` 固定为：解析唯一 JSON 值 → 校验原始值 → 从同一字节解码进 T → 执行业务检查 → 返回 T。

解析原始值时使用 `UseNumber`，沿用现有结构化输出的数值规范化做法，供 Schema 校验器识别；解码进 T 时仍读取原始字节，避免先转成浮点数再转换整数。输入尾部只允许空白，不接受第二个 JSON 值、解释文字或 Markdown 代码围栏。

数据模型的类型化解码使用 `UseNumber`、`DisallowUnknownFields`，并检查尾部已结束。失败时返回 T 的零值，不能交付部分填充的对象。语法、Schema、目标类型或业务检查错误都包装 `ErrInvalidData`，同时保留底层错误链；错误中不主动拼接整段原始 JSON。

先校验原始值是为了区分“字段没有传”和“字段传了合法零值”。第一版不增加 `Validate(T)` 作为原始输入校验的替代，也不自动填充默认值或把字符串数字转换成整数。

### 4.4 LLM 的严格格式

`llm` 保留顶层必须为结构体、属性均为 required、禁止额外字段、指针省略字段仍要求键存在但允许 null，以及动态 map 不适合原生严格格式等现有规则。

默认构造入口把严格规范化作为数据模型的构造回调，只编译一次。`NewStructuredOutputFromModel` 则通过模型方法 `WithSchema` 创建严格副本；这是两个不同用途的模型各自构造一次，不是在每次调用中重复编译。

Format 导出严格副本的 Schema，Decode 也调用严格副本。因此，发给大模型的字段规则和本地 Schema 校验规则一致。

业务检查函数只在本地执行。例如“结束时间不能早于开始时间”，不会因为注册了一个 Go 函数就自动出现在发给大模型的 Schema 中；发送侧能够表达的约束仍需显式配置。

## 五、使用示例

普通业务只需要定义类型并构造模型。下面增加分数范围作为示例：

```go
type Decision struct {
    Approved bool   `json:"approved"`
    Score    int    `json:"score"`
    Reason   string `json:"reason,omitempty"`
}

model, err := datamodel.New[Decision](
    datamodel.WithSchema[Decision](func(s *jsonschema.Schema) error {
        minimum, maximum := 0.0, 100.0
        s.Properties["score"].Minimum = &minimum
        s.Properties["score"].Maximum = &maximum
        return nil
    }),
)
if err != nil {
    return err
}

decision, err := model.DecodeJSON([]byte(`{"approved":false,"score":0}`))
```

模型在组件初始化时构造，后续请求复用 `model`。这个输入可以没有 reason，也允许 approved 为 false、score 为 0；approved 或 score 缺失则报错。

同一类规则用于模型输出时：

```go
type ModelDecision struct {
    Approved bool    `json:"approved"`
    Score    int     `json:"score"`
    Reason   *string `json:"reason,omitempty"`
}

model, err := datamodel.New[ModelDecision](
    datamodel.WithSchema[ModelDecision](func(s *jsonschema.Schema) error {
        minimum, maximum := 0.0, 100.0
        s.Properties["score"].Minimum = &minimum
        s.Properties["score"].Maximum = &maximum
        return nil
    }),
)
if err != nil {
    return err
}
output, err := llm.NewStructuredOutputFromModel(model,
    llm.WithOutputName("decision"),
)
if err != nil {
    return err
}

messages, err := assistant.Invoke(ctx, input,
    llm.WithResponseFormat(output.Format()),
)
if err != nil {
    return err
}
decision, err := output.Decode(messages)
```

这里用指针表达可空 reason，使它符合现有严格格式要求：原模型可以接收缺失的 reason；模型输出的严格副本要求 reason 键存在，允许其为 null。普通模型的非指针可选字段不会被悄悄改成这种语义。

### 阶段一：公共编译能力与数据模型

**新增文件**：`internal/jsonvalidation/schema.go`、`json.go`、`schema_test.go`、`json_test.go`；`pkg/datamodel/model.go`、`options.go`、`errors.go`、`typecheck.go`、`model_test.go`。

内部接口确定为：

```go
type Compiled struct {
    raw      json.RawMessage
    resolved *jsonschema.Resolved
}

func Infer(t reflect.Type) (*jsonschema.Schema, error)
func Compile(s *jsonschema.Schema) (*Compiled, error)
func CompileJSON(raw json.RawMessage) (*Compiled, error)
func (c *Compiled) JSONSchema() json.RawMessage
func (c *Compiled) Validate(instance any) error

func ParseJSON(raw []byte) (any, error)
func DecodeTyped[T any](raw []byte, useNumber bool) (T, error)
```

`Infer` 只调用库的 `ForType`，不施加 LLM 或数据模型的额外政策。`Compile` 先序列化，再调用 `CompileJSON` 冻结并编译。版本检查采用当前工具校验器的规则：未声明、draft-07 和 draft 2020-12 可用，其他版本在编译时返回错误。沿用 `Resolve(nil)`，不增加网络引用加载器。

`ParseJSON` 承接当前 `decodeSingleJSON` 和数值规范化逻辑；`DecodeTyped` 从原字节完成严格解码及尾部检查，不包含 Schema 校验。数据模型传 `useNumber=true`，类型化工具传 false，以分别保留现有结构化输出和工具对接口字段中数值的处理方式。它是内部函数，普通用户的完整入口仍是 `Model.DecodeJSON`。

```go
package datamodel_test

import (
    "errors"
    "testing"

    "github.com/goharness/goharness/pkg/datamodel"
    "github.com/google/jsonschema-go/jsonschema"
)

type decision struct {
    Approved bool   `json:"approved"`
    Score    int    `json:"score"`
    Reason   string `json:"reason,omitempty"`
}

func TestModelDistinguishesMissingFromZero(t *testing.T) {
    model, err := datamodel.New[decision]()
    if err != nil {
        t.Fatal(err)
    }
    value, err := model.DecodeJSON([]byte(`{"approved":false,"score":0}`))
    if err != nil || value != (decision{}) {
        t.Fatalf("value=%+v err=%v", value, err)
    }
    value, err = model.DecodeJSON([]byte(`{"score":0}`))
    if !errors.Is(err, datamodel.ErrInvalidData) || value != (decision{}) {
        t.Fatalf("value=%+v err=%v", value, err)
    }
}

func TestModelFreezesSchemaCallback(t *testing.T) {
    var retained *jsonschema.Schema
    model, err := datamodel.New[decision](
        datamodel.WithSchema[decision](func(s *jsonschema.Schema) error {
            maximum := 100.0
            retained = s.Properties["score"]
            retained.Maximum = &maximum
            return nil
        }),
    )
    if err != nil {
        t.Fatal(err)
    }
    relaxed := 200.0
    retained.Maximum = &relaxed
    value, err := model.DecodeJSON([]byte(`{"approved":true,"score":150}`))
    if !errors.Is(err, datamodel.ErrInvalidData) || value != (decision{}) {
        t.Fatalf("value=%+v err=%v", value, err)
    }
}
```

| 场景 | 输入或操作 | 预期 |
| --- | --- | --- |
| 合法零值与可选字段 | `{"approved":false,"score":0}` | 成功，reason 缺失可接受 |
| 必填与类型错误 | 缺少 approved，或 approved 为字符串 | `ErrInvalidData`，返回零值 |
| 额外字段与尾部内容 | 增加 extra；对象后再跟一个对象或文字 | 拒绝 |
| 范围和目标类型 | score 配置 0～100 后传 101；int8 字段传 300 | 拒绝；不返回部分结果 |
| 指针和容器 | 缺失可选指针、指针为 null、正常嵌套数组和字符串键 map | 按推导规则接受；非可空标量为 null 拒绝 |
| 大整数 | int64 字段传 `9007199254740993` | 成功且数值保持原样 |
| 业务检查 | 用 `WithValidator` 拒绝某个已正确解码的值，返回一个 sentinel error | `errors.Is` 同时找到 `ErrInvalidData` 和该 sentinel；返回零值 |
| Schema 隔离 | 修改回调保留的属性指针；修改 JSONSchema 返回的字节 | 原模型规则不变 |
| 副本规则 | 原模型允许 score=150，WithSchema 副本限制到 100 | 原模型仍接受，副本拒绝；业务检查被保留 |
| 构造失败 | 不支持的类型、错误 Schema 引用、不支持的版本、编辑回调返回错误 | 构造时失败，不生成可用实例 |
| 并发复用 | 同一模型由多个 goroutine 解码各自的输入 | 结果独立，无竞态 |
