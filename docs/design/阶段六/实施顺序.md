# 阶段六实施顺序

- 编写日期：2026-10-12
- 状态：计划，未开始实施
- 目标与范围见[总体方案](总体方案.md)，每个工作项的设计见[具体方案](具体方案.md)（下表“设计”列给出章节）
- 本文只回答两件事：**先做什么、后做什么，为什么**；以及**每一步做到什么程度才算完成**
- 进度只记录在本文最后的“进度”一节，证据放在提交说明与 `.bench/results/stage6-*` 里，不另写长篇复核记录

## 一、排序原则

1. **先测量，再动手。** 总体方案里几处担忧（Redis 保存脚本开销、连接池）是推测，第零波先拿到数据，再决定改不改。
2. **先正确性与安全，再容量，最后扩展能力。** 租户隔离和并发保护出问题会泄露数据或产生脏写，优先级最高；限流和舱壁出问题只是过载；RAG 是新增能力。
3. **先写“护栏”，再暴露能力。** 例如租户安全检索（W3-6）排在检索工具（W3-4）之前：先保证隔离，再把检索交给模型调用。
4. **核心改动最少、最早。** 核心只有八处改动（C1 至 C8），全部放在第一波，其余都是扩展，可以随时增减。
5. **每个工作项可以独立合并。** 一个工作项对应一次提交，自带测试和文档，合并后仓库保持一致状态；停在任何一个工作项之后都不会留下半成品。
6. **每一波有门槛。** 通不过门槛不进入下一波。
7. **旧问题先核实再处理。** 审查报告里遗留的条目已经逐项对照当前代码核实（见[总体方案](总体方案.md)第二节）：已解决的不再做，仍存在的并入下面的工作项，需要数据判断的放进第零波的核查。
8. **只做需要框架语义的事。** 不需要框架内部语义、应用或基础设施能做的，只写对接说明（W5-6），不替应用选基础设施；见[总体方案](总体方案.md)“框架与应用的边界”。

## 二、总览

```text
W0 测量与基线
 └→ W1 正确性与安全（核心八处小改 + tenant + Redis 缓存）
      ├→ W2 容量治理与可观测（指标、模型限流、舱壁与排空、MCP、参考服务）─┐
      └→ W3 RAG（嵌入、Redis Search、入库、工具、评测）            ─┤→ W5 文档与收口
           W4 条件项（exit 模式、终止型工具、决策模型实验、Middleware 重评）─┘（按数据决定）
```

- W2 与 W3 在 W1 完成后互相独立，可以并行，也可以择一先行。
- 单人推进的建议顺序：W0 → W1 → W2 → W3 → W5，W4 只有条件项，按数据决定。选 W2 在前的理由：W2 提供指标和负载工具，W3 的检索与入库负载需要用它们来观察；如果 RAG 是眼前的交付重点，W3 也可以提前，除 W3-1 对限流器的可选接入要延后之外没有其他影响。

## 三、工作项完成的标准（每个工作项都要满足）

1. 代码与单元测试，涉及并发的在 `-race` 下通过。
2. 主扩展 module 与核心 module 的 `go build`、`go vet`、`go test -count=1 ./...` 通过。
3. 相关文档同步更新：用户文档、`检查点行为契约清单`（有新契约时）。
4. 不给核心增加新的外部依赖；新增依赖只在扩展，选发布满 7 天的稳定版并固定。
5. 提交信息写明工作项编号，例如 `stage6/W1-9: 元数据敏感键默认脱敏`。
6. 核心改动在提交说明里列出实际增减的行数。
