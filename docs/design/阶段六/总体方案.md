# 阶段六总体方案：多用户高并发与 RAG 能力

- 编写日期：2026-10-12
- 状态：计划，未开始实施
- 性质：本文只描述目标、范围、技术选择和验收口径；具体设计见[具体方案](具体方案.md)，实施步骤与顺序见[实施顺序](实施顺序.md)
- 前置：轻量化阶段零至五已完成，历史记录见[轻量化改良方案](../../轻量化改良方案.md)，被砍和外移的能力见[设计取舍](../../设计取舍.md)，恢复语义的对照依据见[检查点行为契约清单](../../检查点行为契约清单.md)

## 一、目标

把 goHarness 做成一个后端团队可以直接放进服务里的框架，同时具备四项能力：

| 能力 | 目标 |
| --- | --- |
| Agent | 多个用户并发调用同一批 Agent 实例，互不干扰，过载时有明确的拒绝行为，停机时运行可迁移到其他副本继续 |
| RAG | 不再只有接口和算法，而是能直接接入向量库、嵌入模型和重排服务，完成入库、检索、引用的完整链路，并且按租户隔离 |
| 可观测 | 除调用树外，有可告警的指标；能按租户筛选调用链和用量；默认不泄露内容 |
| 多用户 | 租户与会话隔离默认安全；同会话并发有明确语义（检查点版本冲突兜底）；传统后端能用熟悉的方式接入 |

## 二、现状（2026-10-12，已逐项核对代码）

### 已有，不需要重做
- **Agent 与图引擎**：ReAct 配方、泛型建图门面、Fork/Join 并行与 `Send` 分派、`Interrupt` 与按问题 ID 恢复、嵌套审批传播到根、检查点按整图指纹判断兼容。
- **状态存储**：`state.Store` 接口、内存实现、Redis 实现（`extensions/state/redis`）。Redis 实现用 Lua 做原子 CAS，key 带 `{id}` 哈希标签所以集群可用，支持 TTL、历史裁剪、回退依据。
- **并发保护的底线**：版本冲突返回 `state.ErrConflict`；会话存在未完成运行时新输入返回 `state.ErrUnfinishedRun`，只有显式 `agent.WithAbandonUnfinished()` 才能放弃。
- **观测**：`pkg/observe` 的事件与 `Observer`、`Async` 包装（带丢弃计数）、`Slog`；`extensions/otel` 把事件映射为 span。
- **多用户基础**：`tool.Subject`（含 `TenantID`、角色、权限）与 Middleware；`observe.WithMetadata` 设置的属性会进入所有事件。
- **RAG 的契约与算法**：`extensions/retrieval` 有分块（带重叠的 Token 窗口）、文档索引（`DocumentIndexer`）、混合检索（向量加关键词，RRF 或加权融合，可选 MMR 与重排）、带引用的上下文生成（`HybridRetriever`）；`extensions/cache/retrieval` 的检索缓存键已含租户。
- **子 Agent**：`extensions/subagent`，工具调用内同步运行。

## 三、设计原则

1. **正确性靠 CAS，不靠锁。** 框架不内置分布式锁；同会话串行化由应用选择（按会话粘性路由、数据库或 Redis 锁、队列分区键），检查点版本冲突是最后的兜底：任何串行化失效时，后到的写入都会被版本号拒绝。
2. **核心不增重。** 所有新能力放进 `extensions/`，只通过四个已有接缝接入：`state.Store` 装饰器、`llm.ChatModel` 装饰器、`runnable.Runnable` 装饰器、`observe.Observer`。核心只允许八处小改动（见第六节），每处都有对应的测试。
3. **Redis 优先，接口可换。** 默认用 Redis（会话、向量检索共用一套基础设施，后端团队少运维一个系统）；其他存储由使用者按 `state.Store` 等接口自己实现，对接说明给出要点。
4. **先测量，再优化。** 现有的几处担忧（Redis 脚本开销、连接池）是推测，先建立基线和压测工具，用数据决定要不要改。
5. **租户默认安全。** 会话 key、检索命名空间、缓存键都由统一的租户作用域生成，调用方拿不到“忘了加租户”的写法。
6. **观测默认低基数、不含内容。** 指标标签不放用户和会话；调用载荷需显式开启并经过脱敏。
7. **依赖进扩展，不进核心。** 新依赖只加到扩展模块，选发布满 7 天的稳定版本并固定；引入重依赖的包放进独立 module。
8. **只做需要框架语义的事，其余给接入点。** 见下一小节。

### 框架与应用的边界

判断一项能力该不该由框架写代码，问三个问题：
1. 它是否需要框架内部的语义才能做对？
2. 大多数用户是否都需要？
3. 能不能由应用或基础设施做？

前两问有一个答“是”、且第三问答“否”，才写代码；第三问答“是”的，只提供接入点、示例和对接说明，不替应用选基础设施。

**一条更直接的判断规则：这件事需要的信息，是只有框架知道，还是只有应用知道？**
- 只有框架知道的（Agent 内部状态、工具调用、检查点、嵌套运行、重试与流的内部行为）归框架：并发正确、内部参数可调、可观测、可排空。
- 只有应用知道的（用户、套餐、流量、业务优先级）归应用或网关：请求级限流、额度、排队、同会话串行化。
- 业界惯例也是如此：以 LangChain 为例，它只提供进程内、只按请求数的限流器，明确不跨进程；跨副本的限流与预算由 LiteLLM 这类 LLM 网关加 Redis 和数据库完成。主流框架提供进程内原语和钩子，分布式策略留给网关或平台。

| 类别 | 条目 | 处理 |
| --- | --- | --- |
| 框架自己做 | C1 至 C8、指标观察者、`RedisStore` 缓存上限、`tenant` 的 Store 装饰器、重试抖动、慢消费者超时 | 核心或扩展代码，必做 |
| 框架提供配方（扩展，可选） | 排空（附可选并发上限）、媒体解析与保护、决策模型集成（实验）、嵌入与重排客户端、Redis Search 适配器、检索工具与评测、MCP 信任策略、图可视化、精简的参考服务、子 Agent 的 `AsTool` 与上下文过滤函数、单任务限制 | 扩展代码，不用的人不受影响 |
| 留给应用，只写对接说明 | 额度与计费、消息队列与死信、事件回放、其他存储（Postgres 等）、其他向量库（pgvector、Qdrant 等）、检查点完整性签名与加密、会话串行化（锁、粘性路由、分区键）、跨副本限流（接 LLM 网关）、仪表盘文件与 compose 文件、异步任务模型、A2A 对接、声明式（YAML）Agent 的加载、校验与策略 | 文档，见实施顺序 W5-6 |

对接说明不是空话：它要写清楚应用怎样用框架**已有**的接入点（`Observer`、`state.Store` 接口、四个检索接口、`Resume`）接上自己的基础设施，并给出可以照抄的流程和示例片段。

## 四、总体架构

### 请求路径（一次用户调用）
```text
网关/负载均衡
  → 认证：JWT 等 → tenant.With(ctx, subject)                    [扩展 tenant]
      一次设置 tool.Subject、观测属性、会话 key 前缀
  → 应用自己的额度检查（可选，见对接说明）                      [应用]
      超额 → 429
  → 会话串行化（应用选择：粘性路由、锁或队列分区键）           [应用]
      冲突 → 409
  → 舱壁（进程内并发上限，可选排队）                            [扩展 limits]
      过载 → 503
  → Agent/Graph 运行                                            [核心]
      检查点：Redis CAS（会话 key 带租户前缀，装饰器校验）
      模型：重试（带抖动）→ 进程内限流（已有）
      工具：worker 上限可配置
      检索：嵌入 → 向量与关键词检索 → 重排 → 引用               [扩展 retrieval]
  → 事件流（SSE）：慢消费者超时保护                              [核心 stream]
  → 观测：trace 与 metrics，租户属性贯穿                         [observe + otel]
```

### 数据路径（RAG 入库）
```text
文档来源（调用方提供字节，框架不抓取 URL）
  → 加载器 → 分块 → 批量嵌入（经限流）→ 向量库 upsert（按租户命名空间）
  整条流水线是一次图运行：检查点保存进度，中途失败可恢复，不重复嵌入已完成的批次
```

### 模块布局

## 五、技术栈选择

| 领域 | 默认选择 | 备选 | 理由与约束 |
| --- | --- | --- | --- |
| 会话与检查点 | Redis（已有，`go-redis` v9，`UniversalClient`，单机、哨兵、集群均可） | 其他存储由使用者按 `state.Store` 自己实现（如 Postgres，用乐观版本列实现同样的 CAS 语义） | 热数据低延迟，Lua 原子 CAS 已验证；其他存储只给对接要点，不内置 |
| 同会话串行化 | 不内置 | 按会话粘性路由、数据库行锁、Redis 锁、队列分区键 | 正确性由检查点 CAS 兜底；各团队现成的做法不同，对接说明给几种写法 |
| 限流 | 进程内的 `llm.NewRateLimitedModel`（已有） | 跨副本交给 LLM 网关（如 LiteLLM）或应用自己用 Redis | 跨副本限流需要共享状态，那是网关的职责；框架用重试抖动与 `Retry-After`（C2）优雅处理 429 |
| 额度 | 应用自管，不内置 | Redis 计数、数据库计数 | 账单与对账以应用的数据库为准；框架只提供带租户属性和 `Usage` 的事件，对接说明给出 Redis 计数示例 |
| 异步任务与入库队列 | 不内置 | Kafka、RabbitMQ、NATS、Redis Streams | 恢复是至少一次投递，任何队列都能接；对接说明给出消费者流程（拿锁、幂等、检查点落盘后再确认）、最大尝试次数与死信做法 |
| 事件回放 | 不内置 | Redis Streams 等 | 对接说明给出 SSE 断线续传的思路 |
| 观测 | OpenTelemetry（trace 已有，新增 metrics）→ OTLP；日志用 `slog` | Prometheus 客户端直连 | 厂商中立，后端团队的现有平台通常已接 OTLP；指标名尽量对齐当时版本的 OTel GenAI 语义约定 |
| 向量与关键词检索 | Redis Search（HNSW 向量加全文，一个后端同时实现 `VectorStore` 与 `KeywordSearch`），需要带 Search 模块的 Redis（Redis Stack 或 Redis 8） | 其他向量库（pgvector、Qdrant、Milvus 等）由使用者按四个检索接口自己实现 | 与会话共用基础设施；其他后端只给对接要点，不内置 |
| 嵌入与重排 | HTTP 客户端，OpenAI 兼容的 `/embeddings`；重排用可配置路径的 JSON 接口，复用 `httpclient.Pool` | 各厂商私有 SDK | 自托管的推理服务（如 TEI）通常兼容；不引入厂商 SDK |
| 文档加载 | 文本、Markdown、简化 HTML，只接收字节或 `io.Reader` | PDF、Office 由使用者提供加载器或旁路服务 | 不内置 PDF 解析，避免重依赖；**不在框架里抓取 URL**，避免 SSRF |
| HTTP 服务 | 标准库 `net/http` 与 SSE | chi、gin | 参考服务不引入 Web 框架；说明如何接入已有路由 |
| 集成测试 | 环境变量指向真实服务（沿用 `GOHARNESS_BENCH_REDIS_ADDR` 的做法），单元测试用 miniredis | testcontainers | 不新增依赖；miniredis 不覆盖 Search 命令，向量检索必须用真实 Redis Stack 测，这是已知限制 |
| 协程泄漏检查 | 测试里用 `runtime.NumGoroutine` 稳定后比较的小工具 | goleak | 不新增依赖 |

## 六、核心需要修改的地方

核心只有八处小改动，其余都在扩展。详细设计见[具体方案](具体方案.md)第二节。其中 C1 至 C4 来自多用户高并发的需要，C5 与 C6 来自对旧审查报告遗留项的再分析（见第二节），C7 来自声明式（YAML）Agent 的需要，C8 来自多模态的需要。

| 编号 | 位置 | 改动 | 原因 |
| --- | --- | --- | --- |
| C1 | `pkg/tool/runtime.go`、`node.go`、`agent` 的选项 | worker 上限从常量 128 变成可配置，默认保持 128；`MaxAbandoned` 的上限随之改为该值 | 每个 Agent 实例的并发工具执行上限不应被写死 |
| C2 | `pkg/llm/retry.go`，OpenAI 兼容适配器 | 退避加抖动；错误上暴露 `RetryAfter()`，重试时取较大者 | 避免大量并发运行在 429 后同时重试 |
| C3 | `pkg/stream/run.go` 的 `Config` | 增加可选的发送超时，超时以明确错误终止运行 | 慢客户端不应无限期占住运行 |
| C4 | `pkg/observe` | 增加租户、用户、会话的属性键常量 | 让 `tenant`、`limits`、`otel` 对键名达成一致，不靠字符串约定 |
| C5 | `pkg/observe` | 事件发射边界默认对敏感键（授权头、令牌、密码、密钥、Cookie 等）的值脱敏，应用可追加自己的敏感键 | 元数据原样进入日志和 trace，是多租户下的泄露风险（旧 3.11） |
| C6 | `pkg/tool/tool.go`、`pkg/llm/openai_compatible.go` | 删除 `tool.ParseArgs`；`GenerateConfig` 含保留键（`model`、`messages`、`stream`、`tools`、`functions`）时报错而不是静默覆盖或替换 | 消除两个静默误用的出口（旧 3.12、3.7） |
| C7 | `pkg/agent`、`pkg/graph` | 新增 `agent.WithDefinitionVersion`（图层对应 `SetDefinitionVersion`）：版本串明文写入执行记录，恢复时不一致即拒绝 | 整图指纹不含系统提示、工具与模型，配置变更后挂起的运行会静默用新配置继续 |
| C8 | `pkg/llm/openai_compatible.go` | 内置适配器支持图片输入的编码（`image_url`，内联数据按 MIME 编成 data URI），受 `Capabilities.Vision` 约束；文件、音频、视频仍明确报错 | 目前图片块发不出去，README 示例会失败 |

预计核心增量很小（估算在百行量级），不影响轻量化阶段的代码量目标；以实际改动为准，每项改动都要在实施记录里列出行数变化。

## 七、传统后端怎样用这个框架

框架的几个概念可以直接对应到后端开发者熟悉的东西，接入成本主要是理解这张表：

| 后端熟悉的概念 | 框架里对应的 | 说明 |
| --- | --- | --- |
| 会话 ID、业务主键 | 会话 key（`conversation ID`） | 由 `tenant` 统一生成，带租户前缀 |
| Repository / DAO | `state.Store` | 内置 Redis 实现，也可自己实现 |
| 乐观锁（版本列） | 检查点版本 CAS | 冲突返回 `state.ErrConflict`，对应 HTTP 409 |
| 分布式锁、串行化同一资源 | 应用自选；框架的检查点版本冲突兜底 | 对接说明给粘性路由、数据库或 Redis 锁、队列分区键几种做法 |
| 幂等键、消息重投 | 恢复是 at-least-once，工具调用结果按调用身份复用 | 副作用仍需业务幂等 |
| 中间件、拦截器 | `tool.Middleware`、`llm.ChatModel` 装饰器、`Observer` | 鉴权、审计、重试、限流都挂在这些点上 |
| 主体、角色、权限 | `tool.Subject` | 由 `tenant.With` 与认证结果一起设置 |
| 熔断、舱壁、限流 | `limits` 的排空与可选并发上限、`llm` 的重试与进程内限流 | 跨副本限流交给网关；启用并发上限时过载返回明确错误，对应 503 |
| 工作流、状态机、Saga | `graph` | 节点、条件边、并行、人工审批 |
| 审批任务、待办 | `Interrupt` 与按问题 ID 恢复 | 对应 HTTP 202 加问题 ID |
| 队列、Outbox | 不内置，见对接说明 | 由应用的队列消费者调用框架 |
| 链路追踪、指标 | `observe` 加 OTel | 接入现有 OTLP 平台 |

后端团队接入的四步：用 `tenant.With` 把认证结果转成上下文；用 `limits` 的排空与并发上限包住 Agent；把 `observe.With` 和指标观察者接到现有观测平台；按“错误到 HTTP 状态码”的映射表（见具体方案）写网关层。参考服务把这四步串成一个可运行的例子。

反过来，框架依赖后端提供的基础设施：Redis（必需）、OTLP 接收端、IdP 或网关（认证）。

## 八、非目标

- 不做网关、认证服务、计费系统。
- 不自研向量数据库；只提供 Redis Search 适配器，其他后端按接口自行实现。
- 不内置消息队列、额度、事件回放、其他存储和其他向量库的适配器，只写对接说明。
- 不做音频、视频的输入输出编码，也不做多模态嵌入与检索，有真实需求再立项；图片输入先做。
- 不实现 exactly-once；恢复仍是 at-least-once，副作用幂等由业务负责。
- 不做跨地域部署与跨集群复制。
- 不改变图引擎、检查点和 `observe` 的既有语义；契约清单 A 至 I 节必须继续全部通过。
- 不在阶段内重做已移出核心的后台异步子任务。

## 九、验收口径

1. **正确性**：契约清单 A 至 I 节全部通过，并新增“并发契约”（同会话竞争只有一个成功、串行化失效时后到的写入被拒、租户 key 越权被拒），见具体方案 8.1。
2. **性能**：沿用既有的 10% 规则，以新基线 `pre-stage6` 为固定对照；新能力使用独立场景说明其成本。
3. **容量**：不预设数字。第零波先测出当前的并发上限与延迟分布，再据此设定目标并写入实施记录；没有数据支撑的目标不写进验收。
4. **运维**：提供指标清单与告警建议（写进运维指南，不随仓库提供仪表盘文件），以及多副本部署、Redis 配置、停机排空的指南；另有一份对接说明集（额度、队列、事件回放、其他存储与向量库、完整性与加密）。
5. **RAG**：评测工具能在固定数据集上给出召回率与排序指标，作为回归门槛；向量检索的集成测试在真实 Redis Stack 上通过。
6. **代码量**：核心增量在实施记录中逐项列出；扩展不计入核心目标。

## 十、风险与取舍

| 风险 | 缓解 |
| --- | --- |
| Redis 保存脚本在长会话并发下阻塞 Redis（推测） | 第零波先测；确有问题再优化，候选方案见具体方案 |
| Redis Search 无法用 miniredis 测试 | 环境变量开关的真实 Redis Stack 集成测试，在 CI 中以服务容器运行；README 说明本地如何启动 |
| 租户装饰器无法校验直接拿到底层 Store 的代码 | 文档约定应用只暴露装饰后的 Store；参考服务按此组装 |
| 范围过大 | 按“框架与应用的边界”收缩，只写需要框架语义的代码；分波次，每波有 Gate；第四波只剩条件项，停在任何一波都是一致状态 |
| RAG 与多用户两条线争抢精力 | 第一波完成后两条线互相独立，可以并行或择一先行 |
| 默认敏感键脱敏误伤正常字段（例如把 `input_tokens` 当成令牌） | 按键名的整段单词匹配，不做子串匹配；测试覆盖不应命中的键；提供追加敏感键的入口 |
| MCP 信任策略默认值过严，影响现有接入 | 默认只做“忽略远端只读注解、截断并清理描述”，白名单类限制在端点或命令来自用户输入时才强制；文档写明区别 |
| 去掉 `GenerateConfig` 里传 `tools` 的做法，影响想用 Provider 原生工具的人 | 当前没有使用者；后续如需要，通过类型化选项提供（与 4.5 一起），不开放自由 map 的替换口 |
| 决策模型这个类别很新（2026 年 9 月才出现），接口形状可能变化 | 接口保持厂商中立，适配器放扩展并标注实验，不改核心；至少两家的接口形状稳定、且有真实需求后再转正 |
