## 一、约定

- **包路径**：`extensions` 是独立 module，下面的包都在其中。
- **Redis 键规则**：同一个 Lua 脚本只访问共享同一哈希标签的 key。会话相关的 key 沿用现有做法，标签是会话 key 的 base64url 编码（`{...}`）。
- **租户标识**：租户 ID 只允许 `[A-Za-z0-9._-]`、长度 1 到 64，保证用 `/` 作分隔符不会产生歧义。
- **观测属性键**：`tenant_id`、`user_id`、`conversation_id`。后者是现有 `agent` 已经在用的键，不另造 `session_id`。

## 二、框架内需要修改的地方

### 核心八处（C1 至 C8）

#### C1 工具 worker 上限可配置

**现状**：`NewToolsNode` 为每个节点建一个 `Runtime`（`pkg/tool/node.go` 94 行），`Runtime.workers` 的容量是常量 `maxRuntimeWorkers = 128`（`pkg/tool/runtime.go` 20、96、115 行）。一个 Agent 实例被所有用户共享，所以**这个实例上所有在途运行加起来最多 128 个并发工具执行**，超出的排队等待。批内并发上限 `MaxConcurrency` 另算，不超过 64。

**改动**：
- `RuntimeConfig` 增加 `MaxWorkers`，0 表示 128（保持现状）；校验范围 1 到一个更大的硬上限（初始值 4096，实现时确定）。
- `MaxAbandoned` 的上限改为 `MaxWorkers`。
- `ToolNodeConfig.MaxWorkers` 透传；`agent` 增加 `WithToolWorkers(n)`。

**语义**：这是实例级的全局上限，和批内并发无关；等待 worker 的调用遵守 `ctx`，取消时立即返回。

**测试**：`MaxWorkers=2` 时四个并发运行的工具调用最多两个同时执行，其余等待且可被取消；默认值下现有测试全部不变。

#### C2 LLM 重试加抖动并读取 Retry-After

**现状**：`pkg/llm/retry.go` 的 `retryDelay` 是确定性的指数退避，不抖动；默认可重试判定包含 429，但不读 `Retry-After`。并发运行很多时，遇到限流会同时重试。

**改动**：
- `RetryConfig` 增加 `NoJitter bool`（零值即开启抖动）和 `Rand func() float64`（测试注入，默认用全局随机源）。抖动采用“等量抖动”：延迟取 `d/2 + rand*d/2`，保留下限，避免退化成零延迟。
- 错误若实现 `RetryAfter() time.Duration`，则延迟取抖动结果与该值中较大者；若 `RetryAfter` 超过 `MaxDelay`，不再重试，直接返回错误（避免让运行长时间挂着）。
- OpenAI 兼容适配器在产生带 `StatusCode()` 的错误时解析 `Retry-After` 头（秒数或 HTTP 日期两种格式）。

**取舍**：这是默认行为变化，项目没有使用者，因此直接改默认；依赖确定性延迟的现有测试改用 `NoJitter`。

**测试**：固定 `Rand` 下延迟可复现；`RetryAfter` 较大时被采用；超过 `MaxDelay` 时不重试；流式路径“首个增量之后不重试”的既有语义不变。

#### C3 事件流的慢消费者超时

**现状**：`stream.Run` 的事件队列有界且不丢失；队列满时 `publish` 一直阻塞，直到有空位、读端关闭或 `ctx` 取消（`pkg/stream/run.go` 的 `publish`）。客户端连接还在但读得很慢时，会拖住运行。

**改动**：
- `stream.Config` 增加 `SendTimeout time.Duration`，0 表示不限（现状）。
- 队列满且等待超过 `SendTimeout` 时，以 `ErrSlowConsumer` 为原因取消执行上下文（`Run` 内部改用 `context.WithCancelCause`），运行结束时读端收到该错误。
- 如果运行开启了检查点，被取消的运行停在最近的边界，记为失败而不是中断，可以由应用决定是否 `Resume`。

**测试**：消费者不读取、`SendTimeout=50ms`，运行在有限时间内以 `ErrSlowConsumer` 结束；运行后协程数回落；默认值（0）下行为不变。

#### C4 观测属性键常量

**改动**：`pkg/observe` 增加常量 `AttrTenantID = "tenant_id"`、`AttrUserID = "user_id"`、`AttrConversationID = "conversation_id"`（后者与 `pkg/agent/state.go` 现有键一致）。`tenant`、`limits`、`otel` 都引用这些常量。

**测试**：见第六节的端到端契约测试。

#### C5 元数据敏感键默认脱敏（旧 3.11，在多租户下升为 P1）

**现状**：`observe.WithMetadata` 设置的所有键，经 `Begin` 并入调用元数据，再经 `EventOf` 原样进入 `Event.Attrs`；`observe.Slog` 把每个 `Attrs` 键值都写进日志（`pkg/observe/slog.go` 41 行），`extensions/otel` 的 `attrsOf` 把它们全部写成 span 属性。`CapturePayload` 只对 `Event.Payload` 提供脱敏钩子，对元数据没有任何过滤。应用只要把令牌、授权头之类放进元数据，就会进入日志和链路后端。

**改动**：
- 在事件分发边界（`observe.Emit` 与 `EmitPayload`，此处有 `ctx`）对 `Event.Attrs` 做脱敏：命中敏感键的值替换为 `"[redacted]"`。
- **匹配规则**：键名转小写，把 `.`、`-` 视为 `_`，按 `_` 切成单词；任一单词属于 `{authorization, password, passwd, secret, token, cookie, credential, credentials}`，或出现相邻的 `api`、`key` 或 `private`、`key`，即命中。整词匹配，所以 `access_token` 命中，`input_tokens`、`max_tokens` 不命中。
- `observe.WithSensitiveKeys(ctx, keys ...string)`：应用追加自己的敏感键（同样规范化后精确匹配），随 `ctx` 传递。
- **写时复制**：没有命中时不分配、不修改；命中时复制 `Attrs` 再替换，`ctx` 里的元数据映射和其他观察者收到的同一事件不受影响。
- **范围**：只处理 `Event.Attrs`。`Payload` 仍由 `CapturePayload` 的钩子处理；工具的 `CallInput.Metadata` 是给受信任的工具代码用的，需要租户等业务字段，不过滤。
- 默认开启，不提供关闭开关；确有需要时通过 `WithSensitiveKeys` 之外的调整再评估，避免出现“忘了打开”。

**测试**：元数据含 `authorization` 时，`Slog` 输出与 OTel span 属性中都是 `[redacted]`；`input_tokens`、`max_tokens`、`tool.read_only` 不被改动；自定义敏感键生效；原元数据映射不被修改；无命中路径的基准零额外分配；并发发射在 `-race` 下通过。

#### C6 两个静默误用出口（旧 3.12、3.7）

**改动一：删除 `tool.ParseArgs`**。该函数在解析失败时返回空 map（`pkg/tool/tool.go` 200 行），误用会以空参数执行工具；生产代码没有调用者（只有 `tool_test.go` 在用）。直接删除，同时删除对应测试，保留 `ParseArgsStrict`。

**改动二：`GenerateConfig` 保留键校验**。OpenAI 兼容适配器在 `requestPayload` 里（`pkg/llm/openai_compatible.go` 268 至 297 行）先把 `GenerateConfig` 合并进请求体，再强制写入 `model`、`messages`、`stream`；只有在请求体里没有 `tools` 与 `functions` 时才写入框架生成的工具定义，也就是配置里一旦出现这两个键，框架的工具定义会被静默丢弃。
- 保留键集合为 `model`、`messages`、`stream`、`tools`、`functions`。出现在构造时的配置或单次调用的 `ExtraGenerateConfig` 中，一律返回 `llm.ErrReservedGenerateKey`（带键名），在发送请求之前报错。
- **取舍**：这去掉了“用 `GenerateConfig["tools"]` 传 Provider 原生工具”的做法。项目没有使用者，直接收紧；如果以后需要，用类型化选项提供（与 4.5 一起做），不再开放自由 map 的替换口。
- 约定：`GenerateConfig` 只能来自应用配置，终端用户输入不得直接进入；写进网关指南。

**测试**：五个保留键各一例，分别在构造与调用两处触发；`response_format` 的既有冲突检查不变；正常参数（`temperature`、`max_tokens`、`seed`）不受影响；删除 `ParseArgs` 后全仓库编译通过。

#### C7 定义版本固定（`agent.WithDefinitionVersion`）

**背景**：整图指纹只包含节点（ID 与输入输出类型）、边、分派声明和 State 编解码身份（`pkg/graph/revision.go`），**不包含系统提示、工具集合和模型**。应用若用 YAML 或数据库驱动 Agent 定义，改了配置后，挂起的运行仍能通过指纹检查恢复，并静默使用新配置继续；新配置如果删掉了某个工具，恢复时重放的工具调用会失败。

**改动**：
- `agent.WithDefinitionVersion(v string)` 初始化选项（遵循只用 Option 的约定）；图层增加对应的 `SetDefinitionVersion`，供自建图使用。版本串长度不超过 128 个字符，只允许可打印字符。
- 版本串以明文写入执行记录（不是混进哈希），恢复时**先于指纹比较**：不一致返回 `ErrDefinitionVersionMismatch`，它同时满足 `errors.Is(err, ErrGraphRevisionMismatch)`，既有的处理代码不用改，错误信息又能指出真正的原因。
- 没有设置版本的运行行为完全不变；只有一侧设置了版本、另一侧没有时，按不一致处理（显式优先）。
- 只在“继续执行”时检查；已完成的运行读取保存的结果、放弃运行（abandon）都不受影响。
- 嵌套的子 Agent、`AsTool` 的专家各自有自己的版本，各自的记录各自检查。

**测试**：版本相同可恢复；版本不同返回 `ErrDefinitionVersionMismatch` 且 `errors.Is` 两者都成立；未设置版本时行为与现在完全一致；一侧设置另一侧未设置时拒绝；已完成的运行与 abandon 不受影响；子 Agent 各自版本独立检查；超长或含不可打印字符的版本串被拒绝。

#### C8 图片输入编码（内置 OpenAI 兼容适配器，W1-12）

**现状**：`pkg/llm/openai_compatible.go` 的 `encodeOpenAIMessages` 遇到文本、推理、工具调用与工具结果以外的块，一律返回 `unsupported block type`（698 至 728 行），工具结果里的非文本块也被拒绝（747 行）。数据模型里有图片、文件、音频、视频块，但**图片输入实际发不出去**；README 里的图文消息示例在内置适配器上会失败。至少它是明确报错，没有静默丢弃。

**改动**：
- 含非文本块的消息改用 `content` 数组形式，文本与图片按块顺序混排，图片写成 `{"type":"image_url","image_url":{"url":…}}`；纯文本消息保持现在的字符串形式，已有测试不变。
- 图片的来源：`URI` 是 http 或 https 地址时原样传出；`Data` 内联时按 `MIMEType` 编成 data URI；两者都为空报错。`file://` 等本地 URI 不在适配器里读取，由 W2-10 的解析器在发送前转成 data URI，适配器遇到未解析的本地 URI 返回明确错误。
- 受 `Capabilities.Vision` 约束：为假时返回明确的能力不支持错误并指出块的位置，不静默丢弃。**默认值与 `JSONSchema` 一致，为假**，需要使用者通过 `llm.Config.Capabilities` 显式开启（框架不按模型名猜测能力，文档已有这条原则）。
- 文件、音频、视频块仍然报错，有真实需求再做。
- 工具结果里的非文本块仍然报错，并在错误里说明原因：OpenAI 兼容协议的 `tool` 消息通常只接受文本（凭经验，没有逐家核对），需要图片时放进随后的用户消息。
- README 与相关文档的图文示例按此修正，并写明“目前只支持图片输入”。

**测试**：用 `httptest` 服务捕获请求体，验证图文混排的顺序与结构；纯文本请求体不变；`Vision` 为假时报错；内联 `Data` 编成正确的 data URI；本地 URI 未解析时报错；流式与非流式使用同一份编码；工具结果含图片时的错误信息。

核心增量估算在百行量级（C5 与 C6 合计为净增，`ParseArgs` 的删除抵消一部分，C7 约二三十行，C8 约百行以内）；实施时在记录里列出每项的实际行数。

### 扩展内部两处（E1、E2）

#### E1 `RedisStore` 进程内日志视图加上限

**现状**：`RedisStore.logs` 保存每个会话最近一次保存时的消息摘要（每条消息一个 sha1 十六进制串），只在 `Save` 成功时写入，只在 `Delete` 时清除（`extensions/state/redis/redis.go` 340、357、517 行）。会话数不断增加时内存只增不减。

**这个缓存只是乐观猜测**：命中时只发送新增消息；未命中时 `claimed=0`，客户端发送全部消息体，由脚本比对出真实共享前缀。**所以淘汰一个条目只会让那一次保存多花网络流量，不影响正确性。**

**改动**：
- `RedisStoreConfig` 增加 `LogCacheSize`，0 表示初始值 1024 个会话；用 `container/list` 加 map 实现 LRU，沿用现有的互斥锁。
- 暴露当前条目数与淘汰计数（供指标使用）。

**测试**：保存超过上限数量的会话后条目数不超过上限；淘汰后继续保存与读取的结果与现有日志测试一致；并发保存与删除在 `-race` 下通过。

#### E2 保存脚本的开销优化（候选，由 W0-4 的数据决定是否做）

当前每次保存，脚本在 Redis 的单线程里做这些事：
1. 取回已存日志并逐条 `sha1hex` 比对客户端发来的全部摘要，开销随会话消息数线性增长；
2. 对上一条记录和新记录各做一次 `cjson.decode`，只为比较 `run_id`（记录里包含执行数据，可能很大）；
3. 对 `order` 和 `epochs` 两个 JSON 数组各做一次解码与编码，开销随 `MaxHistory` 增长。

候选优化，按风险从低到高：

| 候选 | 做法 | 正确性依据 | 风险 |
| --- | --- | --- | --- |
| a. 去掉两次记录解码 | 客户端把新记录的 `run_id` 作为参数传入，脚本在主 hash 里单独存当前头部的 `head_run` 字段，直接比较字符串 | 与现有比较的语义完全相同 | 低 |
| b. 命中视图时跳过逐条比对 | 客户端额外发送缓存视图对应的头部记录 ID；脚本在 CAS 已通过且该 ID 等于当前头部时，说明自客户端上次保存以来日志没有变化，直接信任 `claimed` | 日志只在本脚本内、受头部 CAS 保护地修改；头部相同意味着没有其他保存发生（删除重建与放弃都会改变头部记录 ID） | 中，需要为分叉、放弃、删除重建补测试 |
| c. `order` 与 `epochs` 改用原生结构 | 例如用 LIST 保存 `order`，用 SET 保存存活代次，避免整体解码重编码 | 需要重新设计数据布局 | 高，只有 a、b 之后数据仍显示瓶颈才做 |

W0-4 的压测给出“多长会话、多大并发下脚本耗时如何”，再决定做 a、a 加 b，还是都不做。

## 三、租户与多用户（`extensions/tenant`）

### 3.1 目标

让“忘了加租户”在构造层面做不到：会话 key、检查点存储的访问、观测属性、工具主体，都由同一个入口设置。

### 3.2 作用域与会话 key

```go
package tenant

// With 校验 subject.TenantID 后，一次设置三件事：
// 1. tool.WithSubject(ctx, subject)
// 2. observe.WithMetadata(ctx, {tenant_id, user_id})
// 3. 在 ctx 中记录作用域，供 Store 装饰器与 SessionKey 使用
func With(ctx context.Context, subject tool.Subject) (context.Context, error)

func FromContext(ctx context.Context) (Scope, bool)

// SessionKey 生成带租户前缀的会话 key：t/<租户>/u/<用户>/s/<会话>
// 租户与用户不合法时返回错误；会话部分只限制长度。
func SessionKey(ctx context.Context, sessionID string) (string, error)

var (
    ErrNoScope        = errors.New("tenant scope missing in context")
    ErrTenantMismatch = errors.New("conversation key does not belong to the tenant")
)
```

### 3.3 Store 装饰器

```go
// NewStore 包装任意 state.Store：每个方法先从 ctx 取作用域，
// 要求 ConversationID 以 "t/<租户>/" 开头，否则返回 ErrTenantMismatch；
// ctx 里没有作用域返回 ErrNoScope（拒绝，不放行）。
func NewStore(inner state.Store, opts ...StoreOption) state.Store

func StrictUser() StoreOption // 额外要求 "u/<用户>/" 前缀，同租户内的用户之间也隔离
```

要点：
- **透传可选接口**：引擎会对 Store 做类型断言使用 `state.RollbackBasisReader`，装饰器必须实现并透传，否则放弃运行的回退会静默失效。
- **子 Agent 与嵌套子执行的 key** 是在会话 key 后追加 `/agents/...` 或 `/<RunID>/...`，前缀不变，天然通过校验。
- **只能保护经过装饰器的访问**：应用只应暴露装饰后的 Store；参考服务按此组装。
- **失败语义**：越权访问返回错误而不是空结果，避免把越权当成“不存在”。

### 3.4 数据生命周期

- 删除一个会话：`store.Delete`（现有），子 Agent 记录用 `extensions/subagent` 的 `Cleanup`，检索缓存与向量数据按第五节的命名空间删除。
- 保留策略：`RedisStoreConfig.TTL` 与 `MaxHistory`，在部署指南里给出选取方法。
- 按租户列出与清除会话需要应用自己维护会话清单（例如创建会话时记录）；框架不内置租户会话索引，对接说明给出做法。

### 3.5 测试

- 跨租户的 `Load`、`Save`、`Delete`、`Get`、`List` 都被拒绝；无作用域被拒绝。
- 子 Agent key 与嵌套子执行 key 通过；`RollbackBasisReader` 透传，放弃运行后的回退与未装饰时一致。
- 租户 ID 含 `/` 等非法字符被拒绝，不能通过构造特殊租户 ID 越过前缀。

### 3.6 检查点完整性与加密（不实现，只写对接说明，旧 3.10 的后半部分）

检查点是明文 JSON：任何能写 Redis 的人（误操作、被攻破的其他服务、错误的运维脚本）都可以改写 `Execution` 来伪造恢复进度。这属于存储层的访问控制问题，框架不内置签名与加密。对接说明（W5-6）写明应用的做法：

- 传输加密、静态加密和访问控制交给 Redis 的 TLS、ACL 与磁盘加密；不同服务使用不同账号和 key 前缀。
- 需要防篡改的应用，自己写一个 `state.Store` 装饰器，对 `Execution` 做 HMAC：绑定会话 key 与 `RunID`（防止把有效签名搬到别的会话或别的运行），验证失败拒绝，密钥支持轮换。
- 写装饰器时的要点：只签 `Execution`（`Messages` 与 `Values` 经存储层日志去重和 JSON 往返，字节不稳定，强行签名容易误报）；必须透传 `state.RollbackBasisReader`；装饰顺序放在 `tenant.NewStore` 之内。
- 不放进框架的原因：它不需要框架内部语义，密钥管理和轮换又是应用的安全策略；内置反而会让使用者误以为框架已经解决了存储层的信任问题。

## 四、高并发设计

### 4.1 并发模型：一次调用经过的关口

| 顺序 | 关口 | 组件 | 失败时 |
| --- | --- | --- | --- |
| 1 | 认证与作用域 | 应用 + `tenant.With` | 401 或 403 |
| 2 | 额度检查 | 应用自己的实现（可选，见 4.4） | 超额：429 |
| 3 | 请求级限流 | 网关或应用（框架只提供进程内的模型调用限流，见 4.3） | 429 并带 `Retry-After` |
| 4 | 会话串行化 | 应用选择（见 4.2） | 冲突：409 |
| 5 | 舱壁（可选） | `limits.Bulkhead` | 过载：503 并带 `Retry-After` |
| 6 | 运行 | 核心 | 见下 |
| 7 | 检查点保存 | `state.Store`（Redis 加租户装饰器） | 版本冲突：409 |
| 8 | 事件输出 | `stream` | 慢消费者：终止运行 |

第 6 步内部：模型调用是“重试（带抖动）→ 限流装饰器 → 模型”；工具调用受实例级 worker 上限和批内并发限制；检索调用受嵌入限流。

**可选的意思**：每一关都可以不装，装哪几关由使用者按场景选。核心不依赖它们，正确性只依赖第 7 步的 CAS。

### 4.2 会话串行化（不实现，只写对接说明）

同一会话的两个请求同时到来时，**正确性已经由检查点版本冲突兜底**：后到的写入返回 `state.ErrConflict`，会话里有未完成的运行时新输入返回 `state.ErrUnfinishedRun`。串行化只是为了少浪费一次模型调用，不是为了保证数据正确。各团队已有的做法不同，框架不替应用选，对接说明（W5-6）给出几种写法：

| 做法 | 适用 | 要点 |
| --- | --- | --- |
| 按会话 ID 在负载均衡处粘性路由 | 副本数多、希望零额外依赖 | 同一会话总落在同一副本，进程内用一个按会话 key 的互斥即可；副本故障或扩缩容时短暂失去串行化，由版本冲突兜底 |
| 数据库行锁或 Redis 锁 | 已有锁设施 | 拿锁后再调用 `Invoke` 或 `Resume`；锁过期后旧持有者的写入会被版本号拒绝，所以不需要 Redlock 级别的强保证 |
| 队列分区键 | 已经用 Kafka 等队列 | 以会话 key 作分区键，同会话天然有序，见 4.8 |

**对应的 HTTP 语义**：冲突返回 409，响应体里区分“并发更新冲突”（客户端重试）与“有未完成的运行”（应 `Resume` 或显式放弃）。
### 4.3 限流（只保留进程内，跨副本写对接说明）

框架已有 `llm.NewRateLimitedModel`：按实例、进程内的令牌桶，用来保护单个进程对模型厂商的请求节奏。跨副本、按租户、按 token 的限流需要共享状态，是网关的职责，不放进框架：

- **接 LLM 网关**：像 LiteLLM 这样的代理在网关层按 key 或团队做 tpm、rpm 限流和预算，用 Redis 在多副本间共享计数。应用把模型的 `ModelServer` 指向网关即可，框架不需要任何改动。
- **自己用 Redis**：对接说明给出一个令牌桶的参考写法，供没有网关的团队参考。
- **框架负责把 429 处理好**：C2 的重试抖动与 `Retry-After`，避免大量并发运行在被限流后同时重试。
- **组合顺序**：重试在外层，限流在内层（`llm.NewRetryingModel(llm.NewRateLimitedModel(m, ...), ...)`），每次真实请求都重新占用配额。
- 嵌入客户端（第五节）的限流器由应用注入，接口只有一个 `Wait(ctx) error`，可以对接网关或自己的限流。
### 4.4 额度（不实现，只写对接说明）

额度与计费是应用职责，框架不内置。框架提供的是接入点：

- llm 结束事件带 `Usage`（输入、输出、缓存读取、推理 token）和租户、用户属性（C4）。
- 对接说明（W5-6）给出一个可以照抄的 Redis 计数示例：用 `observe.Observer` 对 `tenant_id` 做 `INCRBY`，窗口键带过期（Lua 里只在首次写入时设置过期）；运行前检查已用量，超额返回应用自己的错误，网关映射为 429。
- 这是**软额度**：运行前检查、运行后累加，超额幅度最多是一次运行的用量；需要硬上限的应用自行在运行前预留估算值、结束后退还。
- 观察者在运行线程里调用 Redis 会增加延迟，示例用 `observe.Async` 的阻塞模式（队列满时阻塞而不是丢弃，避免丢账）。
- 账单与对账以应用的数据库为准，Redis 计数只用于近实时的限制。
- 单次运行的预算同理：Observer 累计 token，超限时用 `context.WithCancelCause` 加 `control.RequestInterrupt` 中止当前运行，cookbook 给示例。
### 4.5 舱壁与排空（`limits.Bulkhead`）

本节的核心是**排空**：它依赖 `RequestInterrupt` 与检查点，应用自己做不到；并发上限只是附带的可选能力，应用自己用信号量也能写。

- 每个在途运行用 `context.WithCancelCause` 登记，`Drain` 逐个取消；开启了检查点的运行会以 `graph.ErrInterrupted` 返回，进度已经保存，其他副本可以 `Resume`。**未开启检查点的运行只会被取消**（返回错误），文档明确说明。

**停机流程（参考服务采用）**：就绪探针变为失败 → 停止接收新请求 → `Bulkhead.Drain` → 等待在途请求返回 → 退出。

**测试**：并发上限与排队；排队超时；单租户上限；`Drain` 后在途运行以中断返回且检查点可由另一个实例 `Resume`；流式调用的名额在读端关闭后才释放；协程数回落。

### 4.6 Redis 键空间总表

| 用途 | key 模式 | 类型 | 哈希标签 | 过期 | 阶段 |
| --- | --- | --- | --- | --- | --- |
| 检查点主记录 | `goharness:checkpoint:{b64(会话 key)}` | hash | 会话 key | 配置的 TTL | 已有 |
| 消息日志 | `goharness:checkpoint:{b64(会话 key)}:msgs:<代次>` | list | 同上 | 同上 | 已有 |
| 检索文档 | `goharness:rag:<b64(命名空间)>:<id>` | hash | 无 | 无 | W3-2 |

### 4.7 吞吐与容量

- **并发数估算**：在途运行数约等于“每秒请求数乘以平均运行时长”（排队论的利特尔法则）。舱壁的 `MaxConcurrent` 据此设定，并留出余量。
- **Redis 写入量估算**：每次运行的检查点保存次数约为“节点执行数加 2”（初始、每个节点完成、结束；审批类中断额外同步保存一次）。ReAct 每多一轮工具调用大约多两次保存。这是量级估算，以 W0 实测为准。
- **热点只会出现在同一个会话**：不同会话的 key 分布在不同槽；同一会话的并发写由 CAS 和锁处理。
- **推荐默认配置**（在部署指南里给出，数值在 W0 后确定）：异步持久化（默认），审批类场景用同步；设置 `TTL` 与较小的 `MaxHistory`；限定 `LogCacheSize`。
- **需要一起调的旋钮**：舱壁 `MaxConcurrent`、工具 `MaxWorkers`（C1）、`httpclient.Pool` 的连接数（现状每主机空闲连接默认 20、每主机总连接数不限）、Redis 客户端连接池、`stream.Config.Buffer` 与 `SendTimeout`。部署指南用一张表列出它们的相互关系。

### 4.8 消息队列与事件回放（不实现，只写对接说明）

**消息队列**：框架不内置队列，也不绑定某一种队列。恢复语义是至少一次投递，加上检查点 CAS 与工具幂等，任何队列都能接。对接说明（W5-6）给出消费者的标准流程：

```text
取消息 → 校验租户并 tenant.With → 按应用选择的方式串行化同会话（锁、分区键或粘性路由）
      → 带幂等键调用 Invoke 或 Resume
      → 检查点已落盘后再确认消息
      → 失败时按次数重试，超过最大尝试次数进入死信，并记录指标
```

要点：
- **最大尝试次数加死信是必须的**：Agent 运行很贵，无限重试会烧掉大量模型费用。
- **同一会话的顺序**：Kafka 用会话 key 作分区键即可保证同会话有序，此时额外的锁成为可选项；RabbitMQ、NATS 与 Redis Streams 没有这种保证，靠应用选择的串行化手段（见 4.2）。
- **确认时机**：先落盘检查点，再确认消息；崩溃后重投会走 `Resume`，已完成的工具调用按调用身份复用。
- **排空**：停机时先停止拉取消息，再用 `Bulkhead.Drain` 让在途运行中断落盘，未确认的消息自然重投给其他副本。
- 使用 Redis Streams 时，崩溃消费者的消息用 `XAUTOCLAIM` 接管；它的持久性取决于 Redis 的 AOF 配置，主从异步复制下切换可能丢消息，要求更高持久性时用 Kafka 等。

**事件回放**：框架不内置。思路：应用在消费 `stream.Event` 的同时，把事件按 `stream.Meta.Sequence` 写入自己的存储（例如 Redis Streams，带上限与过期），SSE 断线重连时凭 `Last-Event-ID` 从中续传，重连可以落在任意副本。
### 4.9 `exit` 持久化模式（W4-7，条件项，旧 1.5 扩展）

**为什么可能需要**：每次运行的检查点保存次数约为节点执行数加 2，高并发下这是 Redis 写入量的主要来源。`Durability` 目前只有 `async` 与 `sync`（`pkg/graph/persistence.go`）。

**触发条件**：W0-4 证明保存写入量或脚本开销是瓶颈，并且 E2 的优化不足以解决。没有这个证据就不做。

**语义**：新增 `DurabilityExit`：运行期间不做逐节点保存，只在入口、中断、接受人工输入、完成与失败时保存（其中后四类本来就是同步写入）。进程崩溃后从最近一次保存的边界（通常是入口）重新开始，也就是**重放范围变大**，已完成的 LLM 调用和工具调用会重做。因此默认仍是 `async`；`exit` 只适合便宜、快速、幂等的图（例如入库流水线中的纯计算节点），不适合昂贵的 Agent 运行，文档写明。

**实现要点**：写入器对非终结性写入直接丢弃，不排队；中断路径不受影响，仍然可恢复；`agent.WithDurability` 同步接受新值。

**测试**：模拟崩溃后从入口重放；中断后可 `Resume`；契约清单 A 至 I 节中与逐节点保存无关的条款在 `exit` 模式下通过；依赖逐节点保存的条款（例如“已完成节点不重放”）明确标注不适用，并在文档里说明。

## 五、RAG 扩展

### 5.1 现状与缺口

`extensions/retrieval` 已经有：分块（带重叠的 Token 窗口，稳定的 chunk ID）、文档索引、混合检索（向量与关键词并行，RRF 或加权融合，可选 MMR 与重排）、带引用的上下文生成。这些组件通过 `runnable.Runnable` 接收四类外部能力：

| 契约 | 类型 |
| --- | --- |
| 嵌入 | `Runnable[EmbeddingRequest, EmbeddingResponse]` |
| 向量存储 | `Runnable[VectorRequest, VectorResponse]` |
| 关键词检索 | `Runnable[TextSearchRequest, []SearchHit]` |
| 重排 | `Runnable[RerankRequest, []RerankResult]` |

**这四类在仓库里一个实现都没有**，另外缺文档加载器、入库流水线、Agent 工具和评测。本节补齐这些，使“拿来就能做 RAG”。

### 5.2 整体设计

```text
入库：Source → 加载器 → 分块 → 批量嵌入（经限流）→ 向量库 upsert（按租户命名空间）
检索：查询 → [缓存] → 嵌入 → 向量检索 ∥ 关键词检索 → 融合 → 重排 → 引用文本与结构化引用
Agent：retrieval 工具（租户来自 ctx，模型不能指定）→ 工具结果带引用
```

### 5.3 嵌入客户端（`extensions/retrieval/embedding`，W3-1）

```go
func New(cfg Config) (runnable.Runnable[retrieval.EmbeddingRequest, retrieval.EmbeddingResponse], error)

type Config struct {
    Endpoint   string
    APIKey     string
    Model      string
    Dimensions int
    BatchSize  int                  // 单次请求的输入条数上限
    Pool       *httpclient.Pool     // 复用连接池
    Timeout    time.Duration
    Retry      llm.RetryConfig      // 复用 C2 的抖动与 Retry-After 语义
```

- 协议是 OpenAI 兼容的 `/embeddings`；自托管的推理服务通常兼容，不引入任何厂商 SDK。
- 超过 `BatchSize` 的请求自动切批，保持输入顺序；返回向量数与输入条数不一致时报错，不静默截断。
- 错误携带 `StatusCode()` 与 `RetryAfter()`，与 C2 配合。

**测试**：用 `httptest` 服务验证分批、顺序、重试、`Retry-After`、条数不一致、`ctx` 取消与超时。

### 5.4 Redis Search 适配器（`extensions/retrieval/redisstore`，W3-2）

一个后端同时实现向量存储和关键词检索，与会话共用同一套 Redis。需要带 Search 模块的 Redis（Redis Stack 或 Redis 8）。

```go
type Config struct {
    Client    redis.UniversalClient
    Index     string               // 索引名
    Prefix    string               // 文档 key 前缀
    Dim       int
    Distance  Distance             // Cosine、InnerProduct、L2
    HNSW      HNSWParams           // M、EFConstruction、EFRuntime，初始使用库默认值
    Metadata  []MetadataField      // 声明可过滤的字段及类型：Tag 或 Numeric
}

func New(cfg Config) (*Store, error)
func (s *Store) EnsureIndex(ctx context.Context) error // 幂等；已存在则校验维度与距离是否一致
func (s *Store) VectorStore() runnable.Runnable[retrieval.VectorRequest, retrieval.VectorResponse]
func (s *Store) KeywordSearch() runnable.Runnable[retrieval.TextSearchRequest, []retrieval.SearchHit]
```

设计要点：
- **文档结构**：每个 chunk 一个 hash，字段含 `ns`（命名空间，Tag）、`text`（全文）、`vec`（向量，HNSW）、已声明的元数据字段（Tag 或 Numeric）、其余元数据存为 JSON 字符串（只存不检索）。
- **租户隔离**：**每个查询都强制带 `@ns:{<转义后的命名空间>}` 前置过滤**，不是可选项；命名空间为空直接报错。
- **查询注入防护**：关键词查询里的用户文本必须转义 Search 查询语法的特殊字符，并有测试覆盖（含引号、括号、`|`、`-`、`@`）。
- **向量检索**：`KNN` 加前置过滤，使用方言 2 的参数化查询，向量以二进制传参。
- **删除**：按 ID 删除用 `UNLINK`；按命名空间删除先用 `FT.SEARCH` 分页取出 ID 再批量 `UNLINK`，不用 `KEYS`。
- **集群**：见 4.6 的说明，首版验证范围是单机与主从。
- 声明之外的元数据过滤返回明确错误，不静默忽略。

**测试**：miniredis 不支持 Search 命令（实现时再核对该限制），因此这个适配器只有两层测试：纯函数的查询构造与转义用单元测试；与真实 Redis Stack 的交互用环境变量 `GOHARNESS_TEST_REDIS_STACK_ADDR` 开关的集成测试，覆盖建索引幂等、upsert、KNN、关键词、元数据过滤、命名空间隔离（租户 A 的查询永远看不到租户 B）、删除、维度不一致。

**测试**：`httptest` 服务，覆盖字段映射、排序、空文档、超时与重试。

### 5.6 加载器与入库流水线（W3-3）

**加载器**（`extensions/retrieval/loader`）：

```go
type Source struct {
    Name string
    MIME string
    Body io.Reader
    Metadata retrieval.Metadata
}
// 每个加载器都是 runnable.Runnable[Source, []retrieval.Document]
func Text() ...; func Markdown() ...; func HTML() ...
```

- Markdown 按标题层级切分并把标题路径放入元数据；HTML 去除脚本与样式并取正文（使用 `golang.org/x/net/html`，新依赖，只加在扩展里）。
- **只接收字节流，不在框架里抓取 URL**，避免 SSRF。需要抓取的应用在自己的网关里完成。
- PDF、Office 等不内置，使用者提供自己的加载器，或使用旁路的文本抽取服务，把结果以 `Source` 交进来。

**入库流水线**（`retrieval.NewIngestor`）：

```text
加载 → 分块 → [按嵌入批次动态分派：嵌入 → upsert] → 清理旧版本分块
```

- **幂等**：chunk ID 是稳定的（已有）；文档带 `ID` 与内容哈希形成的版本；重复入库同一版本不产生副作用。
- **更新**：先写入新版本分块，再删除同一文档中版本不是当前版本的旧分块。两步之间新旧并存，不会出现“检索不到”的空窗。
- **可恢复**：流水线是一次图运行，嵌入与 upsert 用动态分派（`Send`）按批次分成成员，每批一个成员；开启检查点后，中途失败恢复时已完成的批次直接复用结果，**不会重复调用嵌入服务**，这是用图引擎做入库的直接收益。会话 key 用 `t/<租户>/ingest/<文档 ID>`。
- **限流**：嵌入客户端接应用注入的限流器（`Limiter`），批量入库不会打满共享的嵌入配额。
- 队列驱动的异步入库由应用的队列消费者调用入库流水线，见 4.8 的消费者流程。

**测试**：幂等（重复入库计数不变）；更新后旧版本被清理；中途让第 N 批失败，恢复后只重做未完成的批次（嵌入调用计数验证）；空文档与超长文档。

### 5.7 Agent 工具与引用（W3-4）

```go
type SearchArgs struct {
    Query string `json:"query" jsonschema:"检索问题"`
    TopK  int    `json:"top_k,omitempty"`
}

func NewTool(retriever Retriever, cfg ToolConfig) tool.Tool // 基于 tool.New[SearchArgs]，标记只读
```

- **租户来自 `ctx`，不在工具参数里**：模型不能指定要查哪个租户。
- 返回内容：带编号的引用文本，加一个 `schema.NewOpaqueBlock("retrieval.citations", ...)` 携带结构化引用（文档 ID、chunk ID、分数、来源元数据），前端可以据此渲染来源。
- 总长度受 `ReferenceRequest.MaxTokens` 约束（现有能力）。
- 空结果返回明确的“没有找到相关内容”，不让模型自行编造。

### 5.8 租户安全检索（W3-6）

`retrieval.Scoped(searcher, ...)`：每次调用把 `Namespace` 设为作用域里的租户（`tenant.FromContext`）；调用方显式传入其他命名空间时返回 `ErrTenantMismatch`；同时把检索缓存的租户（`cache/retrieval` 的 `WithVectorCacheTenant`）设为同一个值，避免缓存与存储使用不同的租户来源。

**测试**：租户 A 的查询无法返回租户 B 的数据（含缓存命中路径）；显式传入他人命名空间被拒绝。

### 5.9 评测（`extensions/retrieval/eval`，W3-7）

```go
type Case struct{ Query string; Relevant []string }
type Report struct {
    RecallAtK map[int]float64
    MRR       float64
    NDCGAtK   map[int]float64
    LatencyP50, LatencyP95 time.Duration
}
func Run(ctx context.Context, s Searcher, cases []Case, ks []int) (Report, error)
```

- 仓库内带一份小的固定数据集与确定性的假嵌入器（基于文本哈希），评测可以离线、无外部依赖地跑，作为检索算法回归的门槛：指标低于已保存的基线报告即失败。
- 真实模型下的评测由使用者用自己的数据集运行同一个函数。

### 5.10 其他向量库（不实现，只写对接说明）

内置的只有 Redis Search 适配器。其他后端按第 5.1 的四个接口自行实现，对接说明（W5-6）给出要点，以 pgvector 为例：

- 表 `chunks(ns text, id text, text text, tsv tsvector, embedding vector(<dim>), metadata jsonb, primary key (ns, id))`；向量列建 HNSW 索引；关键词检索用 `websearch_to_tsquery` 的参数化查询，天然避免注入；**每个查询都带 `ns = $1` 条件**，与 Redis Search 适配器的租户隔离要求一致。
- 通用要点：命名空间必填；关键词查询的用户文本必须转义或参数化；upsert 按稳定的 chunk ID 幂等；删除支持按 ID 与按命名空间；维度与距离度量在建索引时校验。
- 不内置的原因：它需要引入 `pgx` 与另一套集成测试环境，而实现它不需要框架内部语义，放在应用侧或独立仓库更合适。

### 5.11 选择哪个后端

| 情况 | 建议 |
| --- | --- |
| 已经用 Redis 做会话，想少运维一个系统 | 内置的 Redis Search 适配器 |
| 后端以 Postgres 为主，要事务、备份、审计一体 | 按第 5.1 的接口自己写 pgvector 适配器，参考 5.10 的要点 |
| 数据量与召回要求超出以上 | 同样按四个接口自己实现（Qdrant、Milvus 等） |

## 九、补充工作项（旧审查报告遗留项与多 Agent 协作）

### 9.1 MCP 信任策略（W2-7，旧 3.5）

**现状与威胁**（`extensions/mcp/mcp.go`）：
1. `ReadOnlyHint` 被直接信任并成为 `IsReadOnly`（345 行），而只读工具允许自动重试；远端谎报只读会让有副作用的调用被重复执行。
2. 工具 `description` 原样进入提示（351 行），远端可以借此注入指令（工具投毒）。
3. stdio 的命令、参数、环境变量（117 行）和 HTTP、SSE 的端点没有任何约束。端点或命令若来自用户输入，就是 SSRF，命令来自用户则是任意命令执行。

**改动**：

```go
type Policy struct {
    ReadOnly             func(name string, remote *mcp.ToolAnnotations) bool // 默认：忽略远端注解，一律非只读
    AllowedTools         []string // 非空时只暴露这些工具
    DeniedTools          []string // 优先于 AllowedTools
    MaxDescription       int      // 初始值 1024 字节，按字符边界截断
    NamePrefix           string   // 给暴露的工具名加前缀，避免与本地工具重名
    AllowedHosts         []string // HTTP、SSE 端点的主机白名单（精确或 *.后缀）
    BlockPrivateNetworks bool     // 拨号时检查解析后的地址，拒绝回环、私网、链路本地
    AllowedCommands      []string // stdio 可执行文件白名单（绝对路径）
    AllowedEnvKeys       []string // stdio 允许传入的环境变量名
    Strict               bool     // 为真时，端点或命令对应的白名单缺失则 NewClient 报错
}
```

- **零值策略不需要配置**：忽略远端只读注解；描述去除控制字符并截断；其余不限制。现有接入不受影响。
- **端点或命令来自用户输入时必须用 `Strict`**，并设置 `AllowedHosts` 加 `BlockPrivateNetworks`（HTTP、SSE）或 `AllowedCommands`（stdio）。文档与参考服务明确这一点。
- `BlockPrivateNetworks` 在拨号时对解析后的 IP 检查（自定义 `DialContext` 的 `Control` 钩子），避免 DNS 重绑定绕过；因此该客户端使用独立的 `httpclient.Pool`，不与共享池混用。
- 应用想让某些远端工具允许重试时，用 `ReadOnly` 回调按工具名给出判断。

**测试**：
- 远端声称只读的工具默认 `IsReadOnly` 为假，失败后不自动重试；`ReadOnly` 回调返回真才允许重试。
- 描述含控制字符、超长时被清理与截断；`AllowedTools`、`DeniedTools`、`NamePrefix` 生效。
- `AllowedHosts` 拒绝未列出的主机；`BlockPrivateNetworks` 拒绝解析到 `127.0.0.1`、`10.x`、`169.254.x` 的端点（用 `httptest` 与自定义解析器）。
- stdio 命令不在白名单时报错；`Strict` 且白名单缺失时 `NewClient` 报错。

### 9.2 图可视化（W2-8，旧 4.13）

`graph.Snapshot` 已有 `Nodes` 与 `Edges`（边带 `Conditional` 与标签）。新增 `Snapshot.Mermaid()` 与 `Snapshot.DOT()`。

- 节点按 `NodeKind` 区分形状（模型、工具、子图、普通节点）；条件边用虚线并带标签；入口与出口用专门的节点。
- 节点 ID 与标签里的特殊字符按 Mermaid 与 DOT 各自的规则转义，避免产生语法错误或被注入的图。
- **先核对**：当前 `Snapshot.Edges` 是否包含单次求值路由的目标、`Fork/Join` 与动态分派的边；缺失则先补进去（标为条件边），否则图会漏边。

**测试**：ReAct 图、含路由的图、Fork/Join 图、动态分派图的 Mermaid 与 DOT 输出做黄金文件比对；特殊字符 ID 的转义；`Snapshot` 含路由与分派边的单测。

### 9.3 多 Agent 协作（W2-9、W4-8）

**总原则**：不造“多 Agent 运行时”。按优先级提供模式：**静态工作流 优先于 Agent 当工具，优先于 handoff，优先于跨进程（A2A）**。前两种用现有积木已经能搭，本节只补几处小东西，其余写进指南（W5-7）。

**与 Eino ADK 的对照**（Eino 一侧来自其官方文档；没有查到的项标注“未查到”）：

| 能力 | Eino ADK | goHarness 现状 | 处理 |

**MA-1 `subagent.AsTool`：把一个固定的专家 Agent 包装成具名工具**
```go
func AsTool(a agent.Agent, name, description string, opts ...AsToolOption) tool.Tool
```
- 基于 `tool.New`：输入是 `{"task": string}`，也可用 `WithInputSchema` 换成自定义结构；调用时在工具内 `a.Invoke`，输出取最后一条回答的文本。
- **默认只把任务描述交给专家**，不继承父 Agent 的历史，也不泄露父的系统提示和其他工具的输出；需要历史时用 `WithHistory(filter)` 显式传入过滤后的消息。
- 嵌套运行按调用身份成为子执行，嵌套审批、已完成结果复用、检查点命名空间都沿用现有语义，不需要新机制。
- 与通用的 `run_subagent` 并存：固定专家用 `AsTool`，需要让模型按注册表动态选角色时用通用工具。
- **测试**：用脚本化模型的管理者调用两个专家；专家只收到任务描述；专家内审批挂起后恢复，已完成的兄弟不重跑；租户属性出现在专家的事件里。

**MA-2 上下文过滤函数**：放在 `extensions/subagent`，都是纯函数，既给 `AsTool` 的 `WithHistory` 用，也可以直接用在图的 Pre 处理器里。
- `LastN(n)`、`DropToolResults()`、`DropSystem()`、`UserAndFinal()`（只保留用户消息与最终回答）。
- 这是多 Agent 最常见的出错点：传太多导致上下文膨胀，传太少导致专家缺背景，把父的系统提示或其他工具的输出泄露给专家。
- **测试**：每个函数对含工具调用与工具结果的消息序列保持调用与结果成对，不产生孤立的工具结果。

**MA-3 子 Agent 单任务限制**：`subagent.Config` 增加 `TaskTimeout` 与 `MaxLLMCalls`（按单次任务计）。超出时返回模型可修正的错误结果，而不是被静默截断。子 Agent 是工具调用，仍受工具运行时的超时约束（默认 30 秒，配置上限 5 分钟），超出的长任务应整次放到后台，见对接说明。
- **测试**：超时与调用上限各一例；返回的错误结果对模型可读；限制不影响正常任务。

**MA-4 事件里的 Agent 归属与子 Agent 事件透传**：先在 W0-5 核对观测事件是否带 Agent 名称、公共事件流是否透传子 Agent 的事件。缺了名称就补进事件属性（`agent`），W2-1 的指标标签依赖它；透传默认关闭，需要时提供开关（参考 Eino 的 `EmitInternalEvents`：透传事件只用于展示，不影响父 Agent 的状态与检查点，只有中断跨边界传播）。

**MA-5 终止型工具（W4-8，条件项）**
- `agent.WithReturnDirectly(names ...string)`：本轮批里命中的工具完成后，ReAct 循环不再调用模型，这次工具结果作为最终输出；多个同时命中时取批内顺序靠前的一个。
- 用法一：给专家一个 `transfer_to_xxx` 工具，工具结果带结构化的移交标记，外层图用**预先声明目标**的条件边读取标记并路由，保持编译期校验，不引回 `Command`。
- 用法二：“工具结果即最终答案”，省掉一次多余的模型调用。
- **测试**：命中后不再调用模型；多个同时命中的取舍；未命中时行为不变；与审批中断、检查点恢复组合时恢复后仍按终止型处理。

**护栏（写进指南，多数已有）**：嵌套深度上限（工具运行时默认 16）；图的最大步数；群聊的最大轮数；整次请求的总预算由应用用 Observer 累计，超限用 `context.WithCancelCause` 加 `control.RequestInterrupt` 中止；路由目标预先声明；子 Agent 继承父的租户与主体。

**不做**：Agent 注册表与发现、消息总线、预置 supervisor 或 swarm 库、`TurnLoop` 式多轮运行时、共享长期记忆、后台异步子 Agent。

### 9.4 声明式（YAML）Agent：留给应用，框架提供接入点（W1-11、W5-8）

**结论**：加载 YAML、校验字段、按租户放行组件、热更新都由应用负责，框架**不做** `extensions/agentspec` 这样的加载器，也不引入 YAML 依赖。原因：它不需要框架内部语义，应用自己解析后调用 `agent.New(model, opts...)` 就行；做成框架功能，很快会长成一门描述流程的 DSL。

**框架提供的接入点**：
- `agent.New` 的 Option（系统提示、工具、调用次数、重试、超时、深度、并发等都已有对应 Option，且对取值范围有硬上限校验，作为最后一道保险）。
- `subagent.AsTool`（W2-9）：YAML 里的“把 researcher 当工具给 coordinator”落到这个入口。
- `agent.WithDefinitionVersion`（C7，W1-11）：配置变更后挂起的运行拒绝恢复，不静默漂移。
- MCP 信任策略与 `Strict`（W2-7）：YAML 引用 MCP 服务时使用。
- `tool.Subject` 的权限检查：工具的最终授权，YAML 里写了不等于能用。

**示例（W5-8，`extensions/examples/yamlagent`，约百行）**：演示 YAML 解析成结构体，按名字查已注册的模型与工具，映射成 `agent.WithTools`、`WithMaxLLMCalls`、`WithToolRetries` 等 Option，`agents:` 引用映射成 `AsTool`，并把定义的哈希或版本号写入 `WithDefinitionVersion`。示例的 YAML 库只出现在示例 module，不进入框架。

**不可信输入清单（用户可以上传 YAML 时必须做）**：
1. 引用只能来自服务端按租户放行的工具和模型，未放行的名字一律报错并指出 YAML 路径。
2. `limits` 类参数在应用侧先封顶，再传给 Option；框架的硬上限只是兜底。
3. 限制指令长度，拒绝未知字段，限制 `agents:` 的嵌套深度并检测循环引用。
4. 密钥不进 YAML：模型和工具的凭据由应用在注册时提供，YAML 只写名字。
5. 引用 MCP 时使用 `Strict`，并设置主机、命令白名单。
6. 工具调用仍由 `tool.Subject` 的权限检查把关。
7. 每个定义带版本，写入 `WithDefinitionVersion`；会话固定在创建时的版本上。

**应用自己负责**：YAML 解析与字段校验、按租户的注册表与策略、定义的存储与版本管理、热更新、上传审核。

### 9.5 媒体解析与保护（W2-10）

C8 只解决“图片块能编码发送”。媒体从哪里来、能不能读、多大，需要一道策略，放在 `extensions/media`：

```go
type ResolverConfig struct {
    AllowedSchemes       []string // 例如 https、file
    AllowedHosts         []string // http(s) 的主机白名单（精确或 *.后缀）
    FileRoots            []string // file 只允许这些根目录，防路径穿越
    MaxBytes             int64    // 单个媒体的字节上限
    AllowedMIME          []string
    BlockPrivateNetworks bool     // 拨号时拦截回环、私网、链路本地
    Pool                 *httpclient.Pool
}

func NewResolver(cfg ResolverConfig) *Resolver
// 发送前解析消息里的媒体块，把本地或远端 URI 换成内联 data URI；结果只用于本次请求
func (r *Resolver) WrapModel(m llm.ChatModel) llm.ChatModel
// 检查点里内联的媒体数据超过阈值时拒绝保存
func NewStoreGuard(inner state.Store, maxInlineBytes int) state.Store
```

- **只用于本次请求，不写回**：解析出的字节只进请求体，消息和检查点里保留 URI 引用；这样不会撑大 Redis，也不会把大媒体复制到每个检查点版本。
- **不抓取模型自己编出来的 URL**：除非命中白名单；这是防 SSRF 与数据外泄的底线，实现与 W2-7 的私网拦截共用同一套拨号检查。
- **校验 MIME 与内容**：声明的 MIME 与内容嗅探结果不一致时拒绝。
- **`NewStoreGuard`** 是 `state.Store` 装饰器，超过阈值返回明确错误；同样要透传 `state.RollbackBasisReader`。
- **观测**：事件和日志不含媒体字节（默认不含载荷已成立），只记大小与 MIME。

**测试**：非白名单协议与主机被拒绝；解析到私网地址被拒绝；超过字节上限被拒绝；路径穿越被拒绝；MIME 与内容不符被拒绝；解析结果不出现在回传的消息和检查点里；`NewStoreGuard` 拒绝超限的检查点并透传可选接口。

### 9.6 决策模型集成（实验，W4-9）

**背景（据 2026 年 10 月的报道与文档，未逐一核对）**：2026 年 9 月 15 日发布的 Jev（TypeSafe AI）是“System One”类决策模型：输入一个状态和一组带类型的问题，**不生成文本**，只返回概率。问题有三种：`Choice`（从选项里选一个，返回概率分布与置信度）、`Score`（按有序分级打分）、`Noul`（某个命题成立的概率）。一次调用并行答完所有问题，延迟在几十到几百毫秒，输出免费。同类产品还有 Cloudflare 的 Clef、Amazon 的 Strands Decider、OpenAI 的 decisions 接口，接口形状在收敛但仍可能变化。已知局限：不擅长计数、算术、日期比较；状态里的提示注入会生效；对指令按字面理解。

**为什么与我们的图契合**：我们的条件边要求目标预先声明、路由函数每次只求值一次。过去路由要么是写死的规则，要么调一次完整的大模型，又慢又贵。决策模型给出快、便宜、带概率的判断，而且**目标预先声明、编译期校验的好处完全保留**。

| 图里的位置 | 问题类型 | 做法 |
| --- | --- | --- |
| 条件边路由 | Choice | 在预先声明的目标里选一个；置信度低于阈值走兜底节点（完整 LLM 或人工） |
| 条件判断 | Noul | 得到 P(true)，用阈值变成布尔 |
| 评估者与优化者循环 | Score | 判断草稿够不够好，替代每轮一次大模型打分 |
| 工具调用前筛查 | Noul | `tool.Middleware`：对有副作用的工具问“这次调用符合用户意图吗”，低于阈值触发 `Interrupt` 走人工审批 |
| RAG | Noul、Score | 检索结果相关吗、答案有没有被上下文支持，决定是否重新检索 |
| 多 Agent | Choice | 主管选专家，省掉一次大模型调用 |

**设计（草案）**：`extensions/decision`，接口保持厂商中立，与检索的四个接口同一风格。

```go
type Request struct {
    Model     string
    State     any                  // 字符串或可序列化的结构
    Questions map[string]Question  // 键是问题 ID
}

type Answer struct {
    Choice        string             // Choice：选中的选项
    Probabilities map[string]float64 // Choice：各选项的概率
    Score         float64            // Score：概率加权后的位置
    PTrue         float64            // Noul：命题成立的概率
    Confidence    float64
}

type Response struct{ Answers map[string]Answer }

type Model = runnable.Runnable[Request, Response]
```

- **决策节点而不是新边类型**：`decision.Node` 调用模型，把带类型的结果写进 State；后面的条件边用普通谓词读阈值。辅助函数 `decision.Route(answer, minConfidence, targets, fallback)` 在置信度不足时返回兜底目标，兜底目标同样要预先声明。这与厂商文档建议的“把判断组合进代码”一致，也不引入新机制。
- **工具筛查中间件**：`decision.ToolGuard(model, policy)` 只对声明为有副作用的工具询问，低于阈值调用 `graph.Interrupt` 转人工审批；高于阈值直接放行。
- **观测**：决策事件带问题 ID、选中项、概率与置信度，便于离线用线上轨迹校准阈值。事件种类优先用扩展自己定义的值（若 `observe.Kind` 不允许扩展，则退回 `KindLLM` 加 `decision` 属性），不改核心，实现时核对。
- **适配器**：先做一个 HTTP 适配器；并提供脚本化的假实现用于测试和示例，不依赖任何厂商。

**红线（写进文档）**：
1. 决策是建议，不是授权；高风险动作仍需审批，不能因为概率高就跳过。
2. 它不是安全边界：不要把不可信内容原样放进状态，状态里的提示注入会生效。
3. 计数、算术、日期比较留给代码。
4. 阈值要用有代表性的用例校准，并锁定具体的模型版本。

**测试**：用脚本化的假模型验证：按阈值路由、低置信度走兜底、`Noul` 阈值边界、工具筛查低于阈值时触发中断且审批后可恢复、高于阈值时放行；决策事件含概率与置信度；目标仍受编译期校验，路由到未声明的节点编译失败。

**为什么是实验项**：这个类别才出现不到一个月，接口可能变化，因此只做实验性扩展，不绑定厂商，不改核心。转正条件：同类产品的接口形状在至少两家之间稳定，并且有真实的路由或工具筛查需求。
