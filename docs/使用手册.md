# goHarness 使用手册

本手册面向希望快速构建 Agent 的 Go 工程师。goHarness 的核心不是应用注册器，
而是一个以强类型 Graph 为中心的 LLM 编排框架：ChatModel、ToolNode、MCP、
Context Engine 和 Agent 都遵循统一的 Runnable 契约，可以按需组合成业务图。

## 可用性结论

核心编排能力已经具备受控生产使用条件：强类型 Graph、ChatModel、ToolNode、MCP
工具适配、Basic/ReAct/Routing/GroupChat 预置图配方、工具运行时、Middleware、
同步 Callback、OpenAI-compatible 模型、Graph Continuation/Resume 和 Context Engine 都有
明确的执行契约及自动化测试覆盖。

可选扩展不能仅凭核心模块测试直接启用。Cache 应按实际 Provider 参数、
`runnable.Option`、租户隔离和失效策略评估缓存键语义；Redis Checkpoint、MCP 与远程
存储应在目标网络、凭据和失败策略下完成集成测试，再用于生产流量。

## 环境准备

- Go 1.24 或更高版本。
- 使用任一 OpenAI-compatible 服务时，准备模型地址、模型名与 API Key。
- Windows 上运行竞态检测时，安装 MinGW-w64 GCC，并将其 `bin` 目录加入 `PATH`。

```powershell

$env:Path = 'D:\Program Files\msys64\ucrt64\bin;' + $env:Path
$env:CGO_ENABLED = '1'
go test -race -count=1 ./...
```

可先运行内置示例：

```powershell
go run ./examples/basic
go run ./examples/graph
```

## 核心抽象与数据流

所有可执行组件都实现 `runnable.Runnable[I, O]`：

```go
type Runnable[I, O any] interface {
    Invoke(context.Context, I, ...runnable.Option) (O, error)
    Stream(context.Context, I, ...runnable.Option) (*runnable.StreamReader[O], error)
    Collect(context.Context, *runnable.StreamReader[I], ...runnable.Option) (O, error)
    Transform(context.Context, *runnable.StreamReader[I], ...runnable.Option) (*runnable.StreamReader[O], error)
}
```

组件通常只需要实现最自然的一种执行形式，再通过 `runnable.Adapt` 或 Lambda 构造器补齐
其余形式。`StreamReader` 是带背压和取消传播的数据通道；实时观测数据使用 Context 中的
`callback.StreamCallbackOf[T]`，不与最终业务输出混在一起。

框架从底到上的分层是：

| 层级 | 职责 |
| --- | --- |
| Runnable | 统一 ChatModel、ToolNode、Retriever、Agent 和 Graph 的调用契约 |
| ChatModel / Tool / MCP | 提供可复用的模型与工具节点能力 |
| Graph | 定义节点、边、条件、循环、并行和强类型状态流动 |
| Agent | 提供基于 Graph 的 Basic、ReAct、Routing、GroupChat 快捷配方 |
| App / Gateway | 由应用自行注册多个 Runnable、选择路由并管理 HTTP 或任务入口 |

一次典型的工具 Agent 图如下：

```text
[]schema.Message
        |
        v
Context Engine -> ChatModel (llm.ChatModel)
                       |
             assistant tool-call messages
                       v
                 ToolNode (tool.ToolsNode)
                       |
             ordered function-result messages
                       +------> ChatModel (next turn)
```

- `llm.ChatModel` 是 provider-neutral 的模型契约，输入 `llm.Request`，输出
  完整 `llm.Response`。实时模型增量通过 Context EventStream 发布。
- `tool.ToolsNode` 只执行消息末尾连续的 assistant function calls，返回有序的
  tool-result 消息；它本身也是一个 `Runnable[[]schema.Message, []schema.Message]`。
- `extensions/mcp` 将 MCP `tools/list` 和 `tools/call` 适配成 `tool.Tool` 与
  动态 `ToolsNode`，因此 MCP 工具和本地工具可以进入同一张图。
- `graph.Graph[I, O]` 负责节点、边、条件、并行和运行步数。业务 `*State` 是每次运行
  独占的 Context 状态，通过 Pre/Post Handler 与纯节点衔接。

Agent API 是这套图编排能力的快捷装配层。`agent.New` 在有工具时自动组装有界的
`ChatModel -> tools -> ChatModel` ReAct 图。Agent 与公开的 `tool.ToolsNode` 共用
`tool.Runtime`，统一获得 Middleware、鉴权、超时、只读重试、递归保护和并发组调度；
自定义 Graph 与 MCP 动态节点不会进入另一套工具执行路径。

## 五分钟接入

最快的方式是使用 Agent 快捷装配层。下面的代码创建 ChatModel 和一个工具，框架会
自动把它们装配成 ReAct 图，然后直接调用 Agent。应用层只需持有 Agent 或
`map[string]agent.Agent`，不需要框架注册器。

```go
package main

import (
    "context"
    "log"
    "os"

    "goharness/pkg/agent"
    "goharness/pkg/llm"
    "goharness/pkg/schema"
    "goharness/pkg/tool"
)

func main() {
    model, err := llm.New(llm.Config{
        ModelType:   "openai-compatible",
        Model:       "your-model",
        ModelServer: "https://provider.example.com/v1",
        APIKey:      os.Getenv("LLM_API_KEY"),
    })
    if err != nil {
        log.Fatal(err)
    }

    echo := tool.NewFunctionTool(tool.Spec{
        Name:        "echo",
        Description: "返回 text 参数。",
        Parameters: map[string]any{
            "type": "object",
            "properties": map[string]any{
                "text": map[string]any{"type": "string"},
            },
            "required": []string{"text"},
        },
    }, func(ctx context.Context, input tool.CallInput) (tool.Result, error) {
        return tool.TextResult(input.Args["text"].(string)), nil
    })

    assistant, err := agent.New(agent.BaseConfig{
        Name:          "assistant",
        SystemMessage: "You are a helpful assistant.",
        Model:         model,
        Tools:         []tool.Tool{echo},
        MaxLLMCalls:   4,
    })
    if err != nil {
        log.Fatal(err)
    }

    output, err := assistant.Invoke(context.Background(), []schema.Message{
        schema.NewMessage(schema.RoleUser, schema.NewTextBlock("请调用 echo 工具返回 hello。")),
    })
    if err != nil {
        log.Fatal(err)
    }
    for _, message := range output {
        log.Printf("%s: %s", message.Role, message.JoinedText(""))
    }
}
```

`agent.New` 会按配置自动选择图配方：未配置工具时创建 Basic Agent；配置
`Tools` 后创建 ReAct Agent。需要显式表达配方时，使用
`agent.NewBasicAgent`、`agent.NewReactAgent`、`agent.NewRoutingAgent` 或
`agent.NewGroupChat`。

如果应用需要注册多个可命名 Agent，使用普通 Go map，并在 HTTP、RPC 或任务入口按名称路由：

```go
agents := map[string]agent.Agent{
    "assistant":  assistant,
    "researcher": researcher,
}
selected, ok := agents[agentName]
if !ok {
    return fmt.Errorf("unknown agent %q", agentName)
}
reply, err := selected.Invoke(ctx, messages)
```

注册、鉴权、限流和多副本调度属于应用层；框架只负责 Runnable、Graph 和 Agent 执行。

## ChatModel：模型节点

`llm.ChatModel` 就是框架的模型契约。它同时实现：

```go
runnable.Runnable[llm.Request, llm.Response]
```

因此模型既能交给 Agent 快捷装配，也能作为普通 Runnable 使用。接入自定义 Graph 时，
使用 `llm.NewChatModelNode(model)` 包装 provider 模型；该公开节点负责 ChatModel
Start/End/Error 生命周期，并让 Graph 快照与 Callback 将其识别为 `chat_model`。直接调用
模型时，消息、工具定义和生成参数都通过 provider-neutral 的 `llm.Request` 传入：

```go
response, err := model.Invoke(ctx, llm.Request{
    Messages: []schema.Message{schema.NewMessage(schema.RoleUser, schema.NewTextBlock("查询订单状态"))},
    Options: llm.ChatOptions{
        Functions:   toolsNode.Definitions(),
        DeltaStream: false,
    },
})
```

Provider 只负责把不同厂商的协议转换成统一的 Message、ContentBlocks、Usage 和 Response；
Agent 图不依赖 OpenAI、DeepSeek 或 Qwen 的私有响应结构。

### ChatModel 流生命周期

`Model.Stream` 返回 `*runnable.StreamReader[llm.Response]`，Reader 只发送一次完整 Response。
Provider 收到完整上游终止标记后才提交该结果；SSE 提前关闭、Reader 没有产生结果或响应
无法完整归约时返回 `llm.ErrStreamTruncated`，不能提交部分响应。

模型增量不进入 Reader，而是同步发布到 Context EventStream：

```go
ctx = callback.WithStreamCallbacks(ctx,
    callback.StreamCallbackOf[llm.Response]("ui", func(
        ctx context.Context, partial llm.Response,
    ) error {
        return renderPartialResponse(ctx, partial)
    }),
)

reader, err := model.Stream(ctx, request)
response, err := llm.CollectResponse(ctx, reader)
```

Retry 只会重试首个实时增量产生前的可重试错误或静默截断；增量产生后失败会直接返回，
避免重复文本、工具调用或计费。调用 `reader.Close()` 会取消上游 SSE/模型生产协程。缓存只
保存完整 Response，不缓存或重放实时增量。

### 创建 ChatModel

内置 Provider 注册项如下：

| `ModelType` | 默认适配 |
| --- | --- |
| `openai-compatible`、`openai` | 通用 OpenAI-compatible 服务，需按服务填写 `ModelServer` |
| `deepseek` | DeepSeek OpenAI-compatible API |
| `dashscope`、`qwen` | DashScope/Qwen OpenAI-compatible API |

DeepSeek 示例：

```go
model, err := llm.New(llm.Config{
    ModelType: "deepseek",
    Model:     "deepseek-chat",
    APIKey:    os.Getenv("DEEPSEEK_API_KEY"),
})
```

不要将 API Key 写入 `callback.Event`、Checkpoint、日志或 Graph State。若服务端
需要自定义连接池，可在 `llm.Config.HTTPClient` 中传入已配置的 `*http.Client`。

## Tool 与 ToolsNode

工具由 `tool.Spec` 描述，并用 `tool.NewFunctionTool` 包装函数。参数必须是 JSON
Object；空参数会规范化为 `{}`，数组、`null` 和不完整 JSON 会被拒绝。

```go
echo := tool.NewFunctionTool(tool.Spec{
    Name:        "echo",
    Description: "返回 text 参数。",
    Parameters: map[string]any{
        "type": "object",
        "properties": map[string]any{
            "text": map[string]any{"type": "string"},
        },
        "required": []string{"text"},
    },
    IsReadOnly: true,
}, func(ctx context.Context, input tool.CallInput) (tool.Result, error) {
    return tool.TextResult(input.Args["text"].(string)), nil
})

toolsNode, err := tool.NewToolsNode(tool.ToolNodeConfig{
    Name:           "tools",
    Tools:          []tool.Tool{echo},
    MaxConcurrency: 4,
})
```

`ToolsNode` 的输入是完整消息历史，但只执行末尾连续的 assistant function-call 消息，
不会重放历史工具调用；输出是与调用顺序一致的 function-result 消息。调用方把结果追加到
历史，再进入下一个 ChatModel 节点：

```go
toolResults, err := toolsNode.Invoke(ctx, messages)
if err != nil {
    return err
}
messages = append(messages, toolResults...)
```

这是底层节点契约。多数业务不必手写循环，把相同的工具交给 `agent.New` 即可让框架自动
生成 `llm -> tools -> llm` 图：

```go
assistant, err := agent.New(agent.BaseConfig{
    Name:        "tool-assistant",
    Model:       model,
    Tools:       []tool.Tool{echo},
    MaxLLMCalls: 8,
})
```

`tool.Spec.Concurrency` 控制工具批次和 `ToolsNode` 的并发策略。未声明策略的工具
默认串行，避免把有副作用的操作无意并行化。对外部写操作应保持
`IsReadOnly: false`，并只在已验证幂等性和权限边界后配置重试。

### Middleware 与身份

Middleware 是业务控制层，可以授权、拒绝或转换输入输出；Callback 只能观测，
不能用于鉴权。将经过认证的身份放入运行时 Context：

```go
ctx := tool.WithSubject(context.Background(), tool.Subject{
    ID:          "user-42",
    TenantID:    "tenant-a",
    Permissions: []tool.Permission{"tools:write"},
})
```

在 Middleware 中使用 `tool.RequireSubject(ctx)`，并按 `Spec.IsReadOnly`、角色或
权限判断是否调用 `next`。不要把用户身份塞入 Tool 参数或模型 Prompt。

## MCP：把远程工具接入同一张图

MCP 位于独立的 `goharness/extensions` module。它负责连接 stdio、SSE 或 streamable
HTTP Server，将 `tools/list` 转换成 `tool.Tool`，将 `tools/call` 转换成
`tool.Result`。上层图看到的仍然是标准 Tool 和 Runnable，不需要理解 MCP 协议细节。

### 快速装配进 Agent

```go
client, err := mcp.NewClient(mcp.Config{
    Transport: mcp.TransportStreamableHTTP,
    Endpoint:  "https://example.com/mcp",
})
if err != nil {
    return err
}
defer client.Close()

mcpTools, err := client.Tools(ctx)
if err != nil {
    return err
}

assistant, err := agent.New(agent.BaseConfig{
    Name:  "mcp-assistant",
    Model: model,
    Tools: mcpTools,
})
```

`agent.New` 会把 MCP 工具和本地工具按相同的 `tool.Tool` 契约装入 ReAct 图。

### 作为动态 ToolsNode 编入自定义图

```go
mcpNode, err := client.NewToolsNode(ctx, tool.ToolNodeConfig{
    Name:           "mcp-tools",
    MaxConcurrency: 8,
})
```

`mcpNode` 实现 `runnable.NamedRunnable[[]schema.Message, []schema.Message]`。MCP Server
发送 `notifications/tools/list_changed` 后，该节点会在下一次调用前刷新工具 schema 和
路由表。它可以直接通过 `g.AddNode` 接入自定义图，Pre/Post Handler 负责读取和更新
业务 State，MCP 节点本身不需要知道 State 类型。

独立 `ToolsNode` 与 Agent 共用公开的 `tool.Runtime`。两条路径都执行 Middleware、
节点级并发限制、`Spec.Concurrency` 并发组、超时、只读重试、递归深度和 panic 隔离。
自定义拓扑可直接配置 `ToolNodeConfig.Middlewares`，无需自行补一套策略节点。

## 用底层节点显式构建 Agent 图

当预置 ReAct 配方不能表达业务流程时，可以直接把 ChatModel 和 ToolsNode 作为纯
Runnable 放进 Graph。Graph 只声明公开边界 `[I, O]`；每次运行的 `*AgentState` 由
State Factory 创建，Pre/Post Handler 负责节点与 State 之间的映射：

```go
type AgentState struct {
    Messages     []schema.Message
    Output       []schema.Message
    HasToolCalls bool
}

g := graph.NewGraph[[]schema.Message, []schema.Message]("custom-agent")
modelNode, err := llm.NewChatModelNode(model)
if err != nil {
    return err
}
if err := g.SetStateFactory(func(
    _ context.Context, input []schema.Message,
) (*AgentState, error) {
    return &AgentState{Messages: schema.CloneMessages(input)}, nil
}); err != nil {
    return err
}

if err := g.AddNode("chat", modelNode,
    graph.WithPreHandler(func(
        _ context.Context, state *AgentState,
    ) (llm.Request, error) {
        return llm.Request{
            Messages: schema.CloneMessages(state.Messages),
            Options: llm.ChatOptions{Functions: toolsNode.Definitions()},
        }, nil
    }),
    graph.WithPostHandler(func(
        _ context.Context, state *AgentState, response llm.Response,
    ) error {
        state.Messages = append(state.Messages, schema.CloneMessages(response.Messages)...)
        state.Output = schema.CloneMessages(response.Messages)
        state.HasToolCalls = len(tool.TailToolCalls(state.Messages)) > 0
        return nil
    }),
); err != nil {
    return err
}

if err := g.AddNode("tools", toolsNode,
    graph.WithPreHandler(func(
        _ context.Context, state *AgentState,
    ) ([]schema.Message, error) {
        return schema.CloneMessages(state.Messages), nil
    }),
    graph.WithPostHandler(func(
        _ context.Context, state *AgentState, results []schema.Message,
    ) error {
        state.Messages = append(state.Messages, schema.CloneMessages(results)...)
        state.HasToolCalls = false
        return nil
    }),
); err != nil {
    return err
}

finishNode := runnable.Func[[]schema.Message, []schema.Message](func(
    _ context.Context, output []schema.Message, _ ...runnable.Option,
) ([]schema.Message, error) {
    return schema.CloneMessages(output), nil
})
if err := g.AddNode("finish", finishNode,
    graph.WithPreHandler(func(
        _ context.Context, state *AgentState,
    ) ([]schema.Message, error) {
        return schema.CloneMessages(state.Output), nil
    }),
); err != nil {
    return err
}
if err := g.AddEdge(graph.Start, "chat"); err != nil {
    return err
}
if err := g.AddBranch(
    "chat", "tools", "has_tool_calls",
    func(_ context.Context, state *AgentState) (bool, error) {
        return state.HasToolCalls, nil
    },
); err != nil {
    return err
}
if err := g.AddEdge("chat", "finish"); err != nil { // 条件不匹配时的 fallback
    return err
}
if err := g.AddEdge("tools", "chat"); err != nil {
    return err
}
if err := g.AddEdge("finish", graph.End); err != nil {
    return err
}
if err := g.SetMaxSteps(20); err != nil {
    return err
}
compiled, err := g.Compile()
if err != nil {
    return err
}

reply, err := compiled.Invoke(ctx, []schema.Message{
    schema.NewMessage(schema.RoleUser, schema.NewTextBlock("调用 echo 返回 hello")),
})
```

这段代码展示了实际的数据流：PreHandler 从 State 组装 `llm.Request`，ChatModel 产生
function call，PostHandler 写回消息；ToolsNode 只执行消息尾部的新调用，工具 PostHandler
追加 function result，条件边再把控制流送回 ChatModel。ChatModel 和 ToolsNode 都保持纯粹，
不依赖 `AgentState`。`Compile` 会在运行前验证节点、Handler、分支和边类型，`MaxSteps`
防止模型持续调用工具形成无限循环。

这也是预置 Agent 配方存在的原因：标准 ReAct 场景直接使用 `agent.New`，可以省去上述
状态、适配节点和边定义；只有需要审批节点、检索分支、并行任务或领域状态时才下沉到
显式 Graph。

## 选择 Agent 工作流

| 场景 | 推荐 API | 运行方式 |
| --- | --- | --- |
| 单次模型回答 | `agent.New` 或 `agent.NewBasicAgent` | 一次模型调用 |
| 模型调用本地或 MCP 工具 | `agent.New` 或 `agent.NewReactAgent` | `LLM -> Tool -> LLM`，受 `MaxLLMCalls` 限制 |
| 主管模型分派专长 Agent | `agent.NewRoutingAgent` | Supervisor 模式返回主管继续决策；Router 模式只分派一次 |
| 多 Agent 轮流讨论 | `agent.NewGroupChat` | 按选择器和最大轮数执行 |

Routing 配置应显式指定模式，避免零值布尔含义不清：

```go
router, err := agent.NewRoutingAgent(agent.SupervisorConfig{
    BaseConfig: agent.BaseConfig{Name: "dispatcher", Model: model},
    SubAgents:  []agent.Agent{researcher, writer},
    Mode:       agent.RoutingModeSupervisor,
    MaxSteps:   6,
})
```

子 Agent 会收到主管作出路由决定之前的有效对话快照，而不会收到没有配对结果的
主管工具调用消息。应用层无需自行拼接这段历史。

预置 Routing 和 GroupChat 会把成员装配为真实的 `agent:<name>` Graph 节点，不再隐藏在
统一的 `dispatch` 函数中。Graph Snapshot、节点 Callback 和 Continuation 因而都能直接显示
具体成员；Supervisor 可把成员失败转成 Observation，Router 与 GroupChat 则传播失败。

## 消费流式输出

Agent 的 `Stream` 返回 `*runnable.StreamReader[[]schema.Message]`，数据面只包含 END 节点的
最终结果。LLM 增量和 Agent 中间状态使用 Context EventStream，因此不会污染 Graph 的输出类型。

```go
ctx = callback.WithStreamCallbacks(ctx,
    callback.StreamCallbackOf[llm.Response]("tokens", func(
        ctx context.Context, partial llm.Response,
    ) error {
        return pushModelChunk(ctx, partial)
    }),
    callback.StreamCallbackOf[schema.MessageEvent]("agent-state", func(
        ctx context.Context, event schema.MessageEvent,
    ) error {
        return replaceAgentSnapshot(ctx, event.Messages)
    }),
)

reader, err := assistant.Stream(ctx, []schema.Message{
    schema.NewMessage(schema.RoleUser, schema.NewTextBlock("总结这份材料。")),
}, agent.WithDeltaStream(true))
if err != nil {
    return err
}

output, err := reader.Collect(ctx)
if err != nil {
    return err
}
```

服务端将请求 `Context` 透传到模型、Graph 节点、工具、中间件与 Callback；客户端断开
或上游超时应取消该 Context。对于输出已开始的流，不要自动重试整条请求，以免重复执行
工具或重复计费。

## Callback、监控与审计

Callback 是同步直调的观测接口。Handler 在产生事件的 Goroutine 中按注册顺序运行，
因此 `Invoke` 返回时，已产生的回调已执行完毕。它适合审计、计费和关键日志；Handler
错误或 panic 不会改变 Agent、Graph、LLM 或 Tool 的业务结果，会发送给 ErrorSink。

```go
modelMonitor := llm.CallbackFuncs{
    CallbackName: "audit",
    End: func(ctx context.Context, response llm.Response) error {
        if response.Usage != nil {
            log.Printf("tokens=%d", response.Usage.TotalTokens)
        }
        return writeModelAudit(ctx, response)
    },
}
graphMonitor := graph.CallbackFuncs{
    CallbackName: "graph-audit",
    NodeEnd: func(ctx context.Context, result graph.NodeResult) error {
        log.Printf("node=%s step=%d duration=%s",
            result.NodeID, result.Step, result.Duration)
        return nil
    },
}

alerts := callback.ErrorSinkFunc(func(_ context.Context, failure callback.CallbackError) {
    log.Printf("callback failure: %v", failure)
})

manager, err := callback.NewManager(
    callback.Config{Timeout: 2 * time.Second},
    []callback.Handler{modelMonitor, graphMonitor},
    alerts,
)
if err != nil {
    return err
}
ctx = callback.WithManager(ctx, manager)

ctx = callback.WithStreamCallbacks(ctx,
    callback.StreamCallbackOf[llm.Response]("ui", func(
        ctx context.Context, response llm.Response,
    ) error {
        return pushModelChunk(ctx, response)
    }),
)

output, err := assistant.Invoke(ctx, input)
```

生命周期 Callback 和实时流数据只通过 Context 注册。ChatModel、Tool、Retriever、MCP
与 Graph 分别使用所属包的强类型 `Callback`；LLM 增量、Tool 进度和 UI 数据使用独立的
`StreamCallbackOf[T]`，不会挤占生命周期回调。`Timeout` 是协作式 deadline：Handler 必须主动响应
`ctx.Done()`；父 Context 取消仍保持 `context.Canceled` 或
`context.DeadlineExceeded` 的原始语义，不会被误记为 Callback 超时。

Graph 的 `OnNodeStart`、`OnNodeOutput` 与 `OnNodeEnd` 为每个节点建立独立子 Span；
`NodeExecution` 和 `NodeResult` 直接携带节点 ID、节点类别、输入输出类型、步骤、状态与耗时，不需要从通用 map
读取结构元数据。也可用 `graph.CallbackFuncs.OnNode` 统一处理节点开始与输出。

Callback 内部如需在 HTTP 请求取消后继续写审计库，应用自行派生持久化 Context，并设置
自己的上限：

```go
persistCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)
defer cancel()
err := writeAudit(persistCtx, event)
```

耗时指标上报如需异步，应用自行实现队列、重试、关闭和丢弃策略；框架不提供无界异步
Callback 管理器。计费、审计等需要确定性递交的工作应保持同步 Handler。

## 会话历史与执行恢复

无状态请求不需要额外配置。要跨轮保存会话，先配置 `state.Store`，然后每次运行指定
稳定且经过鉴权隔离的会话 ID。

```go
contextBuilder, err := contextengine.NewContextBuilder(contextengine.Config{})
if err != nil {
    return err
}
store := state.NewMemoryStore(state.MemoryStoreConfig{TTL: 24 * time.Hour})
assistant, err := agent.New(agent.BaseConfig{
    Model:           model,
    ContextBuilder:  contextBuilder,
    CheckpointStore: store,
})

output, err := assistant.Invoke(ctx, []schema.Message{
    schema.NewMessage(schema.RoleSystem, schema.NewTextBlock("回答使用中文。")),
    schema.NewMessage(schema.RoleUser, schema.NewTextBlock("记录我的偏好。")),
},
    agent.WithConversationID("tenant-a:user-42:session-7"),
    agent.WithStateValue("locale", "zh-CN"),
)
```

`WithConversationID` 没有 `CheckpointStore` 会返回错误。生产环境使用 Redis 等耐久 Store，
并以 `tenant:user:session` 之类的命名规则隔离会话。State Values 和 Checkpoint 内容必须
可 JSON 序列化；不要写入 client、channel、context、函数、密钥或其他运行时对象。

会话 Store 与执行 Store 相互独立。`state.Store` 只保存已完成的跨轮消息、Values 和版本；
`control.CheckpointStore` 只保存 Graph Continuation 字节。应用为每次可恢复运行提供独立
key，不要把 `conversation_id` 当作框架内置的执行锁。

Graph 恢复结构由 `pkg/graph` 自己拥有：`graph.GraphStateCheckpoint` 保存 State Codec
标识、版本和字节，`graph.CursorStack` 保存节点边界游标；`pkg/state` 不包含图执行状态。

外部暂停使用 typed Cancel Cause：

```go
runCtx, cancel := context.WithCancelCause(ctx)
go func() {
    <-pauseRequested
    cancel(control.RequestInterrupt("用户暂停", map[string]any{"operator": "user-42"}))
}()

output, err := assistant.Invoke(runCtx, input,
    agent.WithConversationID("tenant-a:user-42:session-7"),
    agent.WithCheckpoint(executionStore, "tenant-a:task-42"),
)
if errors.Is(err, graph.ErrInterrupted) {
    output, err = agent.Resume(context.Background(), assistant,
        agent.WithConversationID("tenant-a:user-42:session-7"),
        agent.WithCheckpoint(executionStore, "tenant-a:task-42"),
    )
}
```

只有 `control.InterruptRequest` 会创建 Continuation；普通取消或 deadline 不落盘。Graph
必须成功保存后才返回 `graph.ErrInterrupted`，保存失败会透传 Store 错误。

高危工具审批使用 `agent.WithBeforeToolBatch`。Hook 在整批 Tool Call 解析完成后、任何 Tool
开始前运行；返回 typed interrupt 时该批次执行数为零。批准后 Resume 会重新运行 Hook：

```go
approval := tool.BeforeBatchFunc(func(ctx context.Context, batch tool.Batch) error {
    if needsApproval(batch) && !isApproved(ctx, batch) {
        return control.RequestInterrupt("等待工具审批", nil)
    }
    return nil
})

assistant, err := agent.New(agent.BaseConfig{Model: model, Tools: tools},
    agent.WithBeforeToolBatch(approval),
)
```

恢复可替换 Agent 实例、模型端点和 API Key，但 Graph 名称、拓扑和 State Codec 必须兼容。
Continuation 不保存这些运行时连接信息。恢复是 at-least-once：中断节点和并行分支可能重放，
副作用必须幂等。框架不提供 Lease、分布式锁、fencing 或 exactly-once；多副本应用在调用
Resume 前自行用 Gateway 锁、队列唯一任务、数据库事务或 Redis SETNX 串行化同一 key。

## 编排多个 Agent

Agent 本身也是 Runnable，因此可以继续作为更大图中的节点。使用 `graph.NewGraph[I, O]`
创建 Builder，通过 Pre/Post Handler 在业务 State 与纯 Agent 节点之间映射，最后调用
`Compile()` 获得不可变、可并发复用的 `CompiledGraph`。完整示例见 `examples/graph/main.go`。

```go
builder := graph.NewGraph[[]schema.Message, []schema.Message]("research-team")
// 使用 SetStateFactory、AddNode、WithPreHandler、WithPostHandler 和 AddEdge
// 装配 researcher -> reviewer -> finish，参见 examples/graph/main.go。
team, err := builder.Compile()
if err != nil {
    return err
}

result, err := team.Invoke(ctx, []schema.Message{
    schema.NewMessage(schema.RoleUser, schema.NewTextBlock("分析这个主题。")),
})
```

需要业务状态时，使用 `graph.NewGraph[I, O]` 和 `SetStateFactory`。State 必须是指向
结构体的指针；顺序节点复用同一指针，用户不需要实现 `Clone`。默认 JSON State Codec
要求字段可导出且不能使用 `json:"-"`；复杂类型可通过 `graph.NewStateCodec` 提供自定义
Codec。序列化只发生在 Fan-Out、持久化中断和恢复边界。节点输出为空时，流也会发送空
`Snapshot`，因此前端必须用它替换旧结果，而不是忽略空快照。

## 上线检查清单

- 明确每个 Agent 的最大模型调用数、工具超时、工具并发和 Graph 最大步数。
- 所有可写工具都通过 Middleware 执行认证、租户隔离、权限校验和必要的幂等保护。
- 以 `Context` 传递 Trace、请求取消和 `tool.Subject`，不把敏感数据拼入 Prompt。
- 流式消费者只在收到 `Done` 后保存、扣费或声明成功；`Item.Err` 立即作为失败处理。
- 自定义流适配器应在 Reader 关闭时取消上游；首个数据后的流错误不得自动重试。
- Callback Handler 保持短小、可取消，Handler 失败接入 `ErrorSink` 的日志、告警或死信流程。
- 为会话配置耐久 `state.Store`，验证版本冲突和过期；为可恢复运行单独配置
  `control.CheckpointStore`，验证挂起、Store 失败、重复 Resume 和 at-least-once 幂等。
- 分别在核心模块和已启用的 `extensions` 模块执行单测、`go vet` 与竞态检测。
- 先压测模型限流、工具并发、SSE 中断、网络重试与下游存储故障，再逐步放量。
- 为缓存装饰器验证键隔离、失效、截断流、并发请求和调用方取消语义后再启用。
