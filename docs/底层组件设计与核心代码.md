# goHarness 底层组件设计与核心代码

> 这不是接口清单，也不是把源码逐行翻译成中文。它要回答三个更有用的问题：这个框架为什么要拆出这些组件；一次请求真正经过了什么；面试官顺着并发、错误、恢复和安全继续追问时，应该怎样用源码说明白。

适合已经会读 Go、但希望把一个智能体框架讲成完整工程故事的读者。文中的类型、路径和行为以当前工作区源码为准；为了突出控制流而省略细节的片段会明确标为“教学简化版”。

为了能和源码逐项对照，包路径、类型名、字段名和命令保留原样；除此以外，正文直接用中文说明含义，不要求读者先认识英文简称。

## 0. 第一次读这个项目前，先建立最小心智模型

这份文档不是要求你先懂模型服务、向量检索或分布式恢复，才有资格读下去。对于准备实习的 Go 初学者，第一遍只要先回答下面六个问题：

1. 用户发来一句话后，项目把它放在哪里？
2. 谁决定下一步该调用模型、工具，还是结束？
3. 一次请求中不断变化的数据放在哪里？
4. 用户中途断开时，为什么上游工作能停下来？
5. 工具调用失败时，为什么有时继续问模型，有时整个请求失败？
6. 中断后再继续，为什么仍可能重复执行一次写操作？

后面的十六章就是逐个回答这些问题。你不必在第一遍就记住每个类型名；先能说清“谁负责什么、数据怎么走、失败后会怎样”，再回来看函数签名，效率会高很多。

### 0.1 先把项目想成一个会走流程的客服

假设用户问“帮我查订单”。项目不会直接把这句话交给某个神秘函数然后得到答案，而是像一个有流程的客服：

```text
用户问题
  -> 记成一条消息
  -> 交给模型判断是否需要查订单
  -> 若需要，调用查订单工具
  -> 把工具结果再记成消息
  -> 交回模型组织最终回答
  -> 返回给调用方
```

这里的“模型”可以先理解为一个外部文字服务：给它一组消息，它返回一组消息；它可能直接回答，也可能提出“请调用某个工具”。“工具”则是普通 Go 代码包起来的能力，例如查询数据库、读文件、调用内部订单服务。框架的价值不在于替你写订单业务，而在于把这条流程的顺序、取消、错误、并发和恢复规则统一处理。

### 0.2 初学者只需先认识这些 Go 概念

源码会出现不少类型名，但真正影响阅读的基础不多：

| 看到什么 | 可以先怎样理解 | 在本项目中最常见的用途 |
| --- | --- | --- |
| `struct` | 一张有固定列的记录表 | `Message` 保存一条消息的角色、内容和附加信息 |
| `[]T` | 一串同类型数据，保留顺序 | `[]schema.Message` 是按先后排列的对话消息 |
| `map[string]any` | 用字符串找值的字典 | 保存可扩展的元数据；跨边界前要小心复制 |
| `interface` | 一份能力承诺，不是父类 | 只要有规定的方法，就能被执行图当作节点调用 |
| 方法 | 绑定在某个类型上的函数 | `Invoke` 表示“给我输入，我返回结果” |
| `*T` | 指向同一份记录的地址 | 执行图把同一次运行的工作笔记传给前置、后置处理器 |
| `context.Context` | 请求随身携带的取消和超时信号 | 浏览器断开时通知模型、工具和流读取端停止 |
| `error` | Go 用返回值表达失败的方式 | 区分“这次执行不能继续”和“把错误告诉模型继续想” |

泛型写法也不用害怕。`Runnable[I, O]` 只是在说：“这个组件接收 `I` 类型输入，返回 `O` 类型输出。”把它读成“输入箭头输出”即可。真正的业务类型仍然写在调用点，例如 `Runnable[[]schema.Message, []schema.Message]` 就是“消息列表进，消息列表出”。

### 0.3 最容易混淆的三个“状态”

“状态”不是一个玄学词。它只是程序为了完成工作而暂时或长期保存的数据。这个项目故意把三类状态拆开，因为它们的寿命不同：

```text
一次执行图运行的工作笔记
  例：当前消息、已查到的资料、当前轮数
  寿命：这一次请求结束就可以丢掉

会话检查点
  例：用户过去说过什么、上一轮模型答了什么
  寿命：多轮聊天之间一直保留

恢复记录
  例：流程停在“等待审批”前，下一次应从哪个节点继续
  寿命：一次被业务明确暂停的执行，恢复后即可删除或覆盖
```

不要急着背名称。把它们分别想成“本次任务的草稿纸”“长期聊天记录本”“暂停书签”就够了。第 7 章会用真实代码把三者拆开。

下面这段来自 `examples/graph/main.go`，就是一次执行图的“草稿纸”：

```go
type teamState struct {
    Messages []schema.Message
    Output   []schema.Message
}
```

研究节点和审核节点都能读 `Messages`，后置处理器再把新结果追加进去；最后由 `Output` 交给结束节点。`*teamState` 中的星号表示：同一次运行中，处理器拿到的是同一份草稿纸，而不是每次复制一份。并行场景例外，框架会主动复制，避免两个分支同时改同一份数据。

### 0.4 读这份文档的正确顺序

第一次阅读时，先读本章、第一章、第二章、第三章、第四章的开头、第五章、执行图的“白话解释”、第七章、智能体装配层和第十四章。遇到反射、状态编解码器、限流、检索融合等内容，不必停下来硬啃；先记住它解决的实际问题，第二遍再看实现细节。

每一章都按同一顺序组织：先说“为什么需要它”，再说“最小例子怎样工作”，随后贴真实源码解释关键行，最后给出面试官可能继续追问的边界。你读完一章后，应至少能用自己的话回答：它替谁解决了什么问题；它不负责什么；失败时由谁接住。

## 1. 先把项目讲成一句人话

goHarness 是一个以强类型执行图为执行引擎的 Go 智能体编排框架。它不把模型、工具、检索和审批逻辑硬写在一个循环里，而是先把它们统一成可执行组件，再交给执行图负责顺序、分支、运行状态和恢复。

这里的“强类型”不是指类型很多，而是指框架会检查“上一步产出的数据能不能交给下一步”；“编排”也不是额外业务，意思就是安排多个步骤按什么顺序、条件和规则执行。程序实际运行时才发生的事情，文中会称为“运行阶段”或“运行时”。

先别被“执行图”这个词吓住。这里的图不是画图软件，也不是图数据库；它只是“流程图的程序版本”。

```text
节点 = 一步工作，例如“问模型”或“查订单”
边   = 做完这一步后，下一步该去哪里
分支 = 根据当前结果，选择不同的下一步
```

对初学者而言，先抓住两条最常见路线就够了：

```text
没有工具：用户消息 -> 模型 -> 助手消息 -> 结束

有工具：  用户消息 -> 模型 -> 工具调用 -> 工具结果 -> 模型 -> 助手消息 -> 结束
```

`pkg/agent/new.go` 中的 `agent.New` 恰好把这条选择写得很直白：

```go
if len(resolved.Tools) > 0 {
    return NewReactAgent(ReactAgentConfig{BaseConfig: resolved})
}
return NewBasicAgent(resolved)
```

不用急着理解 `ReactAgentConfig`。先读条件本身：工具列表不为空，就创建带工具循环的智能体；工具列表为空，就创建只调用一次模型的基础智能体。后面的复杂代码，本质上都在保证这两条路线可以安全地取消、观察、恢复和组合。

因此，面试中的第一句话可以这样说：

> 我把智能体看成一张预制的执行图，而不是另一套执行引擎。底层先解决消息表达、统一调用、流式生命周期和观测；执行图再解决编排与运行状态；工具运行环境、模型适配、上下文整理、检索和扩展分别处理各自的外部复杂性；智能体只是把这些能力按基础对话、工具循环、路由或群聊的规则装配起来。

这句话有两个关键边界。

1. 执行图不理解“聊天”或“工具”的业务语义。它只知道节点、边、输入输出类型和运行时状态。
2. 智能体不重新实现调度、超时、流式或恢复。它调用执行图，并在节点的前置、后置处理器中放入智能体领域数据。

如果暂时看不懂“前置、后置处理器”，可以先把它们读成两个小钩子：前置处理器负责“从草稿纸里取出这一节点需要的输入”；后置处理器负责“把节点刚得到的结果写回草稿纸”。第 6 章会用 `examples/graph/main.go` 的真实代码展开它。

### 1.1 一次带工具调用的请求经过哪里

先把下面的图当成路线图，而不是要求背下来的组件名单。第一次阅读只需跟着最粗的竖线走：消息进入 -> 模型判断 -> 可能调用工具 -> 模型给最终回答。横向三条通道是“附加能力”，它们不决定业务结果。

```text
调用方
  |
  v
调用 `agent.New` 或 `Agent.Invoke`
  |
  +--> 加载会话检查点                         (可选，pkg/state)
  |
  v
内置执行图：`Graph[[]schema.Message, []schema.Message]`
  |
  +--> 模型节点的前置处理器
  |      -> 上下文整理器 -> 模型节点 -> 模型服务商的服务器推送事件
  |
  +--> 工具节点（仅当模型返回工具调用）
  |      -> 批次前置钩子 -> 工具运行环境 -> 中间件 -> 工具调用
  |
  +--> 再次调用模型，或结束
  |
  +--> 保存会话检查点                         (可选，pkg/state)
  v
最终 `[]schema.Message`
```

横向还有三条不会改变业务结果的通道：

```text
流读取器      : 数据如何增量传递、背压、关闭和取消
回调          : 生命周期、调用链追踪、用量、错误观察
执行图事件    : 图和节点的控制面事件
```

### 1.2 组件地图：先分清谁负责什么

| 层次 | 包 | 核心职责 | 明确不负责 |
| --- | --- | --- | --- |
| 数据协议 | `schema` | 统一消息、内容块、工具调用关联和元数据 | 决定何时调用模型或工具 |
| 执行协议 | `runnable` | 统一单值/流式输入输出，管理流生命周期 | 决定节点顺序 |
| 观察与控制 | `callback`、`control` | 追踪、生命周期回调、带类型的中断信号 | 鉴权、改写业务结果 |
| 编排 | `graph` | 编译、连线校验、运行状态、并行、恢复边界 | 保存长期会话历史 |
| 会话状态 | `state` | 版本化会话检查点 | 恢复某个执行图节点 |
| 外部副作用 | `tool` | 工具参数、审批、超时、重试、并发、中间件 | 决定模型“该不该”调用工具 |
| 模型适配 | `llm` | 不依赖特定服务商的模型协议、服务器推送事件、增量消息、重试限流 | 管理整个智能体循环 |
| 上下文治理 | `contextengine` | 预算、角色修复、裁剪、缓存标记 | 持久化历史或真正保存缓存 |
| 知识能力 | `retrieval`、`httpclient` | 检索增强流程和共享网络连接池 | 直接控制智能体路由 |
| 装配层 | `agent`、`internal/agentrecipe` | 基础对话、工具循环、路由、群聊的图配方 | 重新发明底层运行时 |
| 可选实现 | `extensions` | 模型上下文协议、键值数据库实现、模型与向量缓存 | 反向依赖核心业务包 |

下面按这个依赖顺序阅读。先有数据，才能谈执行；先有执行，才能谈编排；先有编排，才有一个可信的智能体故事。

对实习面试来说，不需要把表中所有包平铺背下来。可以分三轮掌握：

```text
第一轮：schema、runnable、graph、state、tool、agent
        能讲清一条普通对话和一条工具调用链。

第二轮：callback、control、llm、contextengine
        能讲清取消、流式输出、错误和上下文为什么不混在一起。

第三轮：retrieval、httpclient、extensions
        能讲清可选能力为什么不反向污染核心包。
```

这也是源码阅读顺序，而不是重要性排序。比如没有检索功能的项目照样需要正确处理消息、取消和工具副作用；反过来，检索再强，消息和执行边界混乱也很难维护。

## 2. `schema`：为什么消息不能只是 `string`

源码入口：`pkg/schema/message.go`、`pkg/schema/block.go`、`pkg/schema/clone.go`、`pkg/schema/stream.go`。

最小示例可以把提示词和模型回答都当字符串。但真正的模型会返回文本、推理内容、图片、文件、多个工具调用和工具结果。若把它们都压扁成字符串，会立刻丢掉三个关键信息：内容顺序、工具调用标识，以及模型服务商专有但不能随意解释的字段。

**第一次读这一章时只记住一句话：消息不是一段文字，而是一份按顺序排列的“对话记录”。**

例如，用户问“查一下订单一二三”，模型可能先输出一段文字“我来查询”，紧接着给出一次工具调用；工具返回后，模型再输出最终解释。若只保存拼接后的文本，框架将无法知道哪一段是展示给人的文字，哪一段真的要交给工具执行，也无法把工具结果对应回原调用。

项目因此把消息设计成“角色 + 有序内容块”，而不是“角色 + 一个文本字段”。真实结构在 `pkg/schema/message.go`：

```go
type Message struct {
    Role          Role
    ContentBlocks []ContentBlock
    ResponseMeta  *ResponseMeta
    Extra         map[string]any
}

type ContentBlock struct {
    Type ContentBlockType

    Text               *Text
    Image              *MediaContent
    File               *MediaContent
    Audio              *MediaContent
    Video              *MediaContent
    Reasoning          *Reasoning
    FunctionToolCall   *FunctionToolCall
    FunctionToolResult *FunctionToolResult
    Opaque             *OpaqueContent
}
```

第一次看这段结构体时，不要试图理解每个字段。按下面的层次读就够了：

```text
Message
  - Role：谁说的，例如用户、助手、工具
  - ContentBlocks：说了什么，且必须保留顺序
  - ResponseMeta：模型服务附带的名称、结束原因和用量
  - Extra：当前框架暂时不需要解释、但不能丢掉的附加信息
```

`ContentBlock` 中的 `Text`、`Image`、`File` 等字段看起来像“同一份数据放在很多位置”，其实它表达的是“这一个内容块是哪一种内容”。正常情况下，一个内容块只应该填其中一种；`Validate` 就是在防止一块内容同时既是文字又是工具调用的矛盾状态。

`ContentBlocks` 是切片而不是映射，顺序就是协议的一部分。下面这条消息表达的是“先说明意图，再发起查询”，不能被重新排序：

```go
request := schema.NewMessage(schema.RoleAssistant,
    schema.NewTextBlock("我先查一下库存。"),
    schema.NewFunctionToolCallBlock(
        "call-42", "lookup_stock", `{"sku":"A-100"}`,
    ),
)
```

工具结果同样不是普通异常文本。`FunctionToolResult` 同时保存调用标识、工具名称、嵌套的内容块和错误标志：

```go
result := schema.NewMessage(schema.RoleTool,
    schema.NewFunctionToolResultBlock(
        "call-42", "lookup_stock", true,
        schema.NewTextBlock("inventory service timed out"),
    ),
)
```

这里的 `IsError=true` 表示“下一轮模型可以看见这个工具失败，并自己调整策略”。它不是 Go 语言的 `error`，也不等价于“整个执行图必须失败”。这个区分在工具运行环境一节会变得很重要。

### 2.1 `Validate` 为什么值得专门设计

`ContentBlock.Validate` 强制一个内容块恰好有一份实际内容，并针对工具调用验证调用标识、名称和对象格式参数。也就是说，下面这种看似方便的状态不会混入框架：

```text
一个内容块同时带 Text 和 FunctionToolCall  -> 拒绝
工具调用没有调用标识                         -> 拒绝
参数不是对象格式，或文本不完整               -> 拒绝
媒体内容同时带资源地址和内嵌数据             -> 拒绝
```

这是把协议错误尽量前移。模型流式输出时会产生半截工具参数，但那是增量组装阶段的临时状态；一旦准备交给工具节点 `ToolsNode` 执行，就必须是完整对象。

`ResponseMeta` 则把响应标识、模型名称、完成原因和词元用量附在消息上。其 `validate` 会拒绝负数词元，避免观测或计费数据无声污染。

### 2.2 为什么访问器只看顶层

`Message.TextBlocks()`、`JoinedText()`、`FunctionToolCalls()` 和 `FunctionToolResults()` 都返回防御性副本，而且只筛选顶层块。这样做避免了一个很隐蔽的错误：工具结果里嵌套的文本不应被误当成助手正文或下一次工具调用。

要保留完整多模态顺序，应直接遍历 `ContentBlocks`；要读工具结果内部内容，显式遍历 `FunctionToolResult.ContentBlocks`。框架故意没有万能的 `Message.Text()`，因为“将混合内容转成字符串”的语义必须由调用方明确决定。

### 2.3 防御性复制不是多余分配

`CloneMessages` 深拷贝常见可变容器；`CloneMessagesStrict` 还会拒绝无法可靠复制的未知可变引用。原因是同一条消息会被上下文整理器、工具节点、回调、缓存和并行分支传递。若它们共享 `map[string]any` 或切片，某个旁路写入就可能改变主链路。

可以用下面的判断解释这项取舍：

> 消息是跨组件边界的数据，不是某个节点的私有工作区。框架宁可在边界复制，也不让并行执行和观测代码共享可变引用。

### 2.4 流式消息如何表达

`pkg/schema/stream.go` 定义了两种智能体数据面事件：`MessageEventDelta` 和 `MessageEventSnapshot`。它们只表达消息增量或快照；执行图开始、节点结束和会话检查点等控制面事件走执行图事件或回调，不能和最终业务输出混在一起。

**面试追问：为什么不直接用模型服务商的原始对象数据？**

回答：模型服务商的原始对象数据只适合适配器内部。框架的执行图、工具、会话检查点、缓存和模型上下文协议需要共享一份稳定协议；`Opaque` 内容块仍能保留暂时不理解的服务商字段，既不丢数据，也不把服务商细节扩散到所有包。

## 3. `runnable`：先统一“怎么调用”，再谈“谁调用谁”

源码入口：`pkg/runnable/runnable.go`、`adapter.go`、`stream_reader.go`、`concat.go`。

模型、工具、检索器、智能体和执行图的业务类型不同，但它们都需要被组合。若执行图分别认识模型、工具和检索器，就会越来越像一个巨大的领域分支。`Runnable[I, O]` 把共同点压缩为统一调用协议：

先看它要解决的具体麻烦。假设没有这层约定，执行图想调用一个节点时可能需要这样判断：

```text
这是模型吗？按模型的办法调用。
这是工具吗？按工具的办法调用。
这是检索器吗？再写一套调用办法。
```

节点种类一多，执行图就会被业务判断填满。`Runnable` 的做法是反过来规定：**不管你内部是模型、工具还是普通函数，只要能按约定接收输入并返回结果，执行图就可以调用你。** 这正是 Go 接口适合这里的原因：它不要求组件继承同一个父类，只要求它提供同名且签名正确的方法。

读下面接口时，先忽略泛型和可变参数。把四个方法理解为“输入是一份完整数据还是连续数据，输出是一份完整数据还是连续数据”的四种组合：

```go
type Runnable[I, O any] interface {
    Invoke(context.Context, I, ...Option) (O, error)
    Stream(context.Context, I, ...Option) (*StreamReader[O], error)
    Collect(context.Context, *StreamReader[I], ...Option) (O, error)
    Transform(context.Context, *StreamReader[I], ...Option) (*StreamReader[O], error)
}
```

其中 `I` 是输入类型，`O` 是输出类型；`...Option` 是调用时可选附带的配置。`context.Context` 不是业务输入，它只负责把取消和超时通知下去。若某个工具的业务输入是“订单号”，它的 `I` 可以是订单号结构体；若一个模型的业务输入是一串消息，它的 `I` 就是 `[]schema.Message`。

四个方法不是“让每个实现类多写四遍代码”，而是四种数据形态：

| 方法 | 输入 | 输出 | 典型用途 |
| --- | --- | --- | --- |
| `Invoke` | 单值 | 单值 | 工具、普通节点、最终结果 |
| `Stream` | 单值 | 流 | 模型或智能体输出 |
| `Collect` | 流 | 单值 | 在需要完整值的节点前形成屏障 |
| `Transform` | 流 | 流 | 可连续处理增量数据的节点 |

大多数业务组件只需要实现自己自然的形态。例如 `runnable.Func` 原生实现 `Invoke`，其余形态由 `StreamFromInvoke`、`CollectFromInvoke`、`TransformFromInvoke` 补齐。`Adapter` 会检查一个对象原生拥有的能力，再绑定缺失方法：

对初学者来说，这段设计可以先记成一条规则：**普通函数天然是“给完整输入，等完整结果”；只有真正需要边生成边消费的数据，才需要原生实现流式方法。** 因此不要为了“看起来高级”让每个函数都自己维护通道和协程。

```go
// 教学缩略版，逻辑来自 pkg/runnable/adapter.go
if nativeStream != nil && nativeInvoke == nil {
    invoke = func(ctx context.Context, in I, opts ...Option) (O, error) {
        stream, err := nativeStream(ctx, in, opts...)
        if err != nil { var zero O; return zero, err }
        return Concat(ctx, stream)
    }
}
```

这说明了一个常被忽略的代价：从流退化成单值时必须 `Concat`，也就是必须等流结束。执行图能在编译时识别可流式的节点，但遇到分支判断、普通 `Invoke` 或运行状态的前置、后置处理器时仍可能需要把流物化为完整值。这不是实现缺陷，而是数据依赖决定的屏障。

### 3.1 调用选项与请求上下文分工

两者都能“携带东西”，但语义不同：

```text
请求上下文（源码类型为 `context.Context`）
  - 请求生命周期：取消、截止时间、调用链标记、身份、回调
  - 应沿调用树传播，不能存可选业务配置

调用选项（源码类型为 `runnable.Option`）
  - 调用方显式选择的配置：执行检查点、节点超时、模型参数
  - 可被组合层解析、划分作用域并转发
```

可以用一次“查订单”的调用区分它们：用户关闭页面时，应通过请求上下文让网络请求停止；调用方希望把某个节点的超时设为两秒时，应通过调用选项表达。前者是这次请求的生命线，必须沿调用链自动传递；后者是调用者主动选择的开关，应该在函数签名上看得见。

初学者很容易把 `context.Context` 当成万能背包，在里面塞订单号、模型参数、开关甚至可变映射。这样短期省事，长期会让调用者不知道函数依赖什么，测试也难写。这里的规则很实用：取消、截止时间、调用链身份等请求范围信息放请求上下文；明确可配置的行为放调用选项；真正的业务数据放方法的输入参数。

这套 Option 机制的重点不是配置对象本身，而是"设置函数只执行一次"。`runnable.Option` 是不透明的类型化配置：`WrapOption` 把它绑定到组件配置类型，Graph 在运行入口按 `OptionTypes()` 声明广播、按 `ForNode`/`ForPath` 路径定向，组件入口用 `ResolveComponentOptions` 解析一次并拿到剩余选项。组合调用中，执行图、智能体、节点不会重复执行同一个设置函数；无接收者的类型在入口报错而不是被静默丢弃。

**面试追问：为什么不让所有配置都塞进请求上下文？**

回答：上下文的值应是请求范围的传播数据，调用者不容易从签名看出里面有哪些开关；调用选项是显式参数，便于组合层识别归属。把两者混用，会让超时、身份和模型参数的所有权不清晰。

## 4. 流读取器：它不是通道包装，而是流式生命周期协议

源码入口：`pkg/runnable/stream_reader.go`、`pkg/runnable/concat.go`；代表性测试：`pkg/runnable/stream_reader_test.go`。

最小实现当然可以用 `chan T`。但一旦消费者提前离开页面、网页请求取消、上游报错，单独一个通道不足以说明谁该退出、谁会阻塞、错误交付几次。

先区分“普通调用”和“流式调用”。普通调用像点外卖：下单后等餐做好，一次性拿到完整结果。流式调用像接电话：对方说一句，你就能立刻听到一句，不必等整段话结束。模型逐字生成回答、检索过程持续产出资料、网页持续展示进度，都适合用流式调用。

流读取器可以先想成一根有方向的水管：写入端把数据块放进管子，读取端取走数据块。它比原始 Go 通道多规定了三件事：谁能主动关闭管子；关闭信号怎样反向通知上游；错误只能怎样交付一次。这三件事决定了网页断开后会不会留下卡住的协程。

`Pipe` 因此创建读取端与写入端共享的状态：

```go
type pipeState[T any] struct {
    ctx    context.Context
    cancel context.CancelFunc
    values chan T       // 无缓冲，发送者等消费者接收
    done   chan struct{}
    concat ConcatFunc[T]

    closeOnce sync.Once
    mu        sync.Mutex
    terminal  error
    delivered bool
}
```

这段代码不需要逐字段死记。初读只认四个成员：

```text
values：真正传递数据的无缓冲通道
done：任何一方结束后都会关闭的统一停止信号
ctx：从调用方传下来的取消信号
terminal：这条流最后为什么结束，是正常结束还是某个错误
```

`values` 选无缓冲通道意味着写入端只有在读取端真正接走一个数据块时才能继续。这叫“背压”：展示端读得慢，上游自然放慢，不会在内存里无限堆积尚未展示的文字。它不是性能问题，而是资源保护规则。

除了形成背压，`Send` 还不会因为消费者离开而永久卡住：

```go
func (w *StreamWriter[T]) Send(value T) error {
    select {
    case w.state.values <- value:
        return nil
    case <-w.state.done:
        err, _ := w.state.terminalForWriter()
        return err
    case <-w.state.ctx.Done():
        w.state.finish(w.state.ctx.Err())
        return w.state.ctx.Err()
    }
}
```

这三个分支分别是“消费者接到数据”“流已经结束”“父请求取消”。读取端的 `Close` 则反向关闭 `done` 并取消流的请求上下文：

```go
func (r *StreamReader[T]) Close() error {
    if r == nil || r.state == nil { return nil }
    r.state.finish(context.Canceled)
    if r.state.cancel != nil { r.state.cancel() }
    return nil
}
```

为什么要反向取消？因为用户可能只读了第一个数据块就断开。如果只是不再 `Recv`，上游写入端会卡在无缓冲通道的发送上，服务器推送事件的读取协程也无法退出。`Close` 把“我不再消费”明确传回上游。

这里可以顺带认识一个常用 Go 习惯：`defer reader.Close()` 表示“当前函数无论正常返回还是提前报错，离开时都执行关闭”。它适合释放读取端、网络响应体、锁等资源。第 4.1 节的 `Concat` 正是这样做的，所以它读完流后不会忘记通知上游退出。

### 4.1 终止规则要能背下来

| 发生什么 | 读取端看到什么 | 写入端后续看到什么 |
| --- | --- | --- |
| `Writer.Close()` | `io.EOF` | `io.ErrClosedPipe` |
| `Writer.CloseWithError(err)` | 第一次是 `err`，随后 `io.EOF` | `err` |
| `Reader.Close()` | 不再继续消费 | `context.Canceled` |
| 父请求上下文取消 | 当前终止错误 | 当前终止错误 |

`sync.Once` 保证读取端、写入端、父上下文竞争结束时，`done` 只会关闭一次。`terminalForReader` 用 `delivered` 保证非空终止错误只交付一次，随后按 Go 流习惯返回结束标记。

这里的“竞争”不是业务上的抢单，而是多个协程可能几乎同时做不同的结束动作：写入端正常完成、读取端关闭、请求超时。没有 `sync.Once` 时，重复关闭通道会直接导致异常崩溃；有了它，无论谁先结束，最终状态都只有一份。

`Concat` 在消费完读取端后会 `defer reader.Close()`。默认规则是字符串拼接、切片追加、其他类型取最后一个值；领域组件可以在 `Pipe` 创建时用 `WithConcat` 绑定自己的归约逻辑。

**面试追问：为什么这个流读取器只能有一个消费者？**

回答：多个协程同时 `Recv` 会抢夺同一条消息，顺序和归属都无法预测。需要广播时，应在上层明确复制数据或注册实时事件流，不应把一个读取端假装成发布订阅系统。

## 5. `callback` 与 `control`：观察权和控制权必须分开

源码入口：`pkg/callback/dispatcher.go`、`context.go`、`event_stream.go`、`pkg/control/control.go`。

系统需要指标、调用链追踪、审计、实时用量展示，但这些旁路能力不应让一次正常的智能体调用因为日志失败而失败。`callback.Manager` 在上下文中保存不可变的处理器注册表：

这一章先抓住一句话：**回调负责“看见发生了什么”，中断负责“要求流程在安全位置停下”。** 两者都可能在模型调用前后出现，但权限完全不同。

例如，记录“模型调用用了多少词元”的代码只是观察者。即使写日志的服务器不可用，用户的正常回答也不应该因此失败；反之，“这批付款工具尚未审批”属于业务控制，必须可靠地停止后续工具执行。把前者和后者放进同一套机制，通常会得到“日志一挂，订单也挂”的系统。

```go
ctx = callback.WithManager(ctx, manager)
result, err := assistant.Invoke(ctx, input)
```

组件只定义自己的强类型回调接口。例如模型、工具、执行图、检索器各自定义 `On...Start/End/Error`。通用 `Dispatch[T]` 只调用实现了目标接口的处理器，并按注册顺序运行。每个调用都会复制 `Invocation` 元数据，`Manager.invoke` 还隔离异常崩溃、可选超时和错误接收器。

```text
处理器甲 -> 处理器乙 -> 处理器丙
  失败      继续        继续
    \----> ErrorSink
```

框架中生命周期调用通常故意忽略 `Dispatch` 返回的旁路错误，因此观测故障不会取代主业务错误。若业务必须因为审计未落库而拒绝转账，那不是回调的工作，应该放在中间件或显式执行图节点里。

初学者可以用一个判断题区分位置：这段代码失败后，是否应该改变用户本次请求的业务结果？如果答案是否定的，它适合回调；如果答案是肯定的，它应放进工具中间件或执行图节点，而不是放进回调处理器。

### 5.1 回调、实时事件流、执行图事件的区别

| 通道 | 内容 | 频率 | 是否改变业务结果 |
| --- | --- | --- | --- |
| 回调 | 开始、结束、错误、用量等生命周期 | 低频 | 否 |
| 实时事件流 | 模型响应快照、智能体消息增量 | 高频 | 否 |
| 执行图事件接收器 | 图、节点开始、输出、结束、失败 | 控制面 | 否 |

`EmitStream` 也按 Go 类型精确匹配回调，并同步调用。同步不是为了拖慢主链路，而是为了保证事件顺序可解释；真正需要异步写消息队列的处理器应自行复制数据、放入有界队列并处理丢弃策略。

### 5.2 真正能中断执行的是 `control.InterruptRequest`

`control` 不是普通 `context.Canceled` 的别名。它定义了带原因与元数据的带类型错误：

```go
type InterruptRequest struct {
    Reason   string
    Metadata map[string]any
}

func RequestInterrupt(reason string, metadata map[string]any) error
func AsInterrupt(err error) (InterruptRequest, bool)
```

普通取消的含义是“这次请求不需要继续了”，常见原因是用户离开页面或超时；带类型中断的含义则是“业务故意停在这里，之后可能带着额外条件继续”。举例说，用户离开页面不代表系统应自动补做扣款；而人工审批等待则应保存一个恢复书签，审批通过后从指定节点继续。这就是项目不把所有取消都当成可恢复任务的原因。

执行图只有识别到这个类型，才会在安全边界保存恢复记录。浏览器断开、请求超时或普通 `context.Canceled` 只终止本次请求，不会擅自制造“以后可以继续运行”的任务。

**面试追问：为什么回调不能做鉴权？**

回答：回调没有 `next`，其错误也会被隔离，它天生是观察者。鉴权需要可靠地阻止调用并可能注入租户字段，应放在持有 `next` 的工具中间件或领域节点中。

## 6. `graph`：把运行时错误前移到编译期

源码入口：`pkg/graph/runtime_graph.go`、`compile_plan.go`、`runtime_execute.go`、`stream_execute.go`、`parallel.go`。

执行图的泛型只描述外部边界 `Graph[I, O]`。节点之间的具体类型在运行时通过反射读取 `Invoke` 签名后校验，这是 Go 泛型在异构节点图上的现实选择。

先用白话说：执行图负责“按什么顺序做事”，不负责“订单怎么查”。节点负责各自的一小步业务；边负责连接这些步骤；运行状态负责保存同一次流程中所有步骤都要用到的工作数据。

还有一个容易误解的点：本章的 `Compile()` 不是执行 `go build`，也不是把 Go 代码重新编译成机器码。它是在程序运行前检查“这张流程图能不能走通、前后步骤的数据是否对得上”，然后生成一份可执行的流程快照。

### 6.1 先用一个四步流程理解执行图和运行状态

`examples/graph/main.go` 中的示例不涉及真实模型服务，它用两个预设回答的智能体演示了最小流程：先研究，再审核，最后输出。这正适合第一次理解执行图：

```text
开始
  -> 研究节点：读用户问题，产出研究结果
  -> 审核节点：读已有消息，产出审核结果
  -> 结束节点：返回收集到的输出
```

对应的工作笔记是：

```go
type teamState struct {
    Messages []schema.Message
    Output   []schema.Message
}
```

为什么不能只把上一个节点的输出直接交给下一个节点？在最简单的直线流程里当然可以，但研究、审核、分支、工具结果都可能同时需要“到目前为止的完整消息”和“最终应返回的消息”。`teamState` 就是这次流程专属的共享草稿纸：`Messages` 保存到目前为止的上下文，`Output` 保存最终要交给调用方的结果。

下面几行也来自这个示例，省略了错误处理：

```go
builder := graph.NewGraph[[]schema.Message, []schema.Message]("research-team")
builder.SetStateFactory(func(_ context.Context, input []schema.Message) (*teamState, error) {
    return &teamState{Messages: schema.CloneMessages(input)}, nil
})
builder.AddEdge(graph.Start, "research")
builder.AddEdge("research", "review")
builder.AddEdge("review", "finish")
builder.AddEdge("finish", graph.End)
team, err := builder.Compile()
```

逐行看：`NewGraph` 声明整个流程的外部输入和外部输出都是消息列表；`SetStateFactory` 说明每次新请求都创建一张新的 `teamState` 草稿纸，并把输入消息复制进去；四条 `AddEdge` 只是把步骤连起来；`Compile` 在真正运行前校验这张图。这里的 `schema.CloneMessages` 很关键，它避免调用方后来改动原切片时，悄悄改坏正在运行的流程。

运行时，节点并不直接拿到整张草稿纸。它应该只拿到自己完成工作所需的输入；节点跑完后，再由图边界代码把结果写回草稿纸。这正是前置、后置处理器存在的原因，后面的第 6.4 节会展开。

### 6.2 构图器与编译后的执行图为什么分离

构图时可以增删节点和边。下面是组装关系的示意，省略了具体类型和错误处理；真正的签名与校验由后面的 `Compile()` 完成：

可以把构图器理解为还在白板上画的流程图：你可以加节点、改边、重新讨论。编译后的执行图则像已经打印好的工作单：一份请求拿着它执行时，不应被另一份请求临时改掉。把两者分开，既允许应用启动时自由组装，也保证运行中的请求有稳定快照。

```go
builder := graph.NewGraph[[]schema.Message, []schema.Message]("research-team")
_ = builder.SetStateFactory(func(_ context.Context, input []schema.Message) (*teamState, error) {
    return &teamState{Messages: schema.CloneMessages(input)}, nil
})
_ = builder.AddNode("research", researcher, graph.WithPreHandler(...), graph.WithPostHandler(...))
_ = builder.AddEdge(graph.Start, "research")
_ = builder.AddEdge("research", graph.End)

compiled, err := builder.Compile()
```

关键点是 `Compile()` 不冻结原构图器。保留空指针检查后的关键源码路径如下：它会先 `cloneBuilder()`，再在副本上验证并生成运行计划：

```go
func (g *Graph[I, O]) Compile() (*CompiledGraph[I, O], error) {
    runtime := g.cloneBuilder()
    if err := runtime.compileGraph(map[uintptr]bool{}); err != nil { return nil, err }
    return compileRuntimePlans(runtime)
}
```

因此构图器可以继续修改、再次编译；`CompiledGraph` 持有的是独立的不可变运行快照，可以被多个请求并发复用。

### 6.3 `Compile()` 具体替你挡掉什么

编译阶段检查的不是表面连通性，而是运行时会造成难以定位错误的契约：

第一次不必逐条背下面清单。先理解它至少替你挡住三类低级事故：节点名字写错导致走不到下一步；上一步输出的是一串消息、下一步却要一个订单号；写了条件分支却没有默认去向，流程不知道该停在哪里。把这些错误放在启动阶段报出来，比让用户请求跑到一半才出错好得多。

```text
起点是否有出口，普通节点是否有出口，节点是否可达终点
边两端的输出/输入类型是否可赋值
条件分支的谓词读的是上游输出还是运行状态，是否产生歧义
条件边是否恰好有一个无条件兜底分支
前置处理器、后置处理器、状态创建函数、状态编解码器的类型是否一致
嵌套执行图是否形成递归环
默认对象格式状态编解码器是否会丢失字段或动态类型
```

`bindRuntimeNode` 用反射确认节点方法长成下面这样：

```go
func(context.Context, Input, ...runnable.Option) (Output, error)
```

同时，`compileRuntimePlans` 还绑定合法的 `Stream`、`Collect`、`Transform` 签名。这样“某个节点在第二分钟才因参数类型不对异常崩溃”的问题被变成启动阶段的 `ValidationError`。

### 6.4 运行状态不污染纯节点：前置、后置处理器

执行图不把业务运行状态塞进每个可执行组件的输入类型。节点依然可以是纯函数；只有图边界的处理器负责把运行状态映射为节点输入，并把输出提交回运行状态：

```go
builder.AddNode("search", searchNode,
    graph.WithPreHandler(func(_ context.Context, s *teamState) (SearchRequest, error) {
        return SearchRequest{Query: s.Messages[len(s.Messages)-1].JoinedText("")}, nil
    }),
    graph.WithPostHandler(func(_ context.Context, s *teamState, out SearchResult) error {
        s.Hits = append(s.Hits, out.Hits...)
        return nil
    }),
)
```

这段代码可以拆成两句人话：前置处理器从 `teamState` 的最后一条消息取出查询词，拼成 `SearchRequest` 交给 `searchNode`；后置处理器拿到 `searchNode` 的 `SearchResult` 后，才把命中结果写回 `teamState.Hits`。因此 `searchNode` 本身只需关心“收到查询词，返回搜索结果”，不必知道自己是研究流程里的第几步，也不必知道整个草稿纸长什么样。

这种拆法有两个直接收益：同一个搜索节点能被别的流程复用；单元测试它时只需要构造 `SearchRequest`，不需要把整张执行图跑起来。对于实习项目，这比把所有数据塞进一个全局变量或超大结构体更容易维护。

运行时顺序是：选边 -> 发节点开始事件 -> 前置处理器 -> 节点 `Invoke` -> 后置处理器 -> 发输出、结束事件 -> 再选边。`PostHandler` 在节点成功返回后才运行，因此它就是这个节点对运行状态的提交边界。

源码中使用 `context.WithoutCancel(nodeCtx)` 来执行提交和选下一个分支，这是有意的：节点已经完成后，不能因为调用方刚好取消而把“已发生的业务输出”和“是否更新内部运行状态”撕成不一致的半状态。它不意味着无视所有超时，而是限定在极小的提交边界内。

### 6.5 条件边和最大步数

图允许循环，例如“模型节点 -> 工具节点 -> 模型节点”的工具循环。因此编译期只能检查静态拓扑，不可能证明业务逻辑一定停下。运行时用 `MaxSteps` 保护：每进入一个节点就计数，超过上限返回 `ExecutionError{Code: "graph.max_steps"}`。

为什么需要最大步数？模型可能因为提示词不好、工具一直失败或服务异常，反复要求调用同一个工具。流程图在结构上允许回到模型节点并不等于应该无限循环。最大步数就是总保险丝：即使业务条件写得不完整，也不会把一次请求变成无限占用资源的任务。

条件谓词可以读取上游输出，也可以读取运行状态。若两者都能赋值给谓词参数，框架直接在编译期报歧义，而不是猜测。

### 6.6 并行节点为什么要复制运行状态

`AddParallelNode` 是显式分叉与汇合边界。每个分支开始时，框架先用状态编解码器序列化基础运行状态，再为每个分支反序列化一份独立副本；所有分支成功后，再由合并器按声明顺序提交。

把并行想成“把一份草稿纸复印给多个同事”。如果研究员和审核员同时在同一张纸上涂改，就会出现数据竞争：谁先写、谁后写、是否覆盖对方都无法保证。框架让每个分支拿自己的副本，等所有人完成后再由一个明确的合并器决定怎样写回原稿。它牺牲一点复制成本，换来确定的并发行为。

```go
// 教学缩略版，真实逻辑见 pkg/graph/parallel.go
data := codec.Encode(ctx, base)
for i := range branches {
    branchState[i] = codec.Decode(ctx, data) // 必须是不同指针
}

runAllBranchesConcurrently(branchState)
if firstErr != nil { return firstErr }       // 不执行 merger
return merger(ctx, base, branchState)        // 按声明顺序，而非完成顺序
```

这解决的是所有权，而不是“给映射加一把锁”。并行分支写自己的运行状态，避免数据竞争；合并器集中处理冲突，例如“保留最高分结果”或“按分支名写不同字段”。任一分支失败时，合并器不执行，基础运行状态不会收到半成品。

### 6.7 执行图流式执行的边界

执行图会在可行时把 `StreamReader` 继续传给下游 `Transform`。但以下情况会强制把流收集为完整值：条件分支必须看完整值、普通节点只支持 `Invoke` 或 `Collect`，以及节点依赖运行状态的前置、后置处理器。文档或面试中不要承诺“整张图始终端到端流式”；正确说法是：

> 执行图会尽量保留数据流；但当控制流或运行状态提交需要完整结果时，就会经过明确的流屏障。

**面试追问：为什么不能在执行图的互斥锁内执行用户节点？**

回答：用户节点可能很慢、发生阻塞、回调执行图，甚至再调用嵌套智能体。锁只保护构图快照和少量运行状态访问；持锁执行用户代码会把吞吐下降、死锁和重入风险全部放大。

## 7. 运行状态与统一检查点

源码入口：`pkg/state/checkpoint.go`、`pkg/state/memory.go`、`pkg/graph/checkpoint.go`、`pkg/graph/checkpoint_state.go`、`pkg/agent/state.go`。

运行中的 State 是节点使用的工作数据；Checkpoint 是把需要保留的数据保存下来的完整记录。会话历史和执行进度都属于同一份 Checkpoint：前者说明已经发生过什么，后者说明流程接下来做什么。它们使用一个 Store、一个会话键和一次原子提交。

例如工具需要人工审批时，检查点既保存当前会话，也保存工具节点的入口 State、待回答的问题和恢复位置。审批后从这份检查点继续；下一轮对话也从其中读取历史，无须协调另一套恢复记录。

### 7.1 检查点保存什么

`state.Checkpoint` 中主要有以下内容：

| 内容 | 字段 | 作用 |
| --- | --- | --- |
| 记录与运行标识 | `ID`、`ParentID`、`RunID`、`ConversationID` | 关联一次运行及其检查点历史 |
| 状态和版本 | `Status`、`Version`、`SchemaVersion` | 区分运行阶段、检查并发冲突和格式兼容性 |
| 会话数据 | `Messages`、`Values` | 保存完整对话和附加业务值 |
| 执行进度 | `Execution` | 保存 State、下一轮任务、汇合等待和人工输入记录 |
| 最终结果 | `Result` | 完成后直接复用结果，无须重复执行节点 |

存储层只负责完整记录的保存、读取、历史查询和删除。Graph 在内部解释 `Execution`，校验图版本、任务关系、交互记录和 State Codec。这种职责分工不需要再暴露独立的恢复对象。

检查点格式统一为 v3；执行进度没有另一个格式版本或创建时间。State Codec 继续有自己的 ID 和版本，因为它描述的是业务 State 的编码方式。

### 7.2 并发写入与恢复

`Store.Save` 同时检查调用方携带的 `Version` 和最新检查点 `ID`。写入成功时分配新的 ID、递增 Version、追加历史并更新最新记录；不匹配则返回 `state.ErrConflict`。Memory 在同一把锁内完成这些操作，Redis 通过 Lua 脚本原子提交。

例如两个请求都基于版本七更新同一会话，第一个保存成功后版本变为八，第二个仍带版本七的请求会被拒绝。Version 表示保存次数，不是对话轮数，也不是检查点格式版本。

配置检查点后，运行开始、每轮提交、人工中断和运行完成都会保存。sync 等待每轮写入成功再推进；默认 async 允许执行与写入重叠，并在退出前等待后台写入结束。人工中断、接受输入和完成结果始终同步保存。

`graph.InterruptedError.Checkpoint` 返回已经保存的记录副本，包含实际 ID 和版本；`PendingInterrupts()` 返回需要回答的问题。恢复时仍使用原来的 Store 和会话键调用 `Resume`。完整记录通过 `Checkpoint.JSON()` 导出、`state.DecodeCheckpoint` 解码，无需再单独导出执行进度。

### 7.3 恢复数据，不恢复协程

检查点不保存 Goroutine、网络连接、互斥锁、回调对象或模型客户端。恢复会重新创建运行环境，解码 State，再从记录的任务边界执行。图版本或 Codec 不兼容时明确拒绝恢复。

如果工具扣款成功后，进程在保存下一份检查点前退出，恢复时仍可能再次执行扣款节点。框架提供的是至少一次执行语义，业务写操作需要幂等键、去重记录或事务；检查点的版本检查只能避免记录相互覆盖，不能撤销已经发出的外部调用。

普通取消和超时不会额外生成中断记录，但此前已成功保存的执行进度仍可恢复。显式中断则会同步保存检查点，保存失败时不能返回“已挂起”。

## 8. `tool`：把副作用关进一个可治理的运行环境

源码入口：`pkg/tool/tool.go`、`node.go`、`runtime.go`、`runtime_scheduler.go`、`middleware.go`、`batch_hook.go`。

工具的难点不是“调用一个函数”，而是这个函数可能访问文件、网络、数据库或付款接口。模型提供的参数不可信，调用可能超时、异常崩溃、递归、并发争用，也可能已经成功但响应丢失。

先去掉“工具很神秘”的错觉：工具的核心仍然是一段 Go 函数。`examples/basic/main.go` 用一个最小的回显工具演示了这一点：

```go
echoTool := tool.NewFunctionTool(tool.Spec{
    Name:        "echo",
    Description: "Return the text field from arguments.",
    Parameters: map[string]any{
        "type": "object",
        "properties": map[string]any{
            "text": map[string]any{"type": "string"},
        },
        "required": []string{"text"},
    },
}, func(ctx context.Context, input tool.CallInput) (tool.Result, error) {
    return tool.TextResult(fmt.Sprint(input.Args["text"])), nil
})
```

这里有两层含义：`Spec` 是写给模型和框架看的说明书，告诉它工具叫什么、参数应长什么样；最后那个函数才是真正执行业务的处理函数。模型只会提出“请调用 `echo` 并给参数”，它不拥有数据库连接、文件权限或租户身份。真正的调用仍由本地 Go 代码控制。

因此，工具层的目标不是决定模型聪不聪明，而是把已经决定要执行的外部副作用关进有边界的地方：参数不合法要拒绝；需要审批先暂停；超过时间要停止；写操作不能盲目重试；多个调用不能无上限并发。

### 8.1 工具的最小抽象

```go
type Spec struct {
    Name        string
    Description string
    Parameters  map[string]any
    FileAccess  bool
    IsReadOnly  bool
    Concurrency ConcurrencyPolicy
}

type Tool interface {
    Spec() Spec
    runnable.Runnable[CallInput, Result]
}
```

`Spec` 同时服务三方：模型看到 `Name`、`Description`、`Parameters`，中间件读取安全属性，调度器读取并发组。`Parameters` 会暴露为模型可见的结构化参数约束；但当前 `Spec.Validate` 主要验证名称和并发策略，并不会自动完整校验参数内容。因此租户归属、金额范围、文件路径等业务验证仍应由中间件或处理函数完成。

这一点很重要：参数说明能帮助模型按格式生成调用，但不能替代业务鉴权。比如“转账金额必须小于一万元”“只能查看自己的订单”都依赖当前登录用户和业务规则，不可能只靠模型生成的一段参数文本保证。身份来自可信请求上下文，而不是模型说“我是管理员”。

`CallInput` 有解析后的 `Args`、原始参数、共享网络客户端、消息快照、文件列表和元数据；身份不在这里，而应由 `WithSubject` 放进请求上下文。身份来自可信调用链，不能让模型在工具参数中伪造。

`Result` 又一次区分两类失败：

```go
tool.ErrorResult(schema.NewTextBlock("not found")) // 模型可见结果，Go error 为 nil

return tool.Result{}, errors.New("database unreachable") // 运行时执行失败
```

第一次读到这里时，先按“能不能继续当前流程”区分：找不到订单是模型可以理解并换一种查询方式的业务结果，所以放在 `Result` 里；数据库连接完全不可用是当前工具执行环境出了问题，返回 Go 语言的 `error`。前者会作为一条工具结果消息交回模型，后者由执行图决定是停止、重试还是向上报错。

前者通常继续进入下一轮模型调用，让模型改写策略；后者由 `ToolsNode` 转换成关联原调用标识的工具角色错误消息，模型仍可看到问题并修正。只有批次审批错误、请求上下文取消等控制错误会直接向上返回。

### 8.2 `ToolsNode` 为什么只执行尾部调用

`TailToolCalls` 从消息尾部向前扫描连续的助手工具调用消息，遇到非助手或无调用消息就停。历史调用不能被重新执行：

把 `ToolsNode` 想成工具调用的收银台：模型刚给出的、排在消息末尾的一批调用才是待处理订单；很久以前已经处理过的调用只是历史凭据，不能因为下一轮又经过工具节点就再扣一次款。只处理尾部连续调用，就是用消息顺序划出“本轮待执行”和“历史已完成”的边界。

```text
... 旧的工具结果
... 助手的新工具调用   <- 只处理这里及连续尾部
```

`ToolsNode.Invoke` 的顺序很重要：

```text
严格复制消息
  -> 提取消息尾部连续的工具调用
  -> 对“已知工具 + 完整对象参数”组成批次
  -> 执行批次前置钩子
  -> 并发执行每个工具调用
  -> 按原调用顺序排列结果
  -> 返回只追加的工具角色消息
```

未知工具或参数解析失败不会进入运行环境，而会得到模型可见的错误结果。审批钩子只看到可执行的已知、已解析调用，避免让审批界面对半截对象参数作判断；钩子返回 `InterruptRequest` 时，任何工作协程都还没启动。

并发不会改变消息顺序。源码为每个结果保留原始位置，最终填入同长度的 `output[index]`，所以模型下一轮看到的工具结果顺序仍等于调用顺序，而不是哪个工具先完成。

### 8.3 工具运行环境的保护层次

```text
工具节点调用槽位            : 一次工具批次最多同时启动多少调用
调用作用域信号量            : 该作用域的并发上限
运行环境工作协程            : 一个运行环境的全局执行上限
调度器分组限制器            : 同类外部资源共享的并发上限
```

```go
return r.invokeMiddleware(...)
```

随后，工具中间件持有 `next`，所以它能做鉴权、补充租户标识、改写参数、拒绝调用或包裹输出。运行环境对 `next` 的有效期有额外约束：中间件的 `Handle` 返回后，异步保存下来的 `next` 不可再调用，避免绕过当前调用的资源边界。

中间件可以理解为函数外面的一层安检门：调用真正业务函数前检查身份、补充租户；调用后记录审计或统一转换错误。它和回调的关键区别是中间件拿到 `next`，能决定要不要放行；回调只能旁观，不能可靠阻断。

下面是应用层鉴权中间件的示例，不是框架内置实现：

```go
type Middleware interface {
    Handle(ctx context.Context, spec Spec, input CallInput, next Next) (Result, error)
}

func authorize(ctx context.Context, spec tool.Spec, in tool.CallInput, next tool.Next) (tool.Result, error) {
    subject, err := tool.RequireSubject(ctx)
    if err != nil || !subject.HasPermission("tools:write") {
        return tool.Result{}, tool.Deny(errors.New("permission denied"))
    }
    in.Args["tenant_id"] = subject.TenantID
    return next(ctx, in)
}
```

超时、取消、异常崩溃、递归深度、权限拒绝和死锁风险属于“保护错误”。当中间件已经调用 `next` 后，运行环境会记录下游出现的保护错误；即使中间件随后返回 `nil`，该错误仍会向上返回。反过来，一个从不调用 `next` 的中间件，就是在显式作出允许、拒绝或短路决定，必须由应用自己保证其业务语义。

### 8.4 为什么只重试只读工具

`invokeTool` 的次数计算是：

```go
attempts := 1
if spec.IsReadOnly {
    attempts += r.config.MaxRetries
}
```

写工具可能已在服务器完成扣款或创建资源，只是响应在网络上丢失。自动重试会制造重复副作用。只读并不自动等于安全，但至少是框架能够做出的保守默认；写操作若要重试，应由业务提供幂等键并显式实现策略。

面试时不要把“只读”说成“永远没有风险”。它只是相对安全：重复查两次订单通常只是多一次请求，重复创建订单则可能产生两笔数据。即使工具自称只读，也仍可能慢、失败、泄露权限或打满外部服务，所以超时、鉴权和并发限制仍然需要。

### 8.5 并发组与死锁风险

`ConcurrencyPolicy` 将同类资源放入具名组。嵌套工具调用要按组名严格递增获取锁；如果当前持有“网络”组又请求排序更小的“数据库”组，`detectDeadlock` 返回 `DeadlockError`。这不是万能死锁检测器，而是给可控资源建立统一获取顺序。

**面试追问：为什么工具运行环境不负责“模型该不该调用工具”？**

回答：模型策略属于智能体、提示词和执行图路由；运行环境的职责是“既然决定调用，就让这次副作用可验证、可限制、可审计”。把决策和执行安全混在一起，会使运行环境既难复用也难测试。

## 9. `llm`：模型服务适配与流式协议必须先标准化

源码入口：`pkg/llm/model.go`、`node.go`、`openai_compatible.go`、`sse.go`、`response_stream.go`、`delta.go`、`retry.go`、`rate_limit.go`。

执行图不依赖某一个模型厂商。它看到的是以下协议：

先明确边界：这一包不训练模型，也不决定提示词该怎么写。它只做适配工作。项目内部统一使用 `schema.Message` 表达消息；不同模型服务各有不同的请求格式和持续输出格式；模型适配层把前者编码成服务能听懂的请求，再把后者翻译回项目统一的消息格式。这样工具节点、执行图和智能体就不需要到处判断“当前接的是哪一家模型服务”。

```go
type ChatModel interface {
    runnable.Runnable[Request, Response]
    Capabilities() Capabilities
    ModelInfo() ModelInfo
}

type Request struct {
    Messages  []schema.Message
    Functions []schema.FunctionDefinition
}
```

`ChatModelNode` 将这个模型包装成有名称、能力描述和生命周期回调的执行图节点。它不负责上下文拼装和运行状态更新，那些留给智能体配方的前置、后置处理器，避免“模型节点知道整个智能体”这种耦合。

可以把 `ChatModelNode` 看成执行图里的“模型插座”：它只知道怎样把一份模型请求交给模型，并拿回模型响应；“这一轮对话要带哪些历史消息”“模型返回工具调用后要走哪个节点”不在它这里决定。把这两层拆开后，同一个模型节点既能用于简单对话，也能用于带工具、带审批的流程。

### 9.1 兼容模型服务协议的适配器做了什么

`OpenAICompatibleModel` 将 `schema.Message` 编码为对话补全请求，检查服务地址能力是否支持流式输出和工具调用，复用 `httpclient` 的连接池，再把普通网络响应或服务器推送事件解码回标准响应。

“兼容”不是说所有模型服务行为完全相同，而是说它们使用相近的对话请求和持续输出约定。适配器会在边界处处理差异：哪些服务支持工具调用，流结束如何表示，工具参数片段怎样拼接。业务层不应该直接拿服务商返回的原始数据做判断，否则更换服务时会把改动扩散到工具、智能体和界面。

服务器推送事件解析器 `parseSSE` 处理多行 `data:`、空行分隔、注释、读取缓冲区上限和请求上下文取消。上层 `streamEvents` 只有收到完成标记 `[DONE]` 才发出 `wireEventDone`。这条规则非常关键：网络连接直接关闭不等于模型正常完成。

```text
完成标记                -> 正常完成，交付最终响应
服务器推送事件解析或网络错误 -> CloseWithError(err)
通道提前关闭            -> "stream closed without completion" 错误
```

`responseReaderFromWire` 用 `DeltaAccumulator` 合并文本、推理内容和工具调用片段。工具调用不能简单地把所有字符串拼起来，因为并行工具调用各自有序号、调用标识、名称和参数片段；内容块类型改变时会报错，防止把不同语义硬合并。

这段合并逻辑是流式工具调用最容易漏掉的地方。模型可能先发“我要调用工具甲”，下一段才发工具名称，再随后才发参数的一部分；同时也可能发起工具乙。适配器必须按调用标识和顺序把片段归到正确调用上，等参数完整后再交给工具层。若直接把所有片段拼成一长串文字，工具层无法可靠知道该执行什么。

最终响应交付前会附上 `ResponseMeta` 并逐条 `Validate`。因此下游 `ToolsNode` 接到的不是半截参数，而是经过协议收口的完整消息。

### 9.2 流式重试为什么保守

`RetryingModel` 只在尚未向消费者交付任何响应时重试。一旦用户已经看到一段输出，再换一次请求可能重复文字、重复工具调用或破坏交互顺序。默认可重试对象包括网络错误、四百零八、四百二十五、四百二十九以及五百类状态码；取消与超时不重试。

这条规则体现了一个实习面试常见的取舍：重试不是越多越好。还没把任何内容给用户时，失败后换一次请求通常无感；已经给出“您好，我来查订单”后再从头请求一次，用户可能看到两段重复开头，模型还可能再次请求同一个工具。因此框架宁可保守失败，也不在用户已经看见部分结果后悄悄重放。

`RateLimitedModel` 则用信号量控制并发、用 `nextAllowed` 控制最小间隔；流结束或消费者关闭时才释放配额。它包装的是模型调用频率，不是整个智能体的工具并发。

**面试追问：执行图的 `Stream` 和模型的 `Stream` 有什么不同？**

回答：模型流是模型服务响应的增量协议；执行图流是多个节点之间尽可能连续传递的数据流。执行图可能在分支或运行状态边界收集模型流，最终智能体还会通过 `MessageEvent` 向展示端发快照。三者不能混为同一个通道。

## 10. `contextengine`：每次调用模型前，重新计算上下文是否仍然合法

源码入口：`pkg/contextengine/engine.go`、`builder.go`、`token.go`。

模型上下文不是“永久历史 + 新输入”简单相加。工具调用会不断追加消息，模型有窗口上限，角色序列也可能不再符合模型服务约束。因此 `ContextBuilder` 是一个标准的 `Runnable[Request, Result]`，在每次模型节点的前置处理器中调用。

这里有两个完全不同的“上下文”，务必分开：

```text
Go 的 `context.Context`
  -> 这次请求是否取消、何时超时；第 3、4 章讨论的是它。

模型上下文
  -> 这次真正发送给模型的消息集合；本章讨论的是它。
```

模型上下文可以理解为“把哪些聊天记录放进这次提问的信封里”。模型没有自动记忆每次请求；你发给它的消息越多，它能参考的历史越多，但也会更慢、更贵，并最终超过服务允许的长度。因此每次调用模型前都需要重新整理，而不是只在会话开始时整理一次。

```go
type Request struct {
    Pinned               []schema.Message // 永不裁剪的稳定前缀
    History              []schema.Message
    Input                []schema.Message
    MaxContextTokens     int
    ReservedOutputTokens int
}
```

这三个消息来源的职责不同：`Pinned` 是绝对不能裁掉的稳定前缀，通常放系统提示词或必须遵守的规则；`History` 是历史会话，可在空间不足时从最早部分裁剪；`Input` 是用户刚发来的新消息，通常最不应该丢。理解这个优先级后，下面的算法就不再是难记的七步名单，而是在回答“空间不够时，先舍弃什么”。

核心算法按这个顺序运行：

```text
1. 可用预算 = 最大上下文 - 预留输出
2. 复制稳定前缀；把主体中的系统消息也移到稳定前缀
3. 校验稳定前缀，修复或拒绝其余消息角色
4. 按完整用户轮次丢弃最老历史
5. 若仍超限，优先删除推理内容块，再截断顶层文本
6. 若稳定前缀或不可裁剪开销仍超限，返回预算错误
7. 在稳定前缀末尾标记提示词缓存断点
```

为什么按用户轮次而不是按消息条数裁剪？一轮用户问题可能包含助手工具调用与工具角色结果。只删中间一条会留下没有调用来源的工具结果，模型服务和模型都难以理解。`splitTurns` 保留这层关系。

角色策略有修复模式与严格模式，对应源码配置值 `repair` 和 `strict`：前者会丢掉无法配对的助手、工具消息并记录 `RoleRepairs`，后者立即报错。生产环境的选择取决于输入是否来自可信历史；不能把修复模式当成静默吞数据的万能开关。

为什么角色顺序也要整理？工具结果不是独立聊天内容，它必须能对应到前面的一次助手工具调用。假如历史裁剪掉了“请调用查订单工具”，却留下“订单号不存在”的工具结果，模型不知道这句结果从哪里来，甚至有些模型服务会直接拒绝这组消息。修复模式适合接收可能被人为截断的旧历史；严格模式适合你确信历史一定正确、希望发现任何数据问题的场景。

### 10.1 提示词缓存对齐不等于框架结果缓存

当配置启用且稳定前缀足够长时，构造器只会在前缀最后一条消息 `Extra` 中写入模型服务约定的 `prompt_cache` 断点：

```go
prefix[last].Extra[key] = map[string]any{
    "type": "ephemeral", "breakpoint": true, "scope": "stable_prefix",
}
```

它不保存响应、不设置过期时间、不保证命中。是否命中由模型服务返回的 `CacheReadTokens`、`CacheWriteTokens` 说明。这个边界能避免面试中把“请求缓存标记”误说成“结果缓存”。

可以把它理解成给模型服务一个提示：“前面这段稳定内容经常重复，你可以尝试复用。”项目本身没有把模型答案存起来，也没有决定多久过期。真正的模型结果缓存位于扩展包，且对带工具调用的请求会更谨慎，因为缓存一次工具调用结果可能改变外部副作用。

**面试追问：上下文整理器在执行图的哪一层？**

回答：在内置智能体的模型节点前置处理器内，每次要调用模型前执行。自定义执行图直接放 `ChatModelNode` 时，不会自动获得上下文治理，调用方应在自己的前置处理器或包装节点中接入它。

## 11. 检索与网络请求：它们是能力组件，不是智能体的隐藏特权

源码入口：`pkg/retrieval/types.go`、`chunk.go`、`indexer.go`、`hybrid.go`、`context.go`，以及 `pkg/httpclient/service.go`、`pool.go`。

检索包用 `Runnable` 描述文本切分、向量化、向量存储、关键词检索和重排序等外部能力。它们可以作为执行图节点，也可以被智能体的一个领域节点调用；核心执行图不需要知道向量数据库的名字。

如果你当前只准备基础智能体或工具调用面试，这一章可以先快速读完，再第二遍深入。它不改变前面“消息 -> 模型 -> 工具”的主线，而是给智能体增加一种能力：在提问模型前，先从自己的文档库里找出相关资料，放进模型上下文。

“向量化”也不需要先学数学。可以先把它理解为：把一段文字转换成一组便于按语义比较的数字；相似的文本在数字空间中通常更靠近。检索包负责切分、生成这些数字、保存和查询；模型层只拿到最后挑出来的文字资料，不需要知道底层用了哪种数据库。

### 11.1 从文档到向量：`DocumentIndexer`

`TextChunker` 先按字符位置切片，避免按字节位置切开中文字符。它在词元上限内优先寻找段落、句子、行和词边界，再根据重叠长度回退。片段标识由文档标识、内容摘要和重复出现次数构成，既可追溯也能避免相同片段冲突。

为什么不能整篇文档直接交给模型？一份员工手册可能很长，既超过模型上下文限制，也会让无关内容干扰回答。切分器优先在段落或句子边界切开，并保留一小段重叠内容，目的是防止一个关键信息刚好被切在两段之间后失去上下文。

`DocumentIndexer` 再将分片批量向量化并写入：

```text
Document
  -> TextChunker
  -> 受限并发的向量化批次
  -> 验证每批向量数量与维度
  -> 受限并发的写入批次
  -> 索引统计
```

任一向量化工作协程出错会取消其余工作协程；已经生成的局部向量不会作为成功结果返回。这和执行图并行分支的原则一致：失败时不要伪造完整产物。

`HybridSearcher` 并发发起向量检索与关键词检索，再按倒数排名融合或加权策略融合，可选最大边际相关性多样性和重排序。`HybridRetriever` 则把命中结果变成带引用头、受词元预算限制的文本，方便放入模型上下文。

这里的“混合”并不神秘：关键词检索擅长精确名称、编号和错误码；向量检索擅长同义表达和自然语言问题。两种结果各有盲区，所以先各自查一遍，再把排名合并。最大边际相关性用于避免选出十段几乎相同的资料；重排序则让更精确但计算更贵的步骤只处理少量候选。作为初学者，先记住每一步都能独立替换和测试，比记住融合公式更重要。

### 11.2 为什么单独提供网络客户端池

模型、向量库、搜索和模型上下文协议都要发网络请求。若每个适配器自己创建 `&http.Client{}`，连接复用、超时和空闲连接回收就会分裂。`httpclient.Pool` 共享一个 `http.Transport`，但可为不同超时返回不同客户端：

这部分和业务无关，却经常在实习代码里出问题。网络连接建立有成本，反复创建客户端会让连接无法复用，也让每个调用各自决定超时。共享连接池把“怎样发请求、怎样回收空闲连接、怎样限制错误响应体大小”收在一个地方；模型、检索和远程工具只声明自己要访问哪个服务和多久超时。

```text
不同服务 / 不同超时
            |
            v
      同一个传输层
            |
            v
  每个目标主机各自维护空闲连接池
```

`Service.NewRequest` 只接受相对路径，防止一个调用绕过配置好的基础地址。`DoJSON` 限制错误响应体的读取大小，避免错误响应把内存吞掉。

**面试追问：检索器为什么不直接塞进上下文整理器？**

回答：上下文整理器的职责是对已有消息做预算与协议整理；检索是主动的外部输入输出和召回策略。两者可以串联，但混成一个组件会让上下文裁剪、向量调用、缓存和权限边界无法独立测试。

## 12. `agent`：标准场景的执行图配方，不是另一套运行环境

源码入口：`pkg/agent/new.go`、`base.go`、`basic.go`、`react_agent.go`、`routing.go`、`hub.go`，核心图组装在 `internal/agentrecipe/recipe.go`。

`agent.New` 的选择非常直接：有工具就创建工具循环智能体，没有工具就创建基础对话智能体。

这一包可以理解为“标准流程装配厂”，不是新的执行引擎。前面已经有消息格式、统一调用协议、执行图、工具运行环境和模型节点；智能体层只根据常见场景把这些零件按正确顺序接好，并提供更容易使用的 `Invoke`、`Stream`、会话和恢复入口。

第一次读这一包时，不要从 `base.go` 的许多配置项开始。先问两个业务问题：这次模型能不能调用工具？如果能，工具结果回来后是否还要再问一次模型？答案分别对应基础对话和工具循环。

```go
func New(cfg BaseConfig, opts ...Option) (Agent, error) {
    resolved, err := resolveBaseConfig(cfg, opts...)
    if err != nil { return nil, err }
    if len(resolved.Tools) > 0 {
        return NewReactAgent(ReactAgentConfig{BaseConfig: resolved})
    }
    return NewBasicAgent(resolved)
}
```

`base` 统一完成这些装配工作：构造 `ChatModelNode`、构造 `ToolsNode`、保存工具定义顺序、提供默认 `ContextBuilder`、设置会话存储与每次运行的上限。它不自己运行循环。

`base` 的名字容易让人误会成“什么都做的父类”。在这里它更像一个共享装配箱：基础对话和工具循环都需要模型节点、工具定义、上下文整理器和会话存储，所以放在一起创建；真正的流程差异仍交给不同配方。这样增加一个新智能体类型时，不必复制一套模型和工具初始化代码。

### 12.1 工具循环执行图到底长什么样

`internal/agentrecipe.NewToolRecipe` 创建 `Graph[[]schema.Message, []schema.Message]`，其运行状态是每次运行独占的 `RecipeState`。简化后的拓扑是：

“配方”可以直接理解为预制流程图。它不是用户的业务逻辑，也不是模型本身；它描述的是“先模型、再根据结果决定是否工具、再回模型”的通用骨架。你的业务通过模型提示词、工具实现和前置、后置处理器填进去。

```text
开始（源码名为 `START`）
  |
  +--> 结束节点（源码名为 `finish`）  (已达到最大模型调用次数)
  |
  v
 模型节点
  | \
  |  +--> 结束节点  (没有工具调用)
  v
 工具节点
  |
  +--> 模型节点

结束节点 -> 结束（源码名为 `END`）
```

模型节点的前置处理器读取 `state.Messages`，通过 `base.prepareLLMRequest` 调用上下文整理器，附上当前可用工具定义；后置处理器追加模型消息、解析调用、增加模型调用次数，并决定 `HasCalls`。工具节点的前置处理器把当前调用规范化到消息尾部，随后由 `ToolsNode` 自己执行尾部调用；后置处理器将结果追加为观察消息，再回到模型节点。

这里还有一个容易漏掉的兼容边界：`detectReactActions` 同时识别结构化的 `FunctionToolCall` 和文本中的 `Action:` / `Action Input:`。`toolNodeInput` 会把后者转换成规范的助手工具调用消息，再交给 `ToolsNode`。因此传统的“思考、行动、观察”提示词也能运行；但生产接入应优先使用结构化调用，因为只有它从模型服务到 `schema` 都保留了调用标识与参数协议。

这段设计值得面试时强调：工具循环并不写在 `for {}` 里，而是编码为可编译、可观测、可中断、可恢复的执行图边。`MaxLLMCalls` 是模型成本和无穷循环的第二道保护，第一道是执行图的 `MaxSteps`。

为什么不直接写一个循环？小示例当然可以，但循环写在智能体内部后，审批中断、每步事件、运行状态快照、统一步数限制都要单独补；而执行图已经有这些能力。配方把“回到模型”表示为一条边，因此中断和恢复时，框架知道自己停在模型前还是工具前，不必猜测循环执行到了第几行。

### 12.2 基础对话、路由与群聊的关系

| 类型 | 额外规则 | 底层复用 |
| --- | --- | --- |
| 基础对话 | 一次模型调用，不允许工具 | `ToolRecipe` 的无工具图 |
| 工具循环 | 模型与工具循环 | `ToolRecipe` 的有工具图 |
| 路由 | 根据路由结果选择子智能体 | 执行图 + `RoutingRecipe` |
| 群聊 | 多个智能体按轮次选择发言人 | 执行图 + `GroupRecipe` + 发言枢纽与选择器 |

路由和群聊的复杂度主要在运行状态中的路由轮次、已选智能体、待处理调用和恢复后的重建，不在“又实现一个执行器”。这就是把执行图作为唯一编排引擎的收益。

对于第一次实习，通常不需要先实现路由或群聊。先能写好“基础对话”和“一次工具循环”更重要；理解它们后会发现，路由只是根据一个结果选下一条边，群聊只是把多个智能体放进同一份运行状态里轮流执行，底层机制没有变。

### 12.3 智能体的两个持久化开关

`agent.WithConversationID` 使用 `state.Store` 保存长期会话；`agent.WithCheckpoint` 把 `graph.WithCheckpoint` 放入本次执行图运行选项，用于审批后继续运行。两者的键、存储接口和语义都独立。

```go
conversation := agent.WithConversationID("customer-17") // 长期历史
execution := agent.WithCheckpoint(store, "order-991:approval") // 本次中断恢复

out, err := assistant.Invoke(ctx, input, conversation, execution)
if errors.Is(err, graph.ErrInterrupted) {
    out, err = agent.Resume(ctx, assistant, execution)
}
```

把这两者混成“一个检查点”是典型面试失误：会话可能持续数月，而执行图恢复记录只对应一次暂停在某节点边界的工作流。

可以用一句判断避免混淆：下次用户重新聊天时还要不要读它？要，就用会话检查点；这次流程审批通过后要不要从暂停点接着跑？要，就用恢复记录。两者可以同时存在，但一个不替代另一个。

## 13. `extensions`：核心只依赖接口，具体基础设施向外扩展

`extensions` 是独立的 Go 模块。这样核心 `pkg` 不需要因为键值数据库实现、模型上下文协议客户端库或缓存驱动把所有使用者拉进依赖树；应用按需引入实现。

把核心包和扩展包分开，解决的是依赖边界，而不是目录好看。假如只想跑内存会话和本地工具，却因为框架默认依赖外部键值数据库、远程工具协议和缓存客户端而必须安装所有依赖，使用成本会很高。核心包只定义“需要一个能保存会话的东西”“需要一个能调用工具的东西”的接口；扩展包再提供具体实现。

对初学者的学习策略是：先看接口知道核心希望得到什么能力，等项目真的需要某种基础设施时再看对应扩展。不要在第一次阅读时就钻进所有外部客户端的连接细节。

### 13.1 模型上下文协议如何变成普通工具

源码入口：`extensions/mcp/mcp.go`。

模型上下文协议的 `Client.Initialize` 建立客户端会话，`RefreshTools` 拉取 `tools/list` 并将每一个远程定义转换为 `tool.Tool`。`MCPTool.Spec()` 提供模型可见的参数说明，`MCPTool.Invoke()` 调用远端 `tools/call` 并把文字、图片、音频和结构化结果映射为 `schema.ContentBlock`。

它解决的不是“远程工具有什么魔法”，而是“远程工具也要遵守本地工具的安全边界”。远端服务把可用工具列表告诉客户端，扩展包把每个远端定义包装成普通 `tool.Tool`；此后工具节点仍按同一条路径做参数处理、审批、并发限制和消息转换。核心执行图无需为远端协议再写一套分支。

`DynamicToolsNode` 在收到 `tools/list_changed` 通知后标记需要刷新；下一次调用重新拉取工具列表并原子替换内部 `ToolsNode` 快照。正在执行的旧调用不被中途改变，新调用才看见新的参数说明。这比把远程列表直接暴露成可变映射更容易解释并发行为。

### 13.2 键值存储与缓存解决的各自问题

`extensions/state/redis.RedisStore` 实现的是 `state.Store`，用 Lua 写成的比较并交换操作保持和 `MemoryStore` 相同的乐观版本语义。它不是执行图恢复记录存储，也不是分布式继续运行锁。

这一节容易被“缓存”一词带偏。键值数据库会话存储解决的是“多台应用机器都能读到同一份长期会话”；模型结果缓存解决的是“完全相同、且没有工具副作用的请求不必重复问模型”；向量查询缓存解决的是“相同检索问题不必重复查向量库”。它们都在存数据，但数据含义、失效条件和安全边界不同，不能因为都叫缓存就共用一套粗糙规则。

模型结果缓存包装 `llm.ChatModel`，会按租户、模型和完整请求生成键。默认配置会绕过附带函数定义的请求；即使一次普通请求最终返回了 `FunctionToolCall`，也不会写入缓存，避免缓存改变副作用语义。向量查询缓存则包装向量存储：查询命中可复用，写入或删除成功后通过“数据版本号”使旧键失效，而不扫描全量前缀。两者都保证同一份未命中请求在同一时刻只放行一条后端请求，避免同时击穿后端。

**面试追问：为什么不把缓存写进上下文整理器？**

回答：提示词缓存对齐、模型结果缓存和向量查询缓存分别处于请求组装、模型响应和检索存储三个边界，失效条件与安全条件完全不同。放进一个“大缓存组件”会把这些语义混掉。

## 14. 把组件串起来：一次工具循环智能体调用的完整剖面

下面以“模型调用 `lookup_order`，需要人工审批”走一次真实的因果链。

先看不带审批的主线，只要记住五步：用户消息进入；模型决定要不要工具；工具返回结果；模型组织最终文字；消息返回给调用方。审批、恢复、流式展示和会话保存都在这条主线的明确边界上插入，不能随意插到中间。

```text
用户“查订单”
  -> 统一消息
  -> 上下文整理后发给模型
  -> 模型请求查订单工具
  -> 工具返回订单数据
  -> 连同订单数据再问模型
  -> 模型生成面向用户的回答
```

现在再加入审批：工具真正执行前，批次前置钩子发现还没有批准，便发出带类型中断；执行图把“停在哪里、草稿纸里有什么”存成恢复记录；审批通过后调用 `agent.Resume`，从工具节点的安全边界重新进入。注意它不是从头把整个聊天重跑一遍，也不是在原来的协程里继续，因为原协程可能早已随着请求结束。

下面的详细版本中，首次阅读时优先看每一大步的第一行；缩进的行是该步为什么由对应组件负责：

```text
1. 调用智能体的 `Invoke`
   - 智能体解析调用选项
   - 若带会话标识，加载 `state.Checkpoint`
   - 创建本次 `RecipeState`

2. 执行图进入模型节点
   - 前置处理器从 `RecipeState` 取消息
   - 上下文整理器计算预算、修复角色、裁剪历史
   - `ChatModelNode` 开始回调，调用模型服务
   - 服务器推送事件的增量经 `StreamReader` 传递；展示端可经实时事件流查看快照

3. 模型完成，得到带工具调用内容块的助手消息
   - 后置处理器追加消息，记录调用与模型调用次数
   - 条件边命中工具调用，转到工具节点

4. `ToolsNode` 准备执行
   - 只取消息尾部连续的调用
   - 严格解析对象参数，构造可执行批次
   - 批次前置钩子返回 `InterruptRequest`

5. 执行图在安全边界保存恢复记录
   - 保存 `RecipeState` 的编解码快照、恢复节点、步数和图版本
   - 返回 graph.ErrInterrupted

6. 审批系统保存凭证后调用 `agent.Resume`
   - 校验执行图版本和编解码器
   - 从工具节点边界重新进入批次前置钩子
   - 钩子从可信请求上下文或外部存储读取审批凭证

7. 工具运行环境执行 `lookup_order`
   - 限制并发、超时和组锁
   - 中间件做身份与租户校验
   - 结果转换为工具角色和工具结果内容块

8. 执行图回到模型节点
   - 新消息变多，上下文整理器再执行一次
   - 模型给出最终回答，finish 节点输出

9. 智能体成功后提交长期会话检查点
   - 写入本轮输入和非系统提示词输出
   - 最终消息切片交付调用方
```

把这九步换成可面试的因果表达，就是：消息协议保证模型和工具能看懂彼此；上下文整理保证消息没有超限；模型适配保证外部服务返回的数据能变回统一消息；工具层保证副作用可限制；执行图保证循环、暂停和恢复有明确位置；会话检查点保证下一轮还能读到已完成历史。每一层只解决一个问题，因此某一层替换或出错时，不必让其他层也跟着重写。

这条链也解释了几类常见故障：

| 现象 | 第一处该看哪里 | 为什么 |
| --- | --- | --- |
| 浏览器断开后模型还占资源 | `StreamReader.Close`、模型服务流的取消传播 | 消费者关闭应反向解除上游阻塞 |
| 模型重复调用历史工具 | `TailToolCalls`、配方的消息追加 | `ToolsNode` 只处理连续尾部调用 |
| 审批后重复扣款 | 恢复记录中断点、业务幂等键 | 继续运行属于至少一次，不等于恰好一次 |
| 回调写日志失败导致请求异常 | 处理器调用点是否错误传播了 `Dispatch` 错误 | 观察与业务控制被混用 |
| 上下文超限但历史没被裁剪 | `Pinned` 是否过大、`BudgetError.Reason` | 稳定前缀永不裁剪 |
| 并行检索或执行图运行状态竞态 | 状态编解码器是否产生独立指针 | 不能只依赖“大家小心不要改映射” |

## 15. 面试表达：从“我会用”讲到“我理解为什么这样设计”

实习面试不需要假装自己已经设计过所有基础设施。更可信的表达是：先说一个用户场景，再说这个场景会遇到的风险，然后指出源码把风险放在哪一层处理。只报类型名、包名或概念词，面试官通常会继续追问“为什么这样拆”；能说出前因后果才说明真的读懂。

一个通用回答模板是：

```text
先说场景：用户请求在什么情况下会出问题？
再说风险：不处理会产生什么错误、资源浪费或重复副作用？
最后说设计：哪个组件在什么边界处理，源码中的哪段规则证明它？
```

例如被问“为什么工具只重试只读调用”，不要从“重试机制”开始背。可以说：“网络响应丢失时，扣款可能已经成功；框架无法确认是否成功，因此自动重试写操作会重复扣款。`tool` 包只给 `IsReadOnly` 工具增加重试次数，写操作需要业务方自己给幂等键。”这就是场景、风险、设计和源码规则连在一起的回答。

### 15.1 三十秒版本

> 这个项目把一次智能体请求拆成可组合的步骤。消息层保存用户、模型和工具之间真实发生的内容；执行图负责下一步走哪里，并把本次流程的数据放在独立工作笔记里；工具层负责外部调用的审批、超时、权限和重试；模型层只做外部模型服务的适配；智能体层把这些零件装成普通对话或工具循环。这样取消、恢复和错误不会散落在一个大循环里。

这段话适合先让面试官知道你看到了整体。若对方追问“工作笔记是什么”“为什么能恢复”，再展开下一节的一分钟版本，不必第一句话就塞满所有术语。

### 15.2 一分钟版本

> goHarness 的核心是强类型执行图。所有能力先通过统一可执行协议 `Runnable[I, O]` 调用，消息用有序内容块保留多模态和工具调用关联。执行图在编译阶段用反射验证节点签名、边和运行状态处理器，在运行时负责分支、步数、并行运行状态隔离和带类型中断后的恢复。工具运行环境单独治理副作用，包括审批、鉴权、中间件、超时、只读重试和并发组。模型适配层把模型服务的增量事件统一为标准消息；上下文整理器在每次模型调用前做预算和角色整理。智能体只是用这些组件装配基础对话、工具循环、路由和群聊，因此底层能力可以独立测试和复用。

### 15.3 高频拷问题的回答抓手

| 面试官问什么 | 不要只说概念 | 用源码说什么 |
| --- | --- | --- |
| 为什么自己做执行图，不写循环？ | “更灵活” | `Compile()` 把类型和拓扑错误前移，执行图提供节点事件、运行状态、并行和恢复记录 |
| 为什么要用反射？ | “泛型不够用” | 执行图节点异构，外层只有输入、输出泛型，`bindRuntimeNode` 校验实际 `Invoke` 签名 |
| 流会不会泄漏协程？ | “用请求上下文” | 无缓冲 `Pipe`、`Reader.Close` 反向取消、`Send` 同时监听结束与请求取消 |
| 工具失败会不会中断智能体？ | “看情况” | `Result.IsError` 是模型可见内容，Go 语言的 `error` 是运行控制错误，`ToolsNode` 的转换路径不同 |
| 为什么只重试只读？ | “避免重复” | 写操作可能已成功但响应丢失；幂等键应由业务提供 |
| 继续运行是否恰好一次？ | “不保证” | 恢复记录保存的是节点边界与运行状态，不存在原子包住外部副作用和会话检查点的事务 |
| 回调为什么不能鉴权？ | “职责单一” | `Dispatch` 错误被隔离；只有中间件持有 `next` 和阻断能力 |
| 提示词缓存是不是结果缓存？ | “是优化” | 上下文整理器只写断点元数据，真实命中看模型服务返回的用量字段 |
| 智能体为什么不单独调度？ | “避免重复” | `agentrecipe.NewToolRecipe` 用执行图组装模型、工具、模型的循环 |

```text
1. 数据是什么类型，谁拥有可变状态？
2. 调用者取消时，信号能否传到真正阻塞的上游？
3. 这个错误是控制流错误，还是应交给模型继续推理的内容？
4. 节点重试或继续运行时，外部副作用如何避免重复？
```

能持续回答这四个问题，比背诵每个构造函数更能经得住追问。

## 16. 建议的源码阅读顺序

第一次不要从最复杂的工具循环源码一头扎进去，也不要从最底层接口文件开始死背。先看一个可运行故事，再带着问题向下读。每读一步，先写下一句自己的回答，再进入下一步：

```text
第零步：examples/basic/main.go
  问题：模型什么时候请求工具，审批后怎样继续？
  目标：只跟变量流动，不理解每个包也没关系。

第一步：pkg/schema/message.go, block.go
  问题：一条消息为什么不能只有字符串？
  目标：分清文字、工具调用、工具结果和调用标识。

第二步：pkg/runnable/runnable.go, stream_reader.go
  问题：模型、工具和普通函数怎样被同一种方式调用？流关闭如何传回上游？
  目标：理解完整值调用、连续输出和取消。

第三步：examples/graph/main.go, pkg/graph/runtime_graph.go
  问题：节点、边和本次运行的草稿纸分别是什么？
  目标：看懂 `teamState`、前置处理器、后置处理器和 `Compile()`。

第四步：pkg/state/checkpoint.go, pkg/graph/checkpoint.go
  问题：聊天历史、工作笔记、恢复书签为什么不能混在一起？
  目标：能解释至少一次恢复和幂等键。

第五步：pkg/tool/node.go, runtime.go, runtime_scheduler.go
  问题：为什么模型提出工具调用后仍要经过一层安全运行环境？
  目标：分清工具结果与执行错误，理解审批、超时、并发和只读重试。

第六步：pkg/llm/model.go, openai_compatible.go, response_stream.go
  问题：外部模型服务的不同返回格式怎样不污染业务代码？
  目标：理解适配、持续输出片段和保守重试。

第七步：pkg/contextengine/engine.go, pkg/agent/base.go, internal/agentrecipe/recipe.go
  问题：历史消息何时整理，标准智能体怎样把各层装配起来？
  目标：能从 `agent.New` 追到模型、工具循环和会话保存。

第八步：pkg/callback, pkg/control, pkg/retrieval, pkg/httpclient, extensions
  问题：观察、业务中断、知识检索和可选基础设施为何不写进核心流程？
  目标：理解边界；按项目需要选择深入程度。
```

每读完一个源码文件，都应同时打开同名或相邻测试文件。先看测试名称猜行为，再看断言和实现；这比一次读几百行生产代码更容易建立“这个函数承诺什么、边界在哪里”的感觉。读到最后再回看 `examples/basic/main.go` 和 `examples/graph/main.go`，你看到的就不再只是“创建一个智能体”或“加几个节点”，而是整套数据协议、执行协议、状态边界和外部副作用治理在一次调用里的组合。
